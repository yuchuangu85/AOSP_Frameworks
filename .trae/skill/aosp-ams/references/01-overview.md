# 8.1 基本目标

Android 不只是“内存不够就随机杀进程”，而是要回答：

- 哪些进程最重要
- 哪些虽然不在前台，但仍有用户感知
- 哪些处于绑定链上不能轻易杀
- 哪些进程只是缓存可牺牲
- 哪些进程在当前屏幕状态下仍应被保留

为此 Android 构建了三层模型：

1. **procstate**：进程语义状态
2. **oom_adj / adj**：杀进程优先级近似表示
3. **LMKD 决策**：在内存压力下执行真正 kill

# 8.4 OOM_ADJ 的语义

OOM_ADJ 是对“该进程在内存压力下多容易被杀”的近似编码。
 一般来说：

- 越重要，adj 越低 / 越不容易被杀
- 越不重要，adj 越高 / 越容易被杀

### 专家理解要点

- OOM_ADJ 不是独立计算，它依赖 procstate、连接关系、当前前后台、可见性、FGS、provider/service 绑定等
- “为什么被杀”本质上经常是“为什么最终 adj 这么高”
- 问题定位不能只看被杀瞬间，还要看 adj 演化历史

# 8.8 LMKD 协同模型

LMKD 是最终执行低内存 kill 的组件，但它的输入并不是凭空来的。

### AMS/OomAdjuster 提供的东西

- 当前进程重要性
- procstate / adj
- 进程列表相关信息
- 状态更新时序

### LMKD 综合考虑

- 内存压力
- PSI / reclaim 压力
- minfree / pressure level
- 进程重要性与排序

### 专家结论

- “是 LMKD 杀的”只是结果
- 真正问题通常要往前追到：
  - 为什么它被打到了这个 adj
  - 为什么它在 LRU 中处于这个位置
  - 为什么当时系统进入了这种 pressure
  - 是否存在前台感知错位

# 10.7 LMKD / 回收类（81~90）

1. LMKD kill 被误判为 crash
2. 低内存压力峰值短暂触发误感知 kill
3. 进程被杀前已降为 cached 但用户仍误认为前台
4. 多个后台服务竞争导致目标进程更易被杀
5. 大内存 provider 进程先触发牺牲
6. app 频繁拉起导致成为高 churn 对象
7. 屏幕切换场景 memory pressure 暂时放大
8. 系统更新/安装阶段内存挤压触发 kill
9. 高优先级进程过多导致边界进程牺牲
10. kill 后自动恢复链再触发二次抖动
