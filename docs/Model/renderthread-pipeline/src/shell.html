RENDERTHREAD · GPU · EGL · BLAST
ONE FRAME · NINE STAGES

一句话版本：UI 线程在 syncAndDrawFrame() 里把任务投进 RT 队列并阻塞； RT 的 DrawFrameTask::run() 先 syncFrameState() 同步 RenderNode 树和纹理， 再 prepareTree() 更新属性、动画与 damage；一旦树同步完成，UI 就可以被解除阻塞去准备下一帧。 随后 CanvasContext::draw() 回放 DisplayList、提交 GPU，eglSwapBuffers 触发 dequeue/queueBuffer；BLAST 把 buffer 连同 Transaction 直接提交给 SurfaceFlinger。 RT 不会等上屏，只登记 callback 与 fence。

01RT 不是“另一个 draw 线程”

它持有 EGL context、RenderState、CacheManager 与 GPU context；UI 线程的 draw 只录制 DisplayList，真正的 GPU 回放与资源上传在 RT 上完成。

02UI 只等“树同步”，不等 GPU

syncFrameState 完成 prepareTree 后即可 unblockUiThread()；UI 可继续下一帧，而 RT 仍在回放命令、等 fence、queueBuffer。

03RT 不等待显示

RT 只负责把 buffer 和 Transaction 交给系统，登记 commit/present callback。上屏、retire、buffer 回收由 SurfaceFlinger / HWC 的时间线驱动。

03 / CONCURRENCY & FENCES

谁在等谁：UI、RT、GPU 与 BufferQueue 的并发边界

理解 RenderThread 的关键不是背调用链，而是知道每个同步点阻塞谁、不阻塞谁。下面把一帧里重要的等待关系单独拆出来。

UI 线程只在 postAndWait 期间被阻塞；解阻后可以开始下一帧。RT 的 draw 与 GPU 执行是异步的：flushAndSubmit 只负责提交命令，GPU 完成由 fence 回传。

A为什么 UI 不能等 GPU？

如果 UI 等 GPU 完成，下一帧的输入、动画和 measure/layout 都会被 GPU 延迟串行化。hwui 把 CanvasContext::draw 留在 RT，UI 只等“树同步”这个较短的阶段。

B为什么 RT 不能等 SF？

RT 的职责是把 buffer 与 Transaction 交给系统。上屏时刻由 SurfaceFlinger / HWC 的 VSYNC 与 fence 决定；如果 RT 同步等待上屏，就会阻塞下一帧的 GPU 提交。

C哪些操作会反过来阻塞 RT？

dequeueBuffer 等不到 free slot、prepareTextures 纹理缓存耗尽、GPU 上下文丢失/重建、waitOnFences 等 acquire fence，都会让 RT 的“异步”变成实际阻塞。

// RT 一帧的 CPU 时间（简化） T_rt ≈ T_syncFrameState + T_prepareTree + T_issueDrawCommands + T_swapAndQueue // T_issueDrawCommands = DisplayList 回放 + flush/submit（不含 GPU 完成） // UI 阻塞窗口（简化） T_ui_blocked ≈ T_syncFrameState + T_prepareTree // unblockUiThread 之后 UI 线程继续下一帧 // 帧是否赶上 deadline deadline (8.3ms) ≥ T_ui_draw + T_ui_post_wait + T_rt_work + T_queue_and_transaction

RT 内部：同步/准备变慢

  • RenderNode 树大、属性更新多：prepareTree 遍历成本上升。
  • 纹理上传/图片解码：prepareTextures、uploadIfNeeded 占用 RT。
  • 动画回调/属性动画在 RT 上执行，AnimationContext 超出预算。

GPU / EGL：提交或换缓冲变慢

  • 过度绘制、复杂 Shader、大图层：SkiaOpenGLPipeline::draw 变长。
  • dequeueBuffer 等不到 free slot：BufferQueue 被填满。
  • eglSwapBuffers 被 GPU/驱动阻塞，RT 無法继续下一帧。

BLAST / SF：交接延迟

  • Transaction 错过 SF 的取帧相位：本帧只能下一拍上屏。
  • acquire fence 未 signal：latch 不成立，SF 请求重合成。
  • RT 侧只登记 callback；上屏延迟不直接阻塞 RT。

观测要点

  • DrawFrames <vsyncId> 总括 RT 一帧。
  • flush commands / queueBuffer / Transaction apply 定位交接点。
  • FrameTimeline 对齐 GPU completion、present、release。
