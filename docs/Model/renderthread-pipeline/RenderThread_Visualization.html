01RT 不是“另一个 draw 线程”

它持有 EGL context、RenderState、CacheManager 与 GPU context；UI 线程的 draw 只录制 DisplayList，真正的 GPU 回放与资源上传在 RT 上完成。

02UI 只等“树同步”，不等 GPU

syncFrameState 完成 prepareTree 后即可 unblockUiThread()；UI 可继续下一帧，而 RT 仍在回放命令、等 fence、queueBuffer。

03RT 不等待显示

RT 只负责把 buffer 和 Transaction 交给系统，登记 commit/present callback。上屏、retire、buffer 回收由 SurfaceFlinger / HWC 的时间线驱动。

01RenderThread 的创建与线程模型

每进程一条 Looper 线程：getInstance → initThreadLocals → WorkQueue 串行执行

进程内第一次需要硬件加速渲染时，RenderProxy 的构造函数在初始化列表里调用 RenderThread::getInstance()（RenderProxy.cpp:51），后者用 [[clang::no_destroy]] 的函数内 static 构造唯一实例并 start("RenderThread")，因此每个进程只有一条 RenderThread。这条线程是普通 pthread（ThreadBase : android::Thread）+ 一个自建 Looper，在 threadLoop 里把优先级提到 PRIORITY_DISPLAY、把 Looper 绑到本线程，然后调用 initThreadLocals() 建好 Choreographer、EglManager、RenderState、VulkanManager、CacheManager，之后进入 waitForWork()/processQueue() 的永久循环。所有跨线程请求都以 std::function 投进这条线程的 WorkQueue，按 runAt 排序串行执行；需要返回值时用 WorkQueue::runSync 以 packaged_task 阻塞调用方。RenderThread 还通过 AChoreographer 持有自己独立的 vsync 通道，从而能在 UI 线程之外驱动 RT-only 动画。

android_view_ThreadedRenderer_createProxy()→RenderProxy::RenderProxy()→RenderThread::getInstance()→ThreadBase::start()→RenderThread::threadLoop()→RenderThread::initThreadLocals()→RenderThread::initializeChoreographer()→ThreadBase::waitForWork()→WorkQueue::process()→RenderThread::dispatchFrameCallbacks()

触发者：谁第一次拉起 RenderThread

Java 侧第一次需要硬件加速渲染时，HardwareRenderer 通过 JNI 的 nCreateProxy 进入 android_view_ThreadedRenderer_createProxy()（base/libs/hwui/jni/android_graphics_HardwareRenderer.cpp:189），该函数 new RenderProxy(translucent, rootRenderNode, &factory, useIpcCanvas)。而 RenderProxy 的构造函数初始化列表第一项就是 mRenderThread(RenderThread::getInstance())（RenderProxy.cpp:51）——所以“谁创建了 RT”这个问题最终收敛到 getInstance()。

getInstance() 用一个 [[clang::no_destroy]] static sp<RenderThread> sInstance 的 lambda 完成惰性初始化：sp<RenderThread>::make() 构造对象，thread->start("RenderThread") 起线程，返回后把 gHasRenderThreadInstance 置 true。函数内 static 意味着每进程恰好一条：所有窗口、所有 CanvasContext 都挂在同一条线程的 WorkQueue 上串行执行。

这条线程一旦起来就不可回收：~RenderThread() 里直接 LOG_ALWAYS_FATAL("Can't destroy the render thread")（RenderThread.cpp:197-201）。所以“销毁 renderer”只是 delete CanvasContext，Runtime 级别的 RT 生命周期等于进程生命周期。

它是一条普通 pthread + 一个 Looper，不是 binder 线程

class RenderThread : private ThreadBase（RenderThread.h:86），而 ThreadBase : public Thread 且内含 sp<Looper> mLooper 与 WorkQueue mQueue（platform/android/thread/ThreadBase.h:30-37）。WorkQueue 的唤醒回调就是 mLooper->wake()，即“有新任务”与“Looper 醒来”是同一件事。

threadLoop() 的第一行是 setpriority(PRIO_PROCESS, 0, PRIORITY_DISPLAY)，随后 Looper::setForThread(mLooper)。这里要诚实说明：PRIORITY_DISPLAY 与 android::Thread/Looper 的定义在 system/core，不在本仓库快照内，因此 PRIORITY_DISPLAY 的具体数值“源码中未体现”；能确认的只有符号语义。

它不是 binder 线程：在 base/libs/hwui 全目录检索 IPCThreadState、joinThreadPool、ProcessState::self 均无命中，RT 从头到尾只 poll 自己的 Looper。生产代码里对这条 Looper 只有一次 addFd，即 Choreographer 的 display-event fd（RenderThread.cpp:213-214）；vsync 到达对 RT 而言是“fd 可读”，不是 binder 回调。但要注意：不是 binder 线程 ≠ 不做 binder 调用，requestNextVsync() 就是一次到 SF 的 oneway binder。

initThreadLocals：Choreographer、图形上下文与缓存的建立顺序

threadLoop() 在进入主循环之前调用一次 initThreadLocals()，顺序是：

  • setupFrameInterval()：从 DeviceInfo::getVsyncPeriod() 取周期写入 mTimeLord.setFrameInterval()（221-233），这样即使在拿到真实 vsync 之前 TimeLord 也有一个合法的帧间隔；
  • initializeChoreographer()：建 AChoreographer、注册刷新率回调、把 fd 加进 Looper、生成 ChoreographerSource；Properties::isolatedProcess 为真时改用 DummyVsyncSource（每 16ms 自己 postDelayed 造一个假 vsync，140-160）；
  • new EglManager()、new RenderState(*this)、VulkanManager::getInstance()、new CacheManager(*this)。

注意 EGL/Vulkan 上下文是懒创建的：initThreadLocals 只建管理器，真正的 MakeGL()/createContext() 在 requireGlContext()/requireVkContext() 里（235-270），由 preload() 提前投递（487-498）或第一帧 makeCurrent() 触发。构造本身不碰 GPU，这对首帧启动耗时很关键。

VulkanManager::getInstance() 是单例，源码注释明确指出它可能被 HardwareBitmapUploader 共享而 Vk 上下文已经建好、但 RT 的 mGrContext 仍为空，所以 requireVkContext() 必须两个条件都检查（254-261）。

WorkQueue：单线程串行、按时刻排序、runSync 阻塞调用方

WorkQueue（base/libs/hwui/thread/WorkQueue.h）只有一条 std::vector<WorkItem>。process() 在持锁时把整条队列 move 出来、把 runAt > now 的项塞回，然后在无锁状态下于 RT 线程上顺序执行（62-80）。这就是“hwui 的单线程渲染模型”的全部机制：并行度为零，顺序由 runAt 再按插入位置决定。

post()/postDelayed()/postAt() 只是入队（82-95）；enqueue 按 runAt 找插入点，只有插到队首时才调用 mWakeFunc()（121-134），避免无谓唤醒 RT。

runSync() 是唯一的同步原语：把可调用对象包成 std::packaged_task、post 进去、再 get_future().get() 阻塞调用线程（105-110）。RenderProxy 的构造函数正是用它创建 CanvasContext，保证返回时 context 已在 RT 上构造完毕（58-66）。反过来，destroyContext() 用 runSync([](){}) 当 fence，注释写得很直白：必须确认没有在途的 DrawFrameTask 才能真正 delete（74-82）。

工程含义：任何 runSync 都是一次 UI↔RT 握手，如果 RT 正卡在 prepareTree 或 queueBuffer，UI 线程会跟着一起卡；排查“UI 线程无故阻塞”时要先看 RT 当前在跑什么。

ChoreographerSource：RT 拥有自己的一条 vsync 通道

RT 不是被动等 UI 叫它，它有自己的 frame callback 机制（class IFrameCallback，RenderThread.h:66-73，注释写“Mimics android.view.Choreographer.FrameCallback”）。链路是：

  • requestVsync() 用 mVsyncRequested 去重后调 mVsyncSource->requestNextVsync()（403-408）；
  • ChoreographerSource::requestNextVsync() 即 AChoreographer_postVsyncCallback(...，RenderThread::extendedFrameCallback，this)（127-130），底层落到 DisplayEventReceiver::requestNextVsync() → mEventConnection->requestNextVsync()（native/libs/gui/DisplayEventReceiver.cpp:93-99），是一次到 SF Scheduler 的 binder；
  • vsync 到达后 fd 可读 → Looper → RenderThread::choreographerCallback()（365-383）→ AChoreographer_handlePendingEvents → extendedFrameCallback() 解出 vsyncId/deadline/frameTime（61-74）→ frameCallback()（76-114）。

frameCallback() 里有两个去重门：TimeLord::vsyncReceived() 返回 false（旧 vsync）则丢弃；mFrameCallbackTaskPending 已置位则不再重复投递。真正投递时用 queue().postAt(runAt，dispatchFrameCallbacks)，runAt 默认取 frameTime + (deadline-frameTime)/4，即“在 deadline 前 3/4 处开跑”；若 use_prev_frame_duration_for_render_thread 打开，则用 estimateCallbacksExpectedDuration()（各 callback 期望时长之和再乘 4/3 膨胀，410-418）反推起点，注释说明这是为了给 UI 线程留出生产这一帧的机会（99-107）。

dispatchFrameCallbacks() 把 mFrameCallbacks swap 出来、若非空则先 requestVsync() 预取下一帧、再逐个 doFrame()（385-401）。CanvasContext 就是 IFrameCallback，RT-only 动画走的就是这条路径——这也是“UI 不参与也能动画”的底层机制。

排障：怎么确认卡在哪一步

三条可用的观测手段：

  1. 线程视图：Perfetto/top -H 里找 RenderThread，确认它是否存在、是否在 Running、是否被 futex_wait 挂在 WorkQueue 的 mLock 上。如果 RT 长期 idle 而 UI 卡住，多半是 UI 在 runSync 里等一个永远不会被执行的队列项。
  2. atrace：queue mFrameCallbackTask to run after %.2fms 这条 instant 事件直接给出“本次回调计划在 deadline 前多久开跑”（RenderThread.cpp:109）；DrawFrames <vsyncId> 标记每帧绘制开始；earlyPreloadGlContext 标记预加载。SF 侧 RenderRate（DisplayEventDispatcher.cpp:182）告诉你当前渲染帧率。
  3. dumpsys gfxinfo：走 RenderThread::dumpGraphicsMemory（314-330），会打印 pipeline 类型与各 CanvasContext 的 cache 使用、TextureView 尺寸。

一个高频误判：看到 RT 上出现 binder 相关栈就断定“RT 是 binder 线程”——实际上那是 requestNextVsync 的 oneway 调用，线程主体仍然是 Looper + WorkQueue。

!坑点与边界
误以为每个窗口/每个 View 一条 RenderThread：实际是每进程一条（getInstance 的函数内 static），所有 CanvasContext 共享一条 WorkQueue，所以任何一个窗口的重活都会推迟其他窗口的帧。
误以为 RenderThread 是 binder 线程：base/libs/hwui 内没有任何 IPCThreadState/joinThreadPool；vsync 走 DisplayEventReceiver 的 BitTube fd。但 requestNextVsync 仍是 oneway binder，看到 binder 栈不代表线程类型是 binder。
误以为 queue().post 是“在 RT 上执行完才返回”：post 只入队；需要同步必须用 runSync（packaged_task + future.get）。RenderProxy 构造函数用 runSync、而 setSurface/setSwapBehavior 用 post，两种语义不能混用。
把 PRIORITY_DISPLAY 当成“一定不被抢占”：setpriority 只改 nice 值，且 PRIORITY_DISPLAY 的数值与线程 cgroup/调度策略定义都不在本仓库快照内，源码中未体现其具体效果。
以为 RenderThread 可以被销毁重建：~RenderThread 是 LOG_ALWAYS_FATAL，配合 [[clang::no_destroy]]，任何“销毁 RT 再重建”的方案都会直接 crash。
在 UI 线程高频调用任何 runSync 接口（如 copyLayerInto、buildLayer、createTextureLayer）：每一次都是 UI↔RT 阻塞握手，RT 越忙 UI 卡得越久。
误读 mVsyncRequested/mFrameCallbackTaskPending 只是性能优化：它们同时承担“一个 vsync 只渲染一帧”的正确性职责，去掉会出现同一帧被画两次或回调永久饿死（threadLoop 里 440-446 的补丁注释就是历史事故）。

ThreadedRenderer.draw 末尾同步投递：JNI 拷 14 个 long，然后 UI 线程在 mSignal 上等

UI 线程走完 measure/layout/draw 之后，ThreadedRenderer.draw() 在末尾取本次用于 jank 统计的 FrameInfo，调用继承自 HardwareRenderer 的 syncAndDrawFrame(frameInfo)，进入 native 的 nSyncAndDrawFrame。JNI 层先断言传入长度等于 UI_THREAD_FRAME_INFO_SIZE(=14)，再用 GetLongArrayRegion 把这 14 个 long 一次性拷进 DrawFrameTask 自带的 mFrameInfo 数组，然后调用 RenderProxy::syncAndDrawFrame() → DrawFrameTask::drawFrame()。drawFrame 重置 mSyncResult、把当前时刻记进 mSyncQueued，然后进入 postAndWait()：持 mLock 把 run() 投进 RenderThread 的 WorkQueue，随后在 mSignal 上 wait。RT 侧执行 run() 时会构造 TreeInfo(MODE_FULL) 并调用 syncFrameState()，一旦树同步完成且纹理准备成功，就在 context->draw() 之前 signal 唤醒 UI 线程，让 UI 立刻回去准备下一帧；返回的位标志再告诉 UI 是需要强制 relayout、再 invalidate 一次、还是本帧已被丢弃。整个握手只阻塞一次、零 IPC、零 Parcel。

触发者：draw() 的最后一行才是交棒点

ThreadedRenderer.draw(View, AttachInfo, DrawCallbacks)（base/core/java/android/view/ThreadedRenderer.java:827）先把 attachInfo.mViewRootImpl.mViewFrameInfo.markDrawStart() 打进 FrameInfo，再 updateRootDisplayList() 把所有 RenderNode 的 DisplayList 更新/重录完，补注册历史遗留的 animating node，最后才取 final FrameInfo frameInfo = attachInfo.mViewRootImpl.getUpdatedFrameInfo() 并 syncAndDrawFrame(frameInfo)（846-848）。

注意此时还没有发生任何与 GPU 的交互：UI 线程只完成了“把要画什么记录下来”的工作，真正的同步与绘制在 RT 上。ThreadedRenderer 自己并没有实现 syncAndDrawFrame，它继承自 HardwareRenderer（ThreadedRenderer.java:67 extends HardwareRenderer），实现在 HardwareRenderer.java:595-597：return nSyncAndDrawFrame(mNativeProxy, frameInfo.frameInfo, frameInfo.frameInfo.length)，native 声明在 HardwareRenderer.java:1845。

JNI：一次数组拷贝完成参数传递

android_view_ThreadedRenderer_syncAndDrawFrame（base/libs/hwui/jni/android_graphics_HardwareRenderer.cpp:464-473）做三件很薄的事：

  1. 长度校验：LOG_ALWAYS_FATAL_IF(frameInfoSize != UI_THREAD_FRAME_INFO_SIZE, ...)，Java 侧 FrameInfo.FRAME_INFO_SIZE = ANIMATION_TIME + 1 = 14（base/graphics/java/android/graphics/FrameInfo.java:106），native 侧 static constexpr size_t UI_THREAD_FRAME_INFO_SIZE = 14（base/libs/hwui/FrameInfo.h:34）。注释明确写“This value must be in sync with FRAME_INFO_SIZE in FrameInfo.Java”。
  2. 零拷贝以外的唯一拷贝：env->GetLongArrayRegion(frameInfo, 0, frameInfoSize, proxy->frameInfo())，目标是 RenderProxy::frameInfo() 返回的 mDrawFrameTask.frameInfo()，也就是 DrawFrameTask::mFrameInfo 这块 int64_t[UI_THREAD_FRAME_INFO_SIZE] 的固定缓冲（DrawFrameTask.h:127）。Java long[] → native int64_t[14] 就是这一次 memcpy，之后 UI 线程不再参与数据传递。
  3. 同步进入 RT：return proxy->syncAndDrawFrame()。

这条路径没有任何 Parcel/Binder 参与——它是同一个进程内的 JNI 直接调用，UI 线程用自己的栈一直走到 mSignal.wait()。这也解释了为什么 mFrameInfo 必须是“预先打包成 long[]”的：把一个结构化对象跨 JNI 传，代价远大于拷 112 字节。

mLock / mSignal：阻塞与解阻塞的确切协议

三个函数构成完整的握手：

  • drawFrame()（DrawFrameTask.cpp:72-80）：断言 mContext 非空，mSyncResult = SyncResult::OK，mSyncQueued = systemTime(SYSTEM_TIME_MONOTONIC)，然后 postAndWait()，返回时把 mSyncResult 交给上层。
  • postAndWait()（82-87）：AutoMutex _lock(mLock) → mRenderThread->queue().post([this]{ run(); }) → mSignal.wait(mLock)。先持锁再 post是必要的：如果 post 之后、wait 之前 RT 就跑完 unblockUiThread() 并 signal，这次 signal 会丢失，UI 线程将永久阻塞。持锁 post 保证 RT 即使立刻拿到锁，也必须等 UI 释放锁进入 wait 之后才能 signal。
  • unblockUiThread()（219-222）：AutoMutex _lock(mLock) + mSignal.signal()。它在 run() 里被调用两次位置：canUnblockUiThread 为真时在 draw() 之前（125-127），否则在帧末（159-161）。

所以“UI 线程什么时候解阻塞”取决于 syncFrameState() 的返回值：return info.prepareTextures（216）。只要树同步完成且 pinImages 没有因为 GPU 纹理缓存耗尽而失败，UI 就被提前放走，让 RT 独自去画；否则 UI 必须陪跑到整帧结束——这是 hwui 在显存紧张时的保守策略。RT 单线程保证了 task 正文本身不需要锁，mLock 只用来保护“唤醒先后顺序”。

与 BufferQueue / BLAST / SF 的边界：这一阶段什么都没上屏

必须强调：syncAndDrawFrame() 返回时帧还没有被提交到 Surface。本阶段完成的是：DisplayList 树的所有权/内容交接到 RT、FrameInfo 交接、UI 线程放行。真正的 dequeueBuffer/queueBuffer 与 BLAST 事务在 CanvasContext::draw() 的 pipeline 内部完成，帧提交回调（mFrameCallback 的 frameCommitCallback）也只在 run() 里被 enqueueFrameWork 排队（130-138）。

与 SF 的交集只在数据层面：mFrameInfo[FrameTimelineVsyncId] 一路传到 pipeline，最终作为 frame timeline 的 vsyncId 交给 SurfaceFlinger 做帧时间线与刷新率决策；FrameInterval/FrameDeadline 决定 RT-only 动画的排程。若要“等上屏”，必须显式 FrameRenderRequest.setWaitForPresent(true)，它在 syncAndDraw() 里追加一次 fence()（HardwareRenderer.java:550-570，fence 实现在 866）。这也是文档里反复说的“默认不阻塞上屏、以便流水线化”。

跨进程视角：本阶段零 IPC。UI 线程与 RT 线程之间只有一块 112 字节的 int64_t[14]、一个 Mutex、一个 Condition 和一个 std::function 队列项。

排障：UI 卡在 syncAndDrawFrame 上怎么定位

UI 线程栈停在 Condition::wait / DrawFrameTask::postAndWait 时，按下面顺序排查：

  1. RT 在干什么：抓 Perfetto 看 RT 线程当前 slice。若在 syncFrameState，说明是树同步/纹理上传慢；若已经在 Drawing/queueBuffer 而 UI 还没被唤醒，说明 prepareTextures 返回了 false（纹理缓存耗尽），UI 被设计性地扣到帧末。
  2. 任务是否入队：postAndWait 里 post 与 wait 都在 mLock 内完成，理论上不会丢唤醒。若 UI 永久阻塞，先怀疑 RT 已经卡死（例如 GPU hang、LOG_ALWAYS_FATAL 前一刻），可用 /data/anr 的 native 栈确认。
  3. 帧时长分解：FrameMetrics.SYNC_DURATION（metric id 5）对应 DURATIONS 表里的 SYNC_START → ISSUE_DRAW_COMMANDS_START（FrameMetrics.java:296-298），即 prepareTree 加纹理准备的耗时，不含排队；COMMAND_ISSUE_DURATION 是 ISSUE_DRAW_COMMANDS_START → SWAP_BUFFERS，即 RT 下发命令的耗时。而“交棒后到 RT 真正开始 sync”的 SyncQueued → SyncStart 并没有单列成 metric，它在 FrameInfo::duration() 里被当作 stalled 时间扣掉（FrameInfo.h:172-179）。DrawFrameTask::run() 里算出的 setSyncDelayDuration(now - mSyncQueued) 不进 jank tracker，而是（a）累加进交给 SF 的 dequeueBufferDurationNanos（CanvasContext.cpp:760-776），（b）从 ADPF hint session 上报的 actualDuration 里扣掉（CanvasContext.cpp:918-924）。
  4. 丢帧原因：返回值里带 SYNC_FRAME_DROPPED 时，去 FrameInfo 的 Flags/skippedFrameReason 对号入座（AlreadyDrawn / NoBuffer / NoOutputTarget / ContextIsStopped / NothingToDraw / DrawingOff），细节见 stage-03。

入口：run() 里的 TreeInfo 决定了本次同步的“模式”

DrawFrameTask::run() 在 RT 上先打 DrawFrames <vsyncId> 的 trace，再构造 TreeInfo info(TreeInfo::MODE_FULL, *mContext)、把 mForceDrawFrame 搬进 info.forceDrawFrame 并立刻清零，然后调用 syncFrameState(info)。之后它只读 info.out 的三个字段：canUnblockUiThread = syncFrameState(info)、canDrawThisFrame = !info.out.skippedFrameReason.has_value()、solelyTextureViewUpdates = info.out.solelyTextureViewUpdates（103-108）。

为什么模式在入口就定成 MODE_FULL？因为 TreeInfo::TraversalMode 的注释写得很清楚：MODE_FULL 是“the full monty - sync, push, run animators, etc... Used by DrawFrameTask”，且只有在 UI 线程与 RT 线程都阻塞在 prepare 上时才允许使用；MODE_RT_ONLY 是“只在 RT 上安全可做的事”（TreeInfo.h:66-76）。而此刻 UI 线程正卡在 mSignal.wait() 里，正是 MODE_FULL 成立的前提。同一个 CanvasContext::prepareTree 在别的调用点（如 buildLayer）可能用别的模式。

还有一条容易忽略的约束：DrawFrameTask::run() 在调用 syncFrameState 之前先把 mFrameCommitCallback 交给 mContext->addFrameCommitListener（110-113），保证即使这一帧被 drop，注册的 commit 回调也不会丢。

TimeLord::vsyncReceived：为什么第一次调用可能是“假同步”

syncFrameState() 的第一件事是把 mFrameInfo 里 5 个时间字段交给 mRenderThread->timeLord().vsyncReceived(vsync, intendedVsync, vsyncId, frameDeadline, frameInterval)（176-177）。TimeLord 是两个独立判定拼起来的（TimeLord.cpp:31-51）：

  • intendedVsync 段：只有 intendedVsync > mFrameIntendedTimeNanos 才更新 mFrameIntendedTimeNanos、mFrameVsyncId、mFrameDeadline、mFrameIntervalNanos。注释解释了 vsyncId 的处理：intendedVsync 可能因为调度抖动被前推，但我们没办法把 vsyncId 一起前推，所以直接把它重置成 INVALID_VSYNC_ID（mFrameVsyncId = (vsyncId > mFrameVsyncId) ? vsyncId : INVALID_VSYNC_ID）。这意味着“去重后的 vsyncId 可能变成 -1”，下游必须能接受。
  • vsync 段：只有 vsync > mFrameTimeNanos 才返回 true。返回值才是“这是一帧新的 vsync”的唯一判据，syncFrameState 虽然没检查返回值，但 CanvasContext::prepareTree 会用 timeLord().latestVsync() 与 mSwapHistory.back().vsyncTime 比较，差值 < 2ms 就判 AlreadyDrawn 丢帧（见 CanvasContext.cpp:582-594）。

所以“UI 已经画过这一拍、RT 才被叫醒”这种情况不会被重复画两次，而是变成一个带原因的 skipped frame。另外 computeFrameTimeNanos() 里复制了 Choreographer 的抖动修正逻辑（jitter >= frameInterval 时把 frameTime 对齐到 now - jitter % interval，53-64），说明 RT 的时间基准与 UI 侧是同源的。

makeCurrent / unpinImages / layer apply：顺序不是随意的

syncFrameState 中间这段（178-191）有三步，每一步都有原因：

  1. bool canDraw = mContext->makeCurrent();：CanvasContext::makeCurrent()（439-459）在 mStopped 时直接返回 false，否则调 mRenderPipeline->makeCurrent()；Failed 时还会 mHaveNewSurface = true; setSurface(nullptr);。这就是“上下文被停掉/丢失”的检测点，后面 !canDraw 会变成 ContextIsStopped。
  2. mContext->unpinImages();：CanvasContext.h:121 里就是一行内联 mRenderPipeline->unpinImages()；SkiaGpuPipeline::unpinImages() 对每个 mPinnedImages 调 skgpu::ganesh::UnpinTexture() 然后 clear()（SkiaGpuPipeline.cpp:130-135）。为什么必须在 prepareTree 之前：pin 的语义是“把 mutable image 钉在 GPU 缓存里，一直钉到下一次 UI 线程 draw”（SkiaDisplayList.cpp:96-98 注释），而本帧 prepareTree 里的 pinImages() 会重新 pin；不先 unpin 就等于同一批纹理被重复持有，显存会一路涨。
  3. for (mLayers) mLayers[i]->apply(); 然后 mLayers.clear()：DeferredLayerUpdater::apply() 懒建 Layer、设置 colorFilter/alpha，若有 SurfaceTexture 且 mUpdateTexImage 为真，则 ASurfaceTexture_takeConsumerOwnership + ASurfaceTexture_dequeueBuffer(...) 取一帧，用 ImageSlot::createIfNeeded 包成 SkImage，再 updateLayer(...)（DeferredLayerUpdater.cpp:143-230）。dequeue 的 release fence 通过回调 createReleaseFence/fenceWait 交给 EGL 的 eglManager().fenceWait() 或 Vulkan 的 fenceWait()（129-141）——这是 hwui 里最典型的显式同步（explicit fencing）点。

注意 #ifdef __ANDROID__ 包住的是 layer apply，而 mLayers.clear() 在宏外面：即便在 host 构建下也要清空，否则跨帧状态会泄漏。

prepareTree：MODE_FULL 与 MODE_RT_ONLY 是按节点分的

mContext->prepareTree(info, mFrameInfo, mSyncQueued, mTargetNode) 才真正遍历树（CanvasContext.cpp:506-650）。开头先 mRenderThread.removeFrameCallback(this)（防止上一帧注册的 RT 动画回调与本帧打架），然后处理“上一帧是否被跳过”：若 mCurrentFrameInfo 带有 skippedFrameReason，就复用当前 FrameInfo 并把最老的 skipped 信息记进 mSkippedFrameInfo（只对 AlreadyDrawn/NoBuffer/NoOutputTarget 报告，DrawingOff/ContextIsStopped/NothingToDraw 不报，因为本来就没打算出帧）；否则 mCurrentFrameInfo = mJankTracker.startFrame()。

接着是模式的关键一行：

info.mode = (node.get() == target ? TreeInfo::MODE_FULL : TreeInfo::MODE_RT_ONLY);

代码在 for (const sp<RenderNode>& node : mRenderNodes) 循环里（560-567），注释说明：只有主目标节点（窗口内容）走 FULL，其余节点（非客户区/filler）以实时模式绘制。所以 MODE_FULL/MODE_RT_ONLY 不是“整个 context 的属性”，而是“本次遍历中每个节点的属性”，info.mode 在循环里被反复改写。

之后依次 mAnimationContext->startFrame(info.mode)（554）、node->prepareTree(info)、mAnimationContext->runRemainingAnimations(info)、freePrefetchedLayers()（568-572）。动画结果写进 info.out.hasAnimations/requiresUiRedraw，纹理 pin 结果写进 info.prepareTextures（下面单独讲）。

遍历完还有三道“是否真的能画”的闸门：无输出目标 → NoOutputTarget（576-580）；与 mSwapHistory.back().vsyncTime 差 < 2ms → AlreadyDrawn（582-594）；mRenderNodes.size() > 2 && !mRenderNodes[1]->isRenderable() → NothingToDraw（601-603）。最后 mNativeSurface->reserveNext() 向 BufferQueue 预定下一块 buffer，失败则 NoBuffer，且非 TIMED_OUT 的错误会直接 setSurface(nullptr) 认定 surface 死亡（605-619）。

SkippedFrameReason 只有六个枚举值（base/libs/hwui/SkippedFrameInfo.h:21-28），但产生位置分散在三个函数里，混淆它们会误判掉帧原因：

texture upload 与 UI 解阻塞：prepareTextures 是唯一的闸门

syncFrameState 的返回值是 info.prepareTextures（216），而 TreeInfo 构造时它是 prepareTextures(mode == MODE_FULL)（TreeInfo.cpp:23-29）——所以只有 FULL 遍历才做纹理准备。真正把它置 false 的地方在 SkiaDisplayList::prepareListAndChildren：

if (info.prepareTextures && !info.canvasContext.pinImages(mMutableImages)) {
    info.prepareTextures = false;
    info.canvasContext.unpinImages();
}

也就是：一旦某个 DisplayList 的 mutable image 无法 pin 进 GPU 缓存（SkiaGpuPipeline::pinImages 中 PinAsTexture 失败，或 GrContext 为空），就把本帧标记为“纹理没准备好”，并把已 pin 的全部 unpin 掉释放资源（SkiaDisplayList.cpp:93-105，SkiaGpuPipeline.cpp:115-135）。

这个 boolean 一路传回 DrawFrameTask::run() 变成 canUnblockUiThread：为 true 时在 context->draw() 之前就 unblockUiThread()（125-127），UI 线程立刻回去准备下一帧；为 false 时 UI 线程必须等到 draw() 结束、frameCompleteCallback 执行完之后才在 159-161 被放走。最后 if (!canUnblockUiThread) unblockUiThread(); 是兜底，保证任何路径都不会漏掉 signal（否则 UI 线程永久阻塞）。

配套的还有两条“帧被跳过”的收尾：canDrawThisFrame 为假时，run() 会对 grContext->flushAndSubmit() 手动 flush（注释：syncFrameState 可能已经做了纹理上传/删除，跳过 draw 会让它们堆在队列里），然后 context->waitOnFences() 等栅栏，避免任务与下一帧重叠（140-153）。也就是说“丢帧”不代表“没干活”：纹理上传可能已经发生，必须显式提交并等 fence。

排障：syncFrameState 慢或丢帧怎么定位

按信号从粗到细：

  1. 先看是不是 skip：FrameMetrics 里若这一帧被报为 skipped，检查 skippedFrameReason。六个值里 NoBuffer/AlreadyDrawn 属“节奏问题”（消费端慢或 UI 来晚），NoOutputTarget/ContextIsStopped 属“生命周期问题”（Surface 丢了/被 stop），NothingToDraw/DrawingOff 多半是预期行为，不用当 jank 治。
  2. 再看 sync 耗时：FrameMetrics.SYNC_DURATION = IssueDrawCommandsStart - SyncStart（FrameMetrics.java:296-298），即 prepareTree + 纹理准备的纯 RT 耗时；如果它大而 COMMAND_ISSUE_DURATION 小，问题在树同步/纹理；反之在绘制下发。
  3. 区分“等 buffer”与“画得慢”：Perfetto 里出现 swap chain stuffed（CanvasContext.cpp:502）说明 swapchain 堵住，RT 在等 BufferQueue 而不是在画，此时 reserveNext 或 swapBuffers 会长期占住 RT，进而让 UI 线程卡在 mSignal.wait() 上。
  4. 纹理：trace 里搜 Bitmap#prepareToDraw（SkiaGpuPipeline.cpp:140）与 PinAsTexture 相关 slice；如果 prepareTextures 频繁变 false，表现是“UI 线程阻塞时间被拉长到整帧”，这是显存/纹理缓存压力的典型症状。
  5. 动画：info.out.hasAnimations && info.out.requiresUiRedraw 会置 SYNC_REDRAW_REQUESTED，Java 侧 invalidate() 再来一帧；如果每帧都置位，说明动画无法在 RT 上自驱（例如有 WebView functor），此时 UI 每帧都要参与，jank 会明显上升。

04第 4 拍：prepareTree 遍历与脏区累积

UI 线程被阻塞的那段时间里，RenderThread 首次下树：同步属性、推进动画，把每处变化折算成 damage

DrawFrameTask 在 RenderThread 上跑 syncFrameState() 时，第一件事就是调用 CanvasContext::prepareTree()（base/libs/hwui/renderthread/CanvasContext.cpp:506）。此时 UI 线程还阻塞在 DrawFrameTask::postAndWait() 的 mSignal.wait() 上，所以这是一次“两边都停住”的树同步：RT 替 UI 把属性、DisplayList 与动画一次性对齐。prepareTree 先定下本帧的 FrameInfo（上一帧被跳过就沿用旧结构并记入 mSkippedFrameInfo，否则向 JankTracker::startFrame() 取新槽），把 damage 累加器、ColorArea、layer 更新队列与新的 damageGenerationId 装进 TreeInfo，再对 mRenderNodes 逐个调用 RenderNode::prepareTree()：只有等于 target 的节点走 MODE_FULL（提交 staging 属性与 DisplayList、跑动画），其余走 MODE_RT_ONLY（只跑动画），脏矩形经 push/pop 栈折算成帧级 damage。收尾后按 hasOutputTarget、本 vsync 是否已画、有无可画内容、reserveNext 是否成功写入 skippedFrameReason，决定 draw() 能否继续。

谁在跑这一拍：被 UI 线程等着的 RenderThread

触发者是 DrawFrameTask::run()（base/libs/hwui/renderthread/DrawFrameTask.cpp:89）：UI 线程先调 DrawFrameTask::drawFrame() → postAndWait()，把 run() 投进 RenderThread 的消息队列，然后自己阻塞在 mSignal.wait(mLock)（DrawFrameTask.cpp:82-87）。run() 里构造 TreeInfo info(TreeInfo::MODE_FULL, *mContext)，调用 syncFrameState(info)，其中 mContext->prepareTree(info, mFrameInfo, mSyncQueued, mTargetNode)（DrawFrameTask.cpp:191）就是本阶段。

mRenderNodes 与两种 TraversalMode

mRenderNodes 是 CanvasContext 上的 std::vector<sp<RenderNode>>（base/libs/hwui/renderthread/CanvasContext.h:384）。窗口场景下索引 0 是 backdrop（背景 + caption），索引 1 是 content，2 及以后是 overlay，这个布局在 SkiaPipeline.cpp:402-414 的注释里有完整说明。prepareTree 对每个节点单独定 mode：

  • MODE_FULL：只有 node.get() == target 的那个根节点（CanvasContext.cpp:564）。它才会执行 pushStagingPropertiesChanges()（RenderNode.cpp:237-239）与 pushStagingDisplayListChanges()（RenderNode.cpp:267-269），也就是把 UI 线程录制的 staging DisplayList 和 RenderProperties staging 值真正提交为当前值。
  • MODE_RT_ONLY：其余节点（非 client 的 filler 节点）。只执行 mAnimatorManager.animate(info)（RenderNode.cpp:249-251），不 push 任何 staging 内容。

所以“RT 动画帧”里看到的是旧属性 + 新动画值：动画能推进，但 UI 线程新的录制内容不会被采纳。这也解释了为什么同一套代码能同时服务“UI 帧”和“只有动画在动的帧”。

damage 从哪来：DamageAccumulator 的 push/pop 栈

TreeInfo 通过三行赋值接入脏区计算：info.damageAccumulator = &mDamageAccumulator、info.colorArea、info.layerUpdateQueue，外加 info.damageGenerationId = mDamageId++（CanvasContext.cpp:548-551）。RenderNode::prepareTree() 的第一行就是 LOG_ALWAYS_FATAL_IF(!info.damageAccumulator, "DamageAccumulator missing")（RenderNode.cpp:139），说明这个指针在真实路径上不允许为空。

遍历时的规则：prepareTreeImpl 一进来 info.damageAccumulator->pushTransform(this)（RenderNode.cpp:235），退出时 popTransform()（RenderNode.cpp:338），脏矩形在 pop 时被当前节点的变换矩阵映射后并入父级。damageSelf() 是脏的直接来源：getClipDamageToBounds() 为真时只脏 0,0,width,height，否则脏 DIRTY_MIN..DIRTY_MAX（RenderNode.cpp:158-164），并顺带把 info.out.solelyTextureViewUpdates 置 false（非 TextureView 时）。

特殊情况：同一帧里同一个节点被访问两次（被多个父节点引用）时，无法再算最小脏区，只能直接往父节点推全屏脏区（RenderNode.cpp:229-234）。最终 draw() 里 mDamageAccumulator.finish(&dirty) 取栈顶 pendingDirty 并 roundOut，同时把 pendingDirty 清空（DamageAccumulator.cpp:313-320）。

属性同步、动画推进与动画的尾巴

RenderProperties 是 staging/committed 双份结构。pushStagingPropertiesChanges() 只在 mDirtyPropertyFields 非 0 时动作：先 mAnimatorManager.pushStaging()，注释解释了顺序原因——setupStartValueIfNecessary() 必须在 properties 被 staging 覆盖前调用，否则某些 animator 拿不到起始值（RenderNode.cpp:352-362）；然后 damageSelf(info)、popTransform()、syncProperties()。

动画由 AnimatorManager::animate(info) 驱动，返回 animatorDirtyMask（RenderNode.cpp:250）。它的实现是先 mParent.damageSelf(info) 再 popTransform，跑完 animateCommon 后重新 pushTransform 并再次 damageSelf（AnimatorManager.cpp:137-152），所以动画既改属性又产生脏区，返回的 mask 里带 DISPLAY_LIST 等位。AnimationContext::startFrame(mode)（CanvasContext.cpp:554 → AnimationContext.cpp:55-65）把 mNextFrameAnimations 整条链表搬到 mCurrentFrameAnimations，并把 mFrameTimeMs 设为 ns2ms(mClock.latestVsync())——动画时间基准是 vsync 时钟，不是 systemTime。

遍历完 runRemainingAnimations(info)：把没有被树遍历覆盖到的动画节点（例如不在 target 子树里的）再跑一遍，MODE_FULL 下还会 animators.pushStaging()，并用 LOG_ALWAYS_FATAL_IF 断言 animate 一定把节点从当前帧链表摘掉（AnimationContext.cpp:67-78）。

freePrefetchedLayers()（CanvasContext.cpp:1147-1157）把 mPrefetchedLayers 里剩下的 layer 销毁并打印 “Incorrectly called buildLayer on View: %s, destroying layer...”——出现这条日志说明 buildLayer() 预取的 layer 没被本帧用上。texture 预取受 info.prepareTextures 控制（TreeInfo.h:83），预算耗尽时它被置 false，syncFrameState 把该值返回给上层做降级决策。

五种跳过理由，以及 reserveNext 的“预占”语义

prepareTree 尾部按固定顺序判定本帧能否继续：

  1. hasOutputTarget() 为假 → NoOutputTarget（CanvasContext.cpp:576-580）。判断依据是 mNativeSurface 或 mHardwareBuffer 是否存在（CanvasContext.h:162）。
  2. 本 vsync 已经画过：std::abs(lastSwap.vsyncTime - latestVsync) < 2ms → AlreadyDrawn（CanvasContext.cpp:582-597），注释说明 2ms 是给“vsync 被估算”留的容差。
  3. mRenderNodes.size() > 2 且 mRenderNodes[1]（content）不可渲染 → NothingToDraw（CanvasContext.cpp:601-603）。
  4. 以上都没有才 mNativeSurface->reserveNext()（CanvasContext.cpp:606）。ReliableSurface 会提前 dequeue 一个 buffer 占住（ReliableSurface.cpp:74-111），失败了返回 err 并写成 NoBuffer；若错误不是 TIMED_OUT，认为 surface 永久性损坏，直接 setSurface(nullptr) 并 return（CanvasContext.cpp:607-616）。
  5. DrawingOff 与 ContextIsStopped 不在 prepareTree 产生：前者在 draw() 的 skip lambda 里判 Properties::isDrawingEnabled() && mDrawingEnabled，后者在 syncFrameState 里判 makeCurrent() 失败（DrawFrameTask.cpp:196-205）。

命中 skip 后仍有收尾动作：info.out.hasAnimations || skippedFrameReason 为真时会向 RenderThread 请求下一帧回调（mRenderThread.postFrameCallback(this)，CanvasContext.cpp:621-632），RT 动画或 AnimatedImage 的延迟重绘也在这里排期（CanvasContext.cpp:634-649）。

05第 5 拍：draw 把脏区交给 GPU

finish 脏区 → computeDirtyRect 合并 bufferAge → pipeline->draw → swapBuffers → didSwap 打点与 commit 回调

DrawFrameTask::run() 判定 canDrawThisFrame 后调用 context->draw(solelyTextureViewUpdates)（base/libs/hwui/renderthread/DrawFrameTask.cpp:140-141），仍在 RenderThread 上，而 UI 线程可能已被放行去做下一帧的录制。draw 先用 mDamageAccumulator.finish() 取走本帧总脏区，再跑 skip lambda 判断 DrawingOff / NothingToDraw；跳过时并不直接返回，而是先 flushAndSubmit、waitOnFences，再以 didProduceBuffer=false 回调所有 commit listener。正常路径是：markIssueDrawCommandsStart、getFrame() 拿 buffer、computeDirtyRect() 按 bufferAge 并入 mSwapHistory 的历史脏区、用 ATRACE 打出绘图区域、mRenderPipeline->draw(...) 生成并提交 Skia 命令、waitOnFences() 等 CPU 任务、把 ANativeWindowFrameTimelineInfo 交给 native window、swapBuffers() 触发 EGL 或 Vulkan 呈现，最后按 didSwap 回调 listener(true)、更新 mSwapHistory 并上报 JankTracker 与 HintSession。这一拍是 UI 线程与 GPU 之间的分界：脏区在此定型，buffer 在此交换，本帧的成败也在这里就被决定——脏区算错会残留像素，拿不到 buffer 会掉帧，提交失败则要重建整个 surface。

触发条件：prepareTree 没给 skip 理由

DrawFrameTask::run() 在 syncFrameState(info) 之后拿到两个布尔量：canUnblockUiThread 与 canDrawThisFrame。后者就是 !info.out.skippedFrameReason.has_value()（DrawFrameTask.cpp:107）。为真走 context->draw(solelyTextureViewUpdates)；为假走 else 分支：若有 GrContext 就 grContext->flushAndSubmit()（注释说明这是为了把 syncFrameState 期间排队但没提交的纹理上传/删除做掉），然后 context->waitOnFences()，理由是“让任务不要和下一帧重叠”（DrawFrameTask.cpp:140-153）。

注意 canUnblockUiThread 可能先被兑现：如果 syncFrameState 里没有拿不到的信息，UI 线程在 unblockUiThread()（DrawFrameTask.cpp:125-127）就被放行去做下一帧的 measure/layout/draw 录制，而 RT 还在画当前帧。这正是 hwui 的流水线核心：UI 线程的“下一帧”和 RT 的“当前帧”并行，同步点由 BLAST/SurfaceControl 的 transaction 与 buffer 数量兜底。

脏区三段式：finish → clamp 到窗口 → bufferAge 合并

第一段是 mDamageAccumulator.finish(&dirty)（CanvasContext.cpp:685-686）：把 prepareTree 期间累积在栈顶的 pendingDirty 取出来并 roundOut，同时清空它（DamageAccumulator.cpp:313-320）。

第二段是 computeDirtyRect(frame, &dirty)（CanvasContext.cpp:1258-1307），返回窗口坐标系下的 windowDirty，并原地改写 dirty 为“这个 buffer 上必须重绘的帧区域”。三种情况直接判全屏：frame 宽高变化（不能依赖上一帧内容）、mHaveNewSurface 为真、frame.bufferAge() == 0（新 buffer）。否则先与窗口矩形求交，交不到就打 ALOGW 并清空。真正的巧思在 bufferAge：当 bufferAge() > 1 时，把 mSwapHistory 里最近 bufferAge-1 帧的 swap.damage 逐个 join 进 dirty（1303 之前），因为这块 buffer 上次被写是 bufferAge 帧之前。最后 dirty 为空则设为整帧。

第三段在 draw 里：windowDirty 被当作 screenDirty 传给 mRenderPipeline->draw(frame, windowDirty, dirty, ...)（742-744）与 swapBuffers(frame, drawResult, windowDirty, ...)（787-788）。两个矩形用途不同：dirty 决定画布上要重绘多大区域（含历史），windowDirty 决定 EGL 提交时告诉驱动的 damage 区域。

NothingToDraw 也要收尾：skip 分支的三个副作用

skip lambda 只有两个条件（CanvasContext.cpp:694-704）：!Properties::isDrawingEnabled() || !mDrawingEnabled → DrawingOff；dirty.isEmpty() && Properties::skipEmptyFrames && !surfaceRequiresRedraw() → NothingToDraw。surfaceRequiresRedraw() 在 mHaveNewSurface 为真、或 ANativeWindow 宽高与 mLastFrameWidth/Height 不一致时返回 true（CanvasContext.cpp:1247-1256），防止“空脏区的新 surface 永远不画”。

命中之后不是直接 return，而是做三件事（705-724）：（1） 记 setSkippedFrameReason；（2） 有 GrContext 就 flushAndSubmit()，注释写明目的是“保证纹理上传完成并让 Skia 释放 staging buffer”；（3） waitOnFences()，然后对每个 mFrameCommitCallbacks 以 false（didProduceBuffer）调用并清空。第三条最容易被忽略：commit 回调被调到，不等于本帧产出了 buffer。这个设计的理由是“不要让等待回调的人永久阻塞”。

进入正片：ScopedActiveContext activeContext(this)（726）把一个文件级静态指针 sActiveContext 指向当前 context（CanvasContext.cpp:73-86），供 CanvasContext::getActiveContext() 在深层的 functor/WebView 路径里反查。接着写 FrameInterval、markIssueDrawCommandsStart()（727-730），然后 Frame frame = getFrame()。

等待点：waitOnFences 等的是 CPU 任务，不是 GPU fence

mFrameFences 的类型是 std::vector<std::future<void>>（CanvasContext.h:405），由 enqueueFrameWork() 通过 CommonPool::async(std::move(func)) 填充（CanvasContext.cpp:1235-1237）。waitOnFences() 只是对每个 future 调 fence.get() 并清空（1225-1233），加了一层 ATRACE_CALL 便于观测阻塞时长。

当前源码里 enqueueFrameWork 唯一的调用点是 DrawFrameTask::run() 中执行 frameCallback 的那段（DrawFrameTask.cpp:130-138）：把用户注册的帧回调丢到线程池，回调返回的 frameCommitCallback 再被 addFrameCommitListener 收进 mFrameCommitCallbacks。所以 waitOnFences 等的是“帧回调跑完”，不是 GPU 完成。GPU 侧的显式等待只有两处：Properties::waitForGpuCompletion 为真时 EglManager::swapBuffers 先 fence()（EglManager.cpp:621-626，trace 名 “Finishing GPU work”），以及 Vulkan 用 presentFence 交给 swapchain。

另一处同步在 swapBuffers 前后：waitOnFences() 在 mRenderPipeline->draw(...) 之后、swapBuffers 之前调用（749），目的是保证本帧投出去的 CPU 任务（例如 layer 上传、snapshot 生成）在 buffer 被交出前结束。

FrameTimelineInfo：一帧的身份声明怎么交给 SF

mRenderPipeline->swapBuffers(...) 返回的 didSwap 与 requireSwap 共同决定后半段（CanvasContext.cpp:783-823）：requireSwap 由 pipeline 内部算（OpenGL 是 drawResult.success || mEglManager.damageRequiresSwap()），didSwap 是实际 exchanging 成功与否。若 requireSwap 为真：先 mIsDirty = false，再从 native surface 取错误码——TIMED_OUT 时 postFrameCallback(this) 重试并令 didDraw = false；其他错误或 !didSwap 则 setSurface(nullptr)。随后 mSwapHistory.next()：成功就把 windowDirty 记为 damage，失败则记一个 INT_MAX 的巨型脏区（826-831），保证下一帧必然全屏重绘。

06第 6 拍：Skia 回放与 GPU 提交

把 RenderNode 树回放成 Skia 绘制命令，画进 FBO 0，再 flushAndSubmit 与 swapBuffers 交出去

CanvasContext::draw 把脏区、windowDirty、mRenderNodes 与 LayerUpdateQueue 交给 mRenderPipeline->draw(...) 后，工作落到 Skia 侧。SkiaOpenGLPipeline::draw 先用 EglManager::damageFrame 经 eglSetDamageRegionKHR 把脏区告诉驱动，再按 SkColorType 选 GL 内部格式，用 GrBackendRenderTargets::MakeGL 把 FBO 0 包成后端渲染目标，WrapBackendRenderTarget 得到 SkSurface；随后 SkiaPipeline::renderFrame 先 renderLayersImpl 把更新的 layer 画到各自 surface，再 renderFrameImpl 设 device clip restriction、按需 clear、用 RenderNodeDrawable 递归回放 DisplayList（SkiaDisplayList::draw 只是 mDisplayList.draw(canvas)）；最后 FlushAndSubmit 提交命令，swapBuffers 走 eglSwapBuffersWithDamageKHR 交出 buffer。Vulkan 形状相同，但会返回真实 submissionTime 与 presentFence；此时像素仍在 GPU 的命令队列里：本阶段只负责把命令排进队列并交出 buffer，像素什么时候真的出现在屏幕上、release fence 什么时候回来，都要等 SurfaceFlinger 的合成与 HWC 上屏结束之后才知道；本阶段内除了 waitOnFences 与可选的 GPU 完成等待，没有别的同步点。

实现分三层：SkiaPipeline 实现公共的 renderFrame / renderFrameImpl / renderLayers / getFrameTimestamps 等（pipeline/skia/SkiaPipeline.h:39）；SkiaGpuPipeline 继承它并补上 mHardwareBuffer、createOrUpdateLayer、renderLayersImpl 的 GPU 版本（platform/android/pipeline/skia/SkiaGpuPipeline.h:25）；SkiaOpenGLPipeline 与 SkiaVulkanPipeline 再各自实现 draw / swapBuffers / getFrame / flush（platform/android/pipeline/skia/SkiaOpenGLPipeline.h:33、SkiaVulkanPipeline.h:33）。注意实现文件都在 base/libs/hwui/pipeline/skia/，头文件在 platform/android 与 platform/host 两份，读代码时容易只看到 host 版那个空实现。

FBO 0：把 EGL 默认 framebuffer 包成 SkSurface

入口先处理 damage：if (!isCapturingSkp() && !mHardwareBuffer) mEglManager.damageFrame(frame, dirty)（SkiaOpenGLPipeline.cpp:122-124）。damageFrame 只在 EglExtensions.setDamage 且 mSwapBehavior == SwapBehavior::BufferAge 时生效，用 frame.map() 把脏区映射成 4 个 EGLint 后调 eglSetDamageRegionKHR（EglManager.cpp:604-615）。

然后是格式选择：getSurfaceColorType()（即 SkiaPipeline::mSurfaceColorType）决定 GrGLFramebufferInfo::fFormat——F16 用 GL_RGBA16F，N32 用 GL_RGBA8，1010102 用 GL_RGB10_A2，Alpha_8 用 GL_R8，其他 LOG_ALWAYS_FATAL（126-142）。fFBOID = 0，因为 hwui 直接渲染到 EGL surface 的默认 framebuffer。

紧接着 GrBackendRenderTargets::MakeGL(frame.width(), frame.height(), 0, STENCIL_BUFFER_SIZE, fboInfo)（144-145，第三个参数是 sample count 0，第四个是模板缓冲大小），再 SkSurfaces::WrapBackendRenderTarget(...)，origin 由 getSurfaceOrigin() 给出——OpenGL 下是 kBottomLeft_GrSurfaceOrigin（SkiaOpenGLPipeline.h:52）。有 mHardwareBuffer 时改走 getBufferSkSurface(bufferParams) 并用 bufferParams.getTransform() 当 preTransform（153-161），这时根本不碰 EGL。

renderFrame：先画 layer，再回放主树

SkiaPipeline::renderFrame（SkiaPipeline.cpp:340-365）的顺序值得记牢：（1） 若开了 SKP 捕获则临时把 Properties::skpCaptureEnabled 置真；（2） tryCapture(surface, nodes[0], layers) 决定这一帧是画到 surface 还是录成 SkPicture；（3） renderLayersImpl(layers, opaque)——把所有有更新的 layer 先画完；（4） renderFrameImpl(...) 回放主树；（5） endCapture(surface)；（6） 调试开 debugOverdraw 时再叠加一层 overdraw。

为什么 layer 要先画：layer 的内容在自己的 SkSurface 上渲染，主树回放时只需要把 layer 的 snapshot 当图片贴上来（RenderNodeDrawable.cpp:343-345）。renderLayerImpl（SkiaPipeline.cpp:81-131）做的事很直白：拿 layer surface 的 canvas，设 device clip restriction 为 layerDamage，clear(SK_ColorTRANSPARENT)，然后构造 RenderNodeDrawable root(layerNode, layerCanvas, false) 并 forceDraw；trace 上表现为 “draw layers” 里嵌套若干 “drawLayer [name] W x H”。

renderFrameImpl：clip restriction、clear、单节点与多节点

renderFrameImpl（SkiaPipeline.cpp:374-479）先做三件全局设置：SkAutoCanvasRestore saver(canvas, true)；把 clip（就是 CanvasContext 传下来的 dirty，帧区域）经 preTransform.mapRect(clip).roundOut() 变成 clipRestriction，非 SKP 捕获时用 canvas->androidFramework_setDeviceClipRestriction 直接限制设备绘制区域（这是 HWUI 特有优化，避免为每一层 clip 建 saveLayer）；然后 canvas->concat(preTransform)。SKP 捕获时改为 drawAnnotation（380-387），因为捕获文件要包含全帧内容。

接着 if (!opaque) canvas->clear(SK_ColorTRANSPARENT)（390-392）：opaque 窗口不清屏，靠 buffer age 与 damage 保证正确性。节点数为 1 时（394-398）直接 RenderNodeDrawable root(nodes[0].get(), canvas); root.draw(canvas);，并且尊重 nodes[0]->nothingToDraw()。

多节点时（402-478）布局是 nodes[0]=backdrop、nodes[1]=content、2..=overlay：只有 content 没完全覆盖 backdrop 时，才在右/下补画 backdrop 的边；content 相对 backdrop 平移并被 contentDrawBounds 裁剪后绘制；剩下的 overlay 节点按顺序各自 forceDraw。这套逻辑服务的是窗口缩放/2-up 分屏场景。

UI 线程录制阶段（stage-05 之前）用 SkiaRecordingCanvas：initDisplayList 里优先 renderNode->detachAvailableList() 复用旧 DisplayList，否则 new SkiaDisplayList()，再 mDisplayList->attachRecorder(&mRecorder, SkIRect::MakeWH(width, height))，最终 SkiaCanvas::reset(&mRecorder)（SkiaRecordingCanvas.cpp:59-74）。收尾 finishRecording(destination) 里 destination->setStagingDisplayList(DisplayList(finishRecording()))（104-106）——注意是 staging DisplayList，要等 prepareTree 的 MODE_FULL 才 swap 成当前 DisplayList。

提交：flushAndSubmit 与 swapBuffers，OpenGL 与 Vulkan 的差别

回放结束后 OpenGL 侧在 ATRACE_NAME("flush commands") 保护下调用 skgpu::ganesh::FlushAndSubmit(surface)（SkiaOpenGLPipeline.cpp:180-183），然后 layerUpdateQueue->clear()（184），返回 {true, kUnknownTime, {}}（191）——OpenGL 报不出命令提交时间，presentFence 也是空 fd。

Vulkan 侧同样是 renderFrame，但结束调用 vulkanManager().finishFrame(backBuffer.get())，返回 VkDrawResult，再包成 {true, drawResult.submissionTime, std::move(drawResult.presentFence)}（SkiaVulkanPipeline.cpp:115-128）。所以 FrameInfoIndex::CommandSubmissionCompleted 只有在 Vulkan 下才有真实值（CanvasContext.cpp:790-791 取 max(commandSubmissionTime, SwapBuffers)，OpenGL 下就退化成 SwapBuffers）。

swap 的判定也不同：OpenGL 的 *requireSwap = drawResult.success || mEglManager.damageRequiresSwap()，然后 mEglManager.swapBuffers(frame, screenDirty) → eglSwapBuffersWithDamageKHR（SkiaOpenGLPipeline.cpp:207-213 → EglManager.cpp:621-646）；Vulkan 的 *requireSwap = drawResult.success，再 vulkanManager().swapBuffers(mVkSurface, screenDirty, std::move(drawResult.presentFence))（SkiaVulkanPipeline.cpp:141-147）。两边的第一句都是 currentFrameInfo->markSwapBuffers()——即使最终取消这一帧，从 jank 统计角度看它也算一次 swap（注释原文如此）。

这里就是 hwui 与 BufferQueue 的边界：eglSwapBuffers* 内部通过驱动把 buffer 交回 ANativeWindow 背后的 producer，而 hwui 在 ReliableSurface 构造时已经给这个 window 装了 interceptor（ANativeWindow_setQueueBufferInterceptor / setPerformInterceptor / setQueryInterceptor，ReliableSurface.cpp:61-71）。真正的 queueBuffer → BLASTBufferQueue → SurfaceFlinger 事务属于 stage-07。

CPU / GPU 分工与 fence 语义（哪一段是异步的）

本阶段全部在 RenderThread 的 CPU 上下文里执行：遍历 RenderNode 树、生成 Skia draw ops（mDisplayList.draw(canvas) 只是把已录制的命令流再喂给 SkCanvas，不是重新录制）、把命令组织成 GrOp 列表。FlushAndSubmit 把这些 op 提交给 Ganesh，驱动把 GL 命令批量下发——函数返回时 GPU 通常还没执行完。

fence 语义分三处：（1） DrawResult.presentFence：Vulkan 会带一个 fence fd，OpenGL 恒为空（SkiaOpenGLPipeline.cpp:191）；（2） flush()：OpenGL 用 EglManager::createReleaseFence(true, &sync, &fence)，若驱动不支持 native fence 则 eglClientWaitSyncKHR 自己等 1 秒再返回 -1（SkiaOpenGLPipeline.cpp:261-274），只有 HardwareBuffer 路径会用到它（DrawFrameTask.cpp:163-166）；（3） 隐式同步：eglSwapBuffersWithDamageKHR 时驱动会等待“这一 buffer 上次被消费”的 acquire fence。

源码里没有出现在 SkiaOpenGLPipeline::draw 返回前等待 GPU 的代码：显式 GPU 等待只有 Properties::waitForGpuCompletion 打开时 EglManager::swapBuffers 里的 fence()（EglManager.cpp:621-626）。Vulkan 侧多一个 presentFence 交给 swapchain，由 VulkanManager 内部处理。窗口何时真的上屏、retire fence 何时回来，见 stage-07/stage-08。

07swapBuffers：EGL 交换与 queueBuffer 入队

RenderThread 把画好的帧交给 EGL，驱动在 swap 内部 dequeue 一块 GraphicBuffer，再经 Surface 把 buffer 队列回 BufferQueue

本阶段是 RenderThread 把一帧真正送进 BufferQueue 的一拍：CanvasContext::draw() 在命令提交、waitOnFences() 之后调用 mRenderPipeline->swapBuffers()（CanvasContext.cpp:787），进入 SkiaOpenGLPipeline::swapBuffers()。它先 currentFrameInfo->markSwapBuffers() 钉住时间戳（SkiaOpenGLPipeline.cpp:201），再以 drawResult.success || mEglManager.damageRequiresSwap() 决定 requireSwap，然后交给 EglManager::swapBuffers() 调用 eglSwapBuffersWithDamageKHR()。AOSP 的 libEGL 在 eglSwapBuffersWithDamageKHRImpl() 里先用 native_window_set_surface_damage() 把脏区写到窗口，再转给 vendor 驱动的 eglSwapBuffersWithDamageKHR；真正的 dequeueBuffer/queueBuffer 发生在驱动内部，AOSP 里能验证的只有它对 ANativeWindow 钩子的调用。queueBuffer 经 Surface::hook_queueBuffer() 进入 BufferQueueProducer::queueBuffer()，写入 slot、frameNumber 与 acquire fence，并回调 consumer 的 onFrameAvailable，帧由此离开 RT、进入 BLAST 的地盘。swap 返回码只说明这一拍有没有换来一块新 buffer，真正上屏仍由 SurfaceFlinger 决定；无论成败，结果都会写进 FrameInfoIndex::CommandSubmissionCompleted 与 mSwapHistory，成为后续 jank 与 FrameTimeline 判定的输入。

CanvasContext::draw()→SkiaOpenGLPipeline::swapBuffers()→EglManager::swapBuffers()→eglSwapBuffersWithDamageKHR()→eglSwapBuffersWithDamageKHRImpl()→（vendor EGL 驱动内部）dequeueBuffer / queueBuffer→Surface::hook_queueBuffer()→Surface::queueBufferImpl()→BufferQueueProducer::queueBuffer()

一、谁发起、在哪个线程完成

发起者是 RenderThread：CanvasContext::draw() 在 issueDrawCommands 完成、waitOnFences() 之后执行 mRenderPipeline->swapBuffers(frame, drawResult, windowDirty, mCurrentFrameInfo, &requireSwap)（base/libs/hwui/renderthread/CanvasContext.cpp:787）。这条路径全部是 native C++，不涉及 Java 线程，也不涉及 binder；UI 线程此时早已被 DrawFrameTask::run() 的 unblockUiThread() 放走。

SkiaOpenGLPipeline::swapBuffers() 只有 20 行，但决定了三个结果：其一，进入函数立刻 currentFrameInfo->markSwapBuffers()（SkiaOpenGLPipeline.cpp:201），注释写明“即使取消这一帧，从 jank 指标看它也算已交换”；其二，*requireSwap = drawResult.success || mEglManager.damageRequiresSwap()；其三，真的交换失败（EGL_BAD_SURFACE / EGL_BAD_NATIVE_WINDOW）时只返回 false，由 CanvasContext::draw() 走 setSurface(nullptr) 的兜底。

交换返回后 CanvasContext::draw() 把 FrameInfoIndex::CommandSubmissionCompleted 写成 max(drawResult.commandSubmissionTime, SwapBuffers)，再进入 didSwap 分支：回调 mFrameCommitCallbacks（didProduceBuffer=true）、记录 mSwapHistory 的 damage 与 dequeue/queue 耗时。这些时间戳就是后面 FrameTimeline / gfxinfo 的数据源。

二、Frame：宽高、bufferAge 与 y 轴翻转

Frame 是 hwui 对 EGLSurface 的一层薄封装（base/libs/hwui/renderthread/Frame.h），只有 mWidth、mHeight、mBufferAge、mSurface 四个字段。EglManager::beginFrame() 先 makeCurrent(surface)，再用 eglQuerySurface(EGL_WIDTH/EGL_HEIGHT) 取尺寸、queryBufferAge() 取 buffer age，最后 eglBeginFrame() 通知 driver 新一帧开始。

queryBufferAge() 完全由 EglManager 私有的 SwapBehavior 枚举决定：Discard 返回 0（必然全量重绘）、Preserved 返回 1、BufferAge 才去 eglQuerySurface(EGL_BUFFER_AGE_EXT)。这个枚举在 EglManager::initialize() 里按 Properties::enablePartialUpdates 与 Properties::useBufferAge 选定（EglManager.cpp:126-136）。因此在默认配置下 partial update 很可能根本没开：damageRequiresSwap() 返回 false，swap 只在 drawResult.success 为真时发生。

坐标系是另一个容易踩的点。hwui 内部以左上角为 0,0，而 EGL/GRALLOC 的矩形以左下角为原点，Frame::map() 负责翻转：y = mHeight - (idirty.y() + idirty.height())，输出布局是 {x, y, width, height}（Frame.cpp:34-39）。同一份 map() 既用于 eglSetDamageRegionKHR，也用于 swap 的 damage rect，写错就会局部花屏。

脏区本身不是“上一帧之后所有改动”那么简单：CanvasContext::computeDirtyRect() 在 frame.bufferAge() > 1 时会把最近 bufferAge-1 帧的 mSwapHistory[i].damage 逐个 join() 回来（CanvasContext.cpp:1290-1304），否则环形缓冲里那块还没被覆盖的旧内容会残留。

三、EGL 交换如何变成 dequeue + queueBuffer

EglManager::swapBuffers() 只做两件事：frame.map(screenDirty, rects)、eglSwapBuffersWithDamageKHR(mEglDisplay, frame.mSurface, rects, screenDirty.isEmpty() ? 0 : 1)；Properties::waitForGpuCompletion 为真时先 fence() 等 GPU 完成（仅调试用途）。

往下是 native/opengl/libs/EGL/egl_platform_entries.cpp 的 eglSwapBuffersWithDamageKHRImpl()：n_rects == 0 直接退回 eglSwapBuffers；否则把 rect 转成 android_native_rect_t（注意它把 top 写成 y + height），调 native_window_set_surface_damage()，再调 vendor 的 eglSwapBuffersWithDamageKHR。驱动内部怎么 dequeue、怎么 queue，AOSP 树里没有任何实现——源码中未体现，可验证的只有它对 ANativeWindow 的调用。

这条边界在 Surface 构造函数里显式安装：ANativeWindow::dequeueBuffer = hook_dequeueBuffer、queueBuffer = hook_queueBuffer（native/libs/gui/Surface.cpp:144-149）。所以 hook_queueBuffer 就是“EGL 驱动把 buffer 交回 BufferQueue”的唯一入口，它先查 mQueueInterceptor，没有 interceptor 才走 Surface::queueBuffer()。

再往下 BufferQueueProducer::queueBuffer()（BufferQueueProducer.cpp:976）把 QueueBufferInput deflate 出 acquire fence、dataspace、crop、transform，校验 slot 属于 producer，然后 mSlots[slot].mFence = acquireFence、mBufferState.queue()、++mCore->mFrameCounter 并给定 frameNumber，把 BufferItem 压入 mCore->mQueue。若队尾恰好是可丢弃（droppable）的旧帧，则替换它并合并 mSurfaceDamage。回调在 mCallbackMutex + callbackTicket 的保护下严格按序调用 frameAvailableListener->onFrameAvailable(item)，这一回调正是 BLAST 的起点。

这里有两个容易忽略的顺序细节：其一，mSlots[slot].mFence 与 mSlots[slot].mBufferState.queue() 都在 mCore->mMutex 内完成，但 onFrameAvailable() 是在释放该锁之后、持有 mCallbackMutex 并按 callbackTicket 排队的情况下调用的，注释明确写着“回调不能持有 BufferQueue 主锁”，否则消费者回调里再 acquire/release 会直接死锁；其二，output->numPendingBuffers 与 nextFrameNumber 也在同一临界区写回，Surface 侧据此更新 mConsumerRunningBehind（Surface.cpp:1461 附近）。

四、dequeue 会不会阻塞：缓冲水位与 buffer stuffing

dequeue 的阻塞点在 BufferQueueProducer::waitForFreeSlotThenRelock()（BufferQueueProducer.cpp:347）：一旦 mBufferHasBeenQueued 为真且已出队数量达到 mCore->mMaxDequeuedBufferCount，直接返回 INVALID_OPERATION；队列里未消费的 buffer 超过 getMaxBufferCountLocked()，或找不到空闲 buffer，就进 waitForBufferRelease() 睡在 mCore->mDequeueCondition 上。异步模式（mAsyncMode）或 mDequeueBufferCannotBlock 时改为返回 WOULD_BLOCK。

hwui 两侧都有配置：CanvasContext::setSurface() 会 ANativeWindow_setDequeueTimeout(window, 4000_ms)（CanvasContext.cpp:239-241），让 dequeue 最多等 4 秒而不是无限等；setupPipelineSurface() 还会 native_window_set_producer_throttling_enabled(..., false) 并 setBufferCount()，后者取 NATIVE_WINDOW_MIN_UNDEQUEUED_BUFFERS 再 +2（CanvasContext.cpp:202-215）。这就是“三缓冲”的来源：最少未出队数加两块。

如果 dequeue 失败，prepareTree() 里 mNativeSurface->reserveNext() 返回非 OK 会把 skippedFrameReason 置成 SkippedFrameReason::NoBuffer（CanvasContext.cpp:606-608），这一帧直接跳过——这是“buffer 被 SF 占满”在 RT 侧最直接的可观测信号。

queueBuffer 收尾还有一道同步：connectedApi == NATIVE_WINDOW_API_EGL && enableEglCpuThrottling 时执行 lastQueuedFence->waitForever("Throttling EGL Production")（BufferQueueProducer.cpp:1280-1284），保证最多两块 buffer 在飞、第三块必须等。hwui 主动关掉了 producer throttling，所以这条路径通常不生效，别用它解释卡顿。

还有一个方向相反的限制来自 mMaxAcquiredBufferCount：如果消费者（BLAST）已经 acquire 了太多 buffer，即使 dequeueBuffer 不阻塞，acquireBuffer 也会返回 NO_BUFFER_AVAILABLE，此时 BLASTBufferQueue::acquireNextBufferLocked() 会一路返回，让这一帧停在 mNumFrameAvailable 里等下一次回调。dequeue 端与 acquire 端必须一起看，才能解释“明明有 buffer 却不出帧”。

五、fence 语义：acquire / release / present 不要混用

dequeue 返回的 fence 是 acquire fence，语义是“这块 buffer 何时可以被生产者写入”；BufferQueueProducer::queueBuffer() 把它同时写进 mSlots[slot].mFence 和 BufferItem::mFence，随 onFrameAvailable 交给消费者。消费者必须等它 signal 之后才能采样内容。

release fence 方向相反，是“生产者何时可以重新写这块 buffer”。hwui 在 SkiaOpenGLPipeline::flush() 里调用 mEglManager.createReleaseFence(true, &sync, &fence)（SkiaOpenGLPipeline.cpp:260-278）：优先用 EGL_SYNC_NATIVE_FENCE_ANDROID + glFlush() + eglDupNativeFenceFDANDROID() 导出一个 native fence fd；没有 native fence 扩展时退回 EGL fence，并且必须先 eglClientWaitSyncKHR 等掉同一 slot 的上一个 fence（1 秒超时），否则会破坏“同一 slot 的写-写顺序”（EglManager.cpp:732-784）。

present fence 不在本阶段产生：swap 成功只说明命令已提交，屏幕上何时点亮由 SurfaceFlinger/HWC 决定，present fence 要等 Transaction 完成回调（SurfaceControlStats::presentFence）才回到应用进程。本阶段能拿到的只有 EGL_SUCCESS 和（可选的）createReleaseFence 结果。

六、ReliableSurface：surface 失效时的静默兜底

CanvasContext::setSurface() 并不直接把 ANativeWindow* 交给 pipeline，而是包一层 ReliableSurface（CanvasContext.cpp:232-247）。它在 init() 里安装 cancel/dequeue/queue/perform/query 五个 interceptor，把 window 的每个关键入口都截住。

最值得注意的是失败路径：hook_dequeueBuffer() 一旦 dequeue 失败，就 acquireFallbackBuffer() 分配一块 1x1 的 AHardwareBuffer 当 scratch buffer 返回，并把结果改成 OK；随后 hook_queueBuffer() 认出这是 fallback buffer，close(fenceFd) 后直接返回 OK（ReliableSurface.cpp:175-229）。换句话说，surface 死掉时上层看不到错误，只是屏幕上不再出现新帧。

另外文件开头 constexpr bool DISABLE_BUFFER_PREFETCH = true（ReliableSurface.cpp:31）让 reserveNext() 直接返回 OK，预取路径在此版本是关闭的；hook_perform() 对任何 perform 都 clearReservedBuffer()，hook_query() 则在 ANATIVEWINDOW_QUERY_MIN_UNDEQUEUED_BUFFERS 时把 mExpectedBufferCount 记成 *value + 2，用于校验上层是否设置了足够的 buffer 数。

08BLAST：把 buffer 当作 Transaction 提交

queueBuffer 之后 buffer 不再躺在 BufferQueue 里等 SF latch，而是被 BLAST 装进 Transaction，用 apply token 单向提交给 SurfaceFlinger

BLAST 把 BufferQueue 搬进了应用进程：BufferQueueProducer::queueBuffer() 末尾的 onFrameAvailable() 是一次同进程同步调用，直接进入 BLASTBufferQueue::onFrameAvailable()（BLASTBufferQueue.cpp:779）。它维护一个影子队列 mNumFrameAvailable，然后调用 acquireNextBufferLocked()：从 BufferQueueConsumer 取走 BufferItem，把 buffer / acquire fence / frameNumber / dataspace / damage / destination frame 等全部翻译成 SurfaceComposerClient::Transaction 的 layer_state_t 更新。若此前有 settle 到这一帧的 pending 事务则先 merge，随后 t->setApplyToken(mApplyToken).apply(false /*sync*/, true /*oneWay*/) 通过 binder 调 ISurfaceComposer::setTransactionState() 发给 SF。于是“显示一帧”的语义从 BufferQueue 的 available/latch 变成了 Transaction 的 applied/presented，acquire fence 也由 SF 在 latch 时消费。这一步之所以要单独讲，是因为它把“帧的可见性”从 BufferQueue 的队列语义换成了 Transaction 的提交语义：SF 的 latch 时机被推到 apply 之后，后续 jank 归因（是 applied 慢还是 present 慢）完全取决于这一层维护的两笔账。

一、为什么 buffer 不再“留在 BufferQueue 等 SF”

传统模型里 BufferQueue 的消费者在 SurfaceFlinger 进程内，queueBuffer 之后 buffer 停在队列里，等 SF 在下一拍 acquireBuffer() / latch。BLAST 换掉了这个拓扑：BLASTBufferQueue::createBufferQueue()（BLASTBufferQueue.cpp:1352-1376）用 BufferQueue::createBufferQueue 的变体在本进程内建了一对 producer/consumer，consumer 是本进程的 BLASTBufferItemConsumer，SF 那边只看到 layer_state_t::eBufferChanged。

这带来一个直接后果：BufferQueueProducer::queueBuffer() 调 frameAvailableListener->onFrameAvailable(item) 时并不经过 binder，而是同步函数调用，且就发生在调用 queueBuffer 的那个线程——对 hwui 来说就是 RenderThread。换句话说，本阶段的 Transaction 构建与 apply 的 binder 往返时间，全都记在 RenderThread 的 queueBuffer 上。

另一条注释值得记住：BLAST 的 BufferQueue 在应用进程内，“so it is guaranteed that the BufferQueue is inside SurfaceFlinger's process and there will be no Binder call”（BufferQueueProducer.cpp:1242-1246 附近的 mConsumerIsSurfaceFlinger 分支）。所以 item.mGraphicBuffer.clear() 这个省掉 GraphicBuffer 引用的优化在 BLAST 下不生效，buffer 句柄依旧要留在本地供 Transaction 使用。

顺带解释一个常被问到的现象：BLAST 下 dumpsys SurfaceFlinger 里该 layer 的 buffer 状态更新频率与应用的 queueBuffer 并不一一对应，因为中间还隔着 mNumFrameAvailable 的影子队列和 mPendingTransactions；trace 上要同时看 onFrameAvailable 的 f/a 计数与 SF 侧的 TransactionCallbackInvoker::sendCallbacks。

二、acquireNextBufferLocked：BufferItem 到 Transaction 的翻译

函数开头有两道水位闸门：mNumFrameAvailable == 0 直接 NO_BUFFER_AVAILABLE；mNumAcquired >= (mMaxAcquiredBuffers + 2) 也返回 NO_BUFFER_AVAILABLE（注释说明即使做了检查，消费者仍可能因为已 acquire 满而失败）。mMaxAcquiredBuffers 默认 1，且 BufferQueue 内部允许比 max 多 1（BLASTBufferQueue.h:205-207），所以实际可能挂着 3 块。

随后 mBufferItemConsumer->acquireBuffer(&bufferItem, 0, false) 取帧，rejectBuffer() 在 SCALING_MODE_FREEZE 且尺寸不匹配时拒收并递归重试；接受后 mNumAcquired++、mLastAcquiredFrameNumber 更新，ReleaseCallbackId(buffer->getId(), frameNumber) 对应的 BufferItem 存进 mSubmitted，等 release 回调来认领。

翻译动作全部落在 Transaction 上：t->setBuffer() 带 buffer、dup 过的 acquire fence、frameNumber、producerId、release 回调与 dequeueTime；接着 dataspace、HdrMetadata、setSurfaceDamageRegion、addTransactionCompletedCallback、destination frame（或 eIgnoreDestinationFrame）、buffer crop、transform、setAutoRefresh、setDesiredPresentTime。这是一次“把 BufferItem 的全部语义搬进 layer_state_t”的过程。

FrameTimeline 也在这里对齐：mPendingFrameTimelines 是一个按 frameNumber 排序的队列，先丢弃 < bufferItem.mFrameNumber 的陈旧项，只有队首 frameNumber 完全相等时才 t->setFrameTimelineInfo() 并 pop。对不上就整条 timeline 信息丢失——这是“有帧但没有 FrameTimeline 记录”的常见原因。

三、apply token、事务合并与 buffer barrier

mApplyToken 默认是 sp<BBinder>::make()（BLASTBufferQueue.h:305-306），注释写得很直白：用这个 token 排队的事务不会被同一客户端其它部分的事务堵住。SurfaceComposerClient::Transaction::apply() 里 applyToken 随 setTransactionState() 一起送到 SF，SF 依据 token 对事务做串行化，所以 BLAST 的事务与 ViewRootImpl 的 applyAsync 事务互不阻塞。

合并有两条路径：mergePendingTransactions() 在 acquire 时把 mPendingTransactions 里 targetFrameNumber <= currentFrameNumber 的事务 merge() 进来；mergeWithNextTransaction(t, frameNumber)（BLASTBufferQueue.cpp:1100-1112）则相反——如果 mLastAcquiredFrameNumber >= frameNumber 就立刻 t->setApplyToken(mApplyToken).apply()，否则把事务压进 mPendingTransactions 并 t->clear() 以免被别处重复提交。

同步事务是另一套机制：syncNextTransaction() 建立 mSyncTransaction 与 mTransactionReadyCallback，onFrameAvailable() 在 mTransactionReadyCallback != nullptr 时把 buffer 装进 mSyncTransaction、登记 mSyncedFrameNumbers、加 addTransactionCommittedCallback，并在 mAcquireSingleBuffer 为真时把 callback 交还给调用者。

mSetBufferBarrier / setBufferHasBarrier() 解决的是顺序问题：若上一笔 buffer 事务已经单向发出但状态未知，后续事务会带上 barrier，SF 必须等那笔 buffer 事务先落定才能应用，避免“属性更新跑到了 buffer 前面”导致画面错位。

四、apply 之后：binder 边界与 SF 的消费

Transaction::apply(bool synchronous, bool oneWay)（SurfaceComposerClient.cpp:1146）做四件事：把各 listener 的回调 id 折进 layer_state_t.listeners、cacheBuffers()、按参数置 ISurfaceComposer::eOneWay、取 mApplyToken 后 sf->setTransactionState(std::move(state), applyToken)。之后 clear() 清状态；只有 synchronous 为真才会 syncCallback->wait()。

BLAST 走的是 apply(false, true)（BLASTBufferQueue.cpp:726-727）——既不同步又 one-way，返回时 SF 还没 latch，更不能假设已经 present。任何“apply 之后立刻读屏幕内容/读 presentFence”的假设都是错的。

SF 侧接收后进入 SurfaceFlinger::setTransactionState()（native/services/surfaceflinger/SurfaceFlinger.cpp:5579），在下一拍由 commitTransactions() → commitTransactionsLocked() → Layer::latchBufferImpl() 消费 buffer 与 acquire fence；合成完成后 mTransactionCallbackInvoker.sendCallbacks()（SurfaceFlinger.cpp:3985）把 latchTime、presentFence、SurfaceControlStats 回给客户端的 TransactionCompletedListener。

也就是说：这一阶段结束时 buffer 只是“提交了”，真正的 latch、合成、present 都在 SF 的下一拍。与 GPU 的边界同样在这里断开——应用侧 swap 只提交命令，GPU 完成由 release/present fence 反映，而不是 eglSwapBuffers 的返回值。

五、BufferReleaseChannel：release 回调不再挤占 binder

BLAST 的 buffer 什么时候能还给 BufferQueue，取决于 SF 何时丢弃旧 buffer 或何时完成 present。这条信息走的是独立通道：updateBufferReleaseProducer()（BLASTBufferQueue.cpp:1453-1461）单独发一笔 setBufferReleaseChannel() 事务，注释说明这是为了避免 SELinux 拒发 fd 时把整笔事务一起丢掉。

应用侧 BufferReleaseReader 用 epoll 监听 channel fd，BBQBufferQueueProducer::waitForBufferRelease() 在 BufferQueue 锁外阻塞读，读到后调 releaseBufferCallback()。releaseBufferCallbackLocked() 并不立刻把 buffer 还回去：它先压进 mPendingRelease，再按 isEGL ? max(0, mMaxAcquiredBuffers - mCurrentMaxAcquiredBufferCount) : 0 计算要“扣住”几块（BLASTBufferQueue.cpp:490-538），只有超出的部分才 releaseBuffer() 真正归还，并在 mSyncedFrameNumbers 为空时顺手 acquireNextBufferLocked() 拉下一帧。

这个“扣住”的设计是为了低刷新率下不增加延迟，代价是 buffer 归还变慢；如果 SF 一直不回 release，应用侧最终会在 dequeue 上阻塞，表现就是上一阶段的 SkippedFrameReason::NoBuffer。

六、排障：这一层最容易出现的三类现象

第一类是“apply 成功但画面不动”：check mNumFrameAvailable、mNumAcquired、mPendingRelease.size() 三者的差值（BLASTBufferQueue.h:192-196 的注释给出这个等式，mQueuedBufferTrace 就是它），三者相等且不为 0 说明 buffer 全被扣住。

第二类是“属性更新丢帧”：mergeWithNextTransaction() 把事务藏进 mPendingTransactions 后，只由后续 acquire 的 mergePendingTransactions() 或显式 applyPendingTransactions(frameNumber)（BLASTBufferQueue.cpp:1113-1119）取回；如果目标帧号一直不被 acquire，事务就一直不发出，源码中没有为这个队列设置超时。

第三类是“trace 里 quantum 对不上”：BBQ_TRACE 展开为 ATRACE_FORMAT("%s - %s(f:%u,a:%u)")（BLASTBufferQueue.cpp:92-94），slice 名里带 f:（mNumFrameAvailable）与 a:（mNumAcquired），可直接对照 Transaction::setFrameTimelineInfo 的 instant 事件确认哪一帧丢了 timeline。

onFrameAvailable 是同步调用而不是 binder 回调：BLAST 的 Transaction 构建、merge 与 apply 全部发生在 RenderThread 调用 queueBuffer 的栈里，queueBuffer 的耗时天然包含这一段，不能把它当成“纯入队”。

mergeWithNextTransaction 在目标帧号尚未 acquire 时把事务塞进 mPendingTransactions 并 clear() 掉原事务；源码里没有给这个队列任何超时，如果那一帧永远不来，这笔属性更新就永远不生效。

不要把 BufferQueue 的 “available” 与 SF 的 “applied/presented” 混为一谈：本阶段结束时状态是“事务已提交”，latchTime/presentFence 要等 TransactionCompletedListener 回调才存在。

09回调、帧时间线与 jank 判定

didProduceBuffer、applied、present 三条回调把 RenderThread 的一帧接上 FrameTimeline，并最终交给 JankTracker 定性

本阶段回答“这一帧最后怎么了”。第一段回调在 RenderThread 本地：CanvasContext::draw() 在 didSwap 后把 mFrameCommitCallbacks 逐个以 true /*didProduceBuffer*/ 调用，跳过帧则调用 false；这些回调由 JNI 的 FrameCommitWrapper 转发给 HardwareRenderer$FrameCommitCallback。第二段跨进程：BLAST 提交的 Transaction 完成后，SurfaceFlinger 的 TransactionCallbackInvoker::sendCallbacks() 通过 ITransactionCompletedListener 把 latchTime、presentFence、SurfaceControlStats 回给客户端，在 TransactionCompletedListener::onTransactionCompleted() 里分发 ON_COMMIT / ON_COMPLETE 回调。第三段是时间线归位：SkiaPipeline::getFrameTimestamps() 用 native_window_get_frame_timestamps 取回 acquire/latch/present 等时间戳，写进 FrameInfoIndex::DisplayPresentTime；CanvasContext::onSurfaceStatsAvailable() 再用 SF 的 acquire 统计覆盖 FrameCompleted / GpuCompleted，JankTracker::finishFrame() 据此判定 kMissedDeadline / kSlowRT 等 jank 类型。把这三段串起来，才能回答“这一帧为什么 jank”：是 RT 没产出 buffer、是事务没被应用、还是应用了但没赶上本拍 present——三种情况分别对应 didProduceBuffer、latchTime 与 presentFence，观测入口完全不同。

一、三条回调，对应一段时间线

把“一帧的结果”拆成三段之后，所有观测手段都能对上号：didProduceBuffer 是 RenderThread 本地事实，表示这一拍是否真的产生了一块新 buffer；applied / committed 是 SurfaceFlinger 的 binder 事实，表示事务已被应用（latchTime）；present 是显示事实，表示这一帧何时被刷新到屏幕（presentFence 与 DisplayPresentTime）。三者之间有严格的先后，但彼此可能差好几拍。

第一段在 CanvasContext::draw() 里收尾：if (didSwap) 分支以 true /*didProduceBuffer*/ 调用 mFrameCommitCallbacks 并清空（CanvasContext.cpp:878-883）；而帧被跳过时走的是另一条路径——skippedFrameReason 命中后 waitOnFences()，同样把回调以 false /*didProduceBuffer*/ 调用后清空（CanvasContext.cpp:717-722）。所以回调一定会来，只是参数不同。

第二段在 TransactionCompletedListener：CallbackId::Type::ON_COMMIT 只带 latch 信息，ON_COMPLETE 还会带 presentFence 与每块 Surface 的统计。第三段是 getFrameTimestamps()：它按 frameNumber 向 BufferQueue 的 ProducerFrameEventHistory 查询，因此帧号必须对得上，否则查不到。

二、RenderThread 内部：DrawFrameTask 的三种回调

DrawFrameTask 持有三个 std::function（DrawFrameTask.h:130-132）：mFrameCallback 对应 Java 的 FrameDrawingCallback，签名是 std::function<std::function<void(bool)>(int32_t, int64_t)>；mFrameCommitCallback 对应 FrameCommitCallback，签名 void(bool)；mFrameCompleteCallback 更轻量，只表示“RT 做完了这次尝试”。

run() 的顺序值得背下来：先 syncFrameState()（此时 UI 线程可能仍被阻塞），把 mFrameCommitCallback 直接 addFrameCommitListener()；再把三个回调搬进局部变量并清空成员，注释写着“From this point on anything in "this" is *UNSAFE TO ACCESS*”；然后 unblockUiThread() 放走 UI 线程；最后才 mFrameCallback 通过 enqueueFrameWork() 丢到 CommonPool 上异步执行，它返回的 FrameCommitCallback 再被 addFrameCommitListener()。

这个设计解释了为什么 FrameDrawingCallback.onFrameDraw() 必须返回一个 FrameCommitCallback（base/graphics/java/android/graphics/HardwareRenderer.java:1114-1118）：drawing 回调是异步的，唯一可靠的“这一帧到底有没有产生 buffer”的答案在稍后 didProduceBuffer 里。JNI 侧 FrameCommitWrapper::onFrameCommit() 转调 Java 后立刻 releaseObject()，即 global ref 只活到一次回调（android_graphics_HardwareRenderer.cpp:146-152）。

三、跨进程：applied 与 present 数据从哪来

客户端侧的实现就在 SurfaceComposerClient.cpp 里：TransactionCompletedListener::onTransactionCompleted(ListenerStats)（SurfaceComposerClient.cpp:481）先按 callbackId 把 mCallbacks extract 出来，再分两轮分发——先 ON_COMMIT，再 ON_COMPLETE。ON_COMPLETE 里会用 latchTime、acquireTimeOrFence、presentFence、previousReleaseFence、transformHint、eventStats 组装 SurfaceControlStats，并顺手把 previousReleaseCallbackId 对应的 release 回调在同一轮里执行掉——注释说明这是为了省一次 IPC。

ON_COMMIT 与 ON_COMPLETE 的区别是理解“applied 与 present 不同”的关键：前者在事务被应用后就能发，后者要等真正的 present fence 有值；同一个 CallbackId 可能出现在多笔合并的事务里，代码用一个 callbacksMap 并在调用后 erase 保证只回调一次。

线程上，startListeningLocked() 会 ProcessState::self()->startThreadPool()（SurfaceComposerClient.cpp:414-420），所以这些回调跑在客户端进程的 Binder 线程池线程上，不是 RenderThread、也不是 UI 线程。任何回调里做的操作都必须考虑与 RT 的并发：SurfaceComposerClient::Transaction::apply() 内部会 mState move 走，但 SurfaceControl 的 transformHint 更新是直接写在回调里的。

SF 侧发送点有两处包装：TransactionCallbackInvoker::sendCallbacks(bool onCommitOnly)（native/services/surfaceflinger/TransactionCallbackInvoker.cpp:158）在合成后由 SurfaceFlinger.cpp:3985 调用，先 writeReleaseFence() 把 release fence 写进 BufferReleaseChannel，再对每个 listener 调 onTransactionCompleted(stats)；如果走了 BackgroundExecutor，trace 上会多一个 TransactionCallbackInvoker::sendCallbacks 切片。

四、jank 判定：FrameInfoIndex 与 JankTracker

JankTracker 的静态比较表定义在 base/libs/hwui/JankTracker.cpp:46-61：kMissedVsync 看 IntendedVsync→Vsync 是否 ≥1 个 interval；kSlowUI 看 Vsync→SyncStart 是否超过 0.5 个 interval；kSlowSync 看 SyncStart→IssueDrawCommandsStart 是否超过 0.2；kSlowRT 看 IssueDrawCommandsStart→FrameCompleted 是否超过 0.75。四者是“谁慢”的第一层归因。

第二层是 deadline：finishFrame() 里若 GpuCompleted >= FrameDeadline 就记 kMissedDeadline 并 reportJank()，同时用 jitterNanos % frameInterval 反推下一帧的“未 stuffing 起点” mNextFrameStartUnstuffed（JankTracker.cpp:209-220）。如果某帧提前于 intended vsync 开始（mNextFrameStartUnstuffed - IntendedVsync > 0.1 * interval），说明处于三缓冲状态，此时 deadline 会被重算成 mNextFrameStartUnstuffed + WorkloadTarget，按时完成反而记 kHighInputLatency（JankTracker.cpp:196-216）。

关键输入 FrameCompleted / GpuCompleted 的来源分两种：mExpectSurfaceStats 为真（即设过 SurfaceControl）时，它们由 onSurfaceStatsAvailable() 用 SF 回传的 acquireTimeOrFence 覆盖，FrameCompleted = max(gpuCompleteTime, SwapBuffersCompleted)、GpuCompleted = max(gpuCompleteTime, CommandSubmissionCompleted)（CanvasContext.cpp:1058-1061）；没有 SurfaceControl 时退回 markFrameCompleted() 并把 GpuCompleted 直接等于 FrameCompleted（CanvasContext.cpp:896-898）。这也是为什么同机对比时，有/无 SurfaceControl 的 jank 数据不能直接比。

阈值之外还有两条过滤：总时长超过 10 秒的帧直接丢弃（IGNORE_EXCEEDING，JankTracker.cpp:65），带 FrameInfoFlags::SurfaceCanvas 的直接绘制帧被豁免（EXEMPT_FRAMES_FLAGS，JankTracker.cpp:74）。

五、FrameTimeline 与 getFrameTimestamps

FrameTimeline 的前提是 frameNumber 与 vsyncId 严格配对：CanvasContext::draw() 里构造 ANativeWindowFrameTimelineInfo（frameNumber、frameTimelineVsyncId、inputEventId、startTimeNanos、skippedFrameVsyncId、dequeueBufferDurationNanos…，CanvasContext.cpp:757-781），再 mRenderPipeline->setFrameTimelineInfo(ftl)；BLAST 在 acquire 时按 frameNumber 精确匹配并 t->setFrameTimelineInfo()。

SkiaPipeline::getFrameTimestamps()（SkiaPipeline.cpp:590）是读取侧：它调 native_window_get_frame_timestamps()，一次性取 requestedPresent / acquire / latch / firstRefreshStart / lastRefreshStart / gpuCompositionDone / displayPresent / dequeueReady / release 九个时间戳，其中 desiredPresentTime 之外的大部分数据来自 SF 回填的 FrameEventHistory。

hwui 自己只在 reportMetricsWithPresentTime() 里用它取 outDisplayPresentTime（CanvasContext.cpp:963-969），并且要求 mLastFrameMetricsInfos 环已满才处理队首那一帧——也就是延迟若干帧才上报 present 时间。这解释了为什么应用刚启动的头几帧在 framestats 里缺 present 列。

时间源本身也被过滤过：TimeLord::vsyncReceived() 只在 intendedVsync 前进时更新 vsyncId 与 deadline，computeFrameTimeNanos() 用与 Choreographer 相同的逻辑把落后多个 interval 的 vsync 重新对齐到最近的 interval（TimeLord.cpp:31-64）。所以 FrameInfoIndex::Vsync 不一定等于 Choreographer 那一拍的原始值。

UI 线程只在 postAndWait 期间被阻塞；解阻后可以开始下一帧。RT 的 draw 与 GPU 执行是异步的：flushAndSubmit 只负责提交命令，GPU 完成由 fence 回传。

A为什么 UI 不能等 GPU？

如果 UI 等 GPU 完成，下一帧的输入、动画和 measure/layout 都会被 GPU 延迟串行化。hwui 把 CanvasContext::draw 留在 RT，UI 只等“树同步”这个较短的阶段。

B为什么 RT 不能等 SF？

RT 的职责是把 buffer 与 Transaction 交给系统。上屏时刻由 SurfaceFlinger / HWC 的 VSYNC 与 fence 决定；如果 RT 同步等待上屏，就会阻塞下一帧的 GPU 提交。

C哪些操作会反过来阻塞 RT？

dequeueBuffer 等不到 free slot、prepareTextures 纹理缓存耗尽、GPU 上下文丢失/重建、waitOnFences 等 acquire fence，都会让 RT 的“异步”变成实际阻塞。

RT 内部：同步/准备变慢

  • RenderNode 树大、属性更新多：prepareTree 遍历成本上升。
  • 纹理上传/图片解码：prepareTextures、uploadIfNeeded 占用 RT。
  • 动画回调/属性动画在 RT 上执行，AnimationContext 超出预算。

GPU / EGL：提交或换缓冲变慢

  • 过度绘制、复杂 Shader、大图层：SkiaOpenGLPipeline::draw 变长。
  • dequeueBuffer 等不到 free slot：BufferQueue 被填满。
  • eglSwapBuffers 被 GPU/驱动阻塞，RT 無法继续下一帧。

BLAST / SF：交接延迟

  • Transaction 错过 SF 的取帧相位：本帧只能下一拍上屏。
  • acquire fence 未 signal：latch 不成立，SF 请求重合成。
  • RT 侧只登记 callback；上屏延迟不直接阻塞 RT。

观测要点

  • DrawFrames <vsyncId> 总括 RT 一帧。
  • flush commands / queueBuffer / Transaction apply 定位交接点。
  • FrameTimeline 对齐 GPU completion、present、release。
