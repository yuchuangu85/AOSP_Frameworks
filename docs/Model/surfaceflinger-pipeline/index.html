00 / OVERVIEW

App 只“交帧”，
SurfaceFlinger 决定它怎么上屏

SurfaceFlinger 不是简单的“把 buffer 贴到屏幕”：它要在一个 VSYNC 周期内完成事务应用、快照、 buffer latch、合成策略选择、HWC/GPU 合成、present。每一步错过截止线，都会让这一帧顺延或让合成走更慢的路径。

BLAST → SCHEDULER → COMPOSITION
ONE VSYNC · NINE STAGES

一句话版本：APP 的 BLAST Transaction 把 buffer 连同 acquire fence、release listener、FrameTimeline info 一起提交给 SF。SF 的 Scheduler 在自己的 VSYNC 相位调用 onFrameSignal，先 commit （应用事务、生成只读 LayerSnapshot、latch buffer），再 composite（CompositionEngine 让 HWC 选择 overlay 或 client composition，必要时 RenderEngine 做 GPU 合成），最后 presentDisplay 把图层交给 HWC；HWC/DRM 在随后的扫描输出中把像素打到面板，retire fence 与 buffer release 再异步回传。

01buffer 不“躺在”BufferQueue 等 SF

BLAST 下 buffer 作为 Transaction 的 BufferData 跨进程提交；SF 侧不持有旧式 BufferQueueConsumer，latch 与 release 都围绕 Transaction 和 fence。

02commit 与 composite 是两段

commit 把当前事务应用到 mDrawingState 并生成只读 LayerSnapshot；composite 才让 CompositionEngine/HWC 决定怎么画。commit 没活时 SF 可以空转。

03合成路径决定耗时

HWC 能直接 overlay 时，SF 只做 validate/present；如果 HWC 要求 client composition，RenderEngine 必须先画到 client target，这一段最容易把 present 推过 VSYNC。

01输入：BLAST 事务把 buffer 送进 SF

buffer 不留在 BufferQueue：它在 app 进程的 BBQ 里被取走，随 Transaction 跨进程进 SF

App 的 RenderThread 画完一帧后调用 Surface::queueBuffer，进入本进程内的 BLASTBufferQueue（BBQ）：BufferQueueProducer::queueBuffer 把 buffer 放进队列后立刻同步回调 BLASTBufferQueue::onFrameAvailable，后者用 acquireNextBufferLocked 把 buffer 从 BufferQueue 里取出来，塞进一个 SurfaceComposerClient::Transaction（setBuffer + setFrameTimelineInfo + mergePendingTransactions），再用 setApplyToken(...).apply(oneway) 送到 SurfaceFlinger。SF 侧在 binder 线程执行 SurfaceFlinger::setTransactionState：把客户端状态解析成 ResolvedComposerState、构造 QueuedTransactionState、push 进 TransactionHandler 的 lockless 队列，然后 setTransactionFlags(eTransactionFlushNeeded) 唤醒主线程。主线程在下一个 vsync 的 commit 阶段才 collectTransactions/flushTransactions 按 apply token 分队列取出并应用。所以本阶段的本质是：buffer 的生命周期从 BufferQueue 移交给 Transaction，唯一的跨进程动作是一次带 GraphicBuffer 与 acquire fence 的 oneway 事务。注意 apply 是 one-way：RT 发完事务就继续画下一帧，SF 侧的延迟只能通过 buffer 积压或 BLAST sync 事务反向影响 client；acquire fence 只被记录成 FenceTime，不在提交路径上等待。

Surface::queueBuffer()→BufferQueueProducer::queueBuffer()→BLASTBufferQueue::onFrameAvailable()→BLASTBufferQueue::acquireNextBufferLocked()→SurfaceComposerClient::Transaction::setBuffer()→SurfaceComposerClient::Transaction::apply()→SurfaceFlinger::setTransactionState()→TransactionHandler::queueTransaction()→SurfaceFlinger::setTransactionFlags()→Scheduler::scheduleFrame()

触发者与线程：queueBuffer → onFrameAvailable 全在 app 的 RenderThread 上

一帧画完后，硬件渲染器的 RenderThread 在 eglSwapBuffersWithDamage 路径里调用 Surface::queueBuffer，最终进入 BufferQueueProducer::queueBuffer。关键前提是BLASTBufferQueue 位于 client 进程：SurfaceControl::generateSurfaceLocked() 里就地 sp<BLASTBufferQueue>::make(...) 建出一个 BBQ 和一个 [BBQ] 子 SurfaceControl（native/libs/gui/SurfaceControl.cpp:142-149）；BLASTBufferQueue::initialize() 的注释也直说 "since the adapter is in the client process, set dequeue timeout explicitly so that dequeueBuffer will block"（BLASTBufferQueue.cpp:198-200）。

因此 queueBuffer 不是 binder 调用，而是对本地 BBQBufferQueueProducer（BufferQueueProducer 子类，BLASTBufferQueue.cpp:1251-1257）的虚函数调用；队列尾部在 mCallbackMutex 下同步回调 listener->onFrameAvailable(item)（BufferQueueProducer.cpp:1263-1277）。所以 BLASTBufferQueue::onFrameAvailable 就跑在RenderThread 上——这一点是理解 BLAST 输入路径的起点。

一个容易忽略的细节：BBQBufferQueueProducer 构造时传 false /* consumerIsSurfaceFlinger*/（BLASTBufferQueue.cpp:1255），所以 queueBuffer 在回调前会执行 item.mGraphicBuffer.clear()（BufferQueueProducer.cpp:1245-1247）。注释解释了 SF 作为 consumer 时可以不清空——因为 BufferQueue 在 SF 进程内、不会有 binder 调用；BLAST 走 else 分支清空，而 BBQ 的回调也确实只用 item.mFrameNumber，buffer 要靠后续 acquireBuffer 重新取。

BLAST 的核心：buffer 不留在 BufferQueue，而是成为 Transaction 的字段

onFrameAvailable 先做 shadow queue 记账（mNumFrameAvailable++，BLASTBufferQueue.cpp:829），再在非同步事务路径上调用 acquireNextBufferLocked(std::nullopt)（864）。这个函数是整个 BLAST 模型的枢纽：

  • 先从 BufferItemConsumer 真正 acquireBuffer（600 行），成功后 mNumFrameAvailable--（610）——buffer 从 BufferQueue 里被拿走了，BQ 队列不再持有它；
  • 把 (GraphicBuffer, acquireFence, frameNumber, producerId, releaseBufferCallback, dequeueTime) 一次性塞进 Transaction：t->setBuffer(...)（667-668）；
  • 紧接着 dataspace / HDR metadata / surface damage / crop / transform / transformToDisplayInverse / autoRefresh / desiredPresentTime 全部进同一个 Transaction（669-691）；
  • 用 mPendingFrameTimelines 把 Choreographer 传下来的 FrameTimelineInfo（vsyncId 等）按 frameNumber 对齐后 setFrameTimelineInfo（704-721）；
  • 把攒下的旧事务按 frameNumber 顺序 merge 进来（mergePendingTransactions，723），最后 t->setApplyToken(mApplyToken).apply(false, true)（726）。

这段顺序解释了 BLAST 与旧模型的本质差别：缓冲区不再「留在 BufferQueue 等 SF 来 dequeue」，而是被 client 侧立即取出、作为 Transaction 的一个字段（layer_state_t::BufferData）送过进程边界。BufferQueue 退化成 client 进程内的一个过渡队列，buffer 何时可被复用由 Transaction 的 release 回调决定，而不是由 BQ 的 free slot 决定。

apply token：SF 侧按 token 分队列，保证同一 client 内有序

Transaction 不是立刻生效的，它先进 SF 的队列。SurfaceComposerClient::Transaction::apply()（native/libs/gui/SurfaceComposerClient.cpp:1146-1225）做三件事：cacheBuffers()、把 eOneWay 之类的 flags 合入 mState.mFlags（1190-1197）、然后 sf->setTransactionState(std::move(state), applyToken)（1207-1209）。apply token 优先取 Transaction 自己设的（BBQ 在 setApplyToken 里存下来的那个），否则用进程内默认 token sApplyToken（1205、1227-1234）。

SF 侧 SurfaceFlinger::setTransactionState 跑在binder 线程（函数开头就 IPCThreadState::self()->getCallingPid() 取调用者身份，5583-5586）。它先 sanitize、解析 externalTexture（5645-5682），把客户端状态搬进 QueuedTransactionState（5684-5701，其中 applyToken 是显式字段），然后按注释所说 "Transactions are added via a lockless queue and does not need to be added from the main thread"，直接把事务 push 进 lockless 队列（5716-5721），最后 setTransactionFlags(eTransactionFlushNeeded, ...)（5729）把主线程叫醒。注意这里不做任何 buffer 处理：事务只是入队。

队列的按 token 划分发生在主线程：TransactionHandler::collectTransactions() 把 mLocklessTransactionQueue 里的元素搬进 mPendingTransactionQueues[token]（TransactionHandler.cpp:39-48），每个 apply token 一条 std::queue（TransactionHandler.h:95-96）。这保证了同一 token（通常同一个 SurfaceControl 的 client）内事务严格 FIFO，而不同 token 之间没有全局顺序——这正是「apply token 是 client 提交顺序的锚点」的源码依据。

BLAST 的回调边界：commit / present / release 三条独立通道

BBQ 在每个 setBuffer 的 Transaction 上都挂了回调：t->addTransactionCompletedCallback(makeTransactionCallbackThunk(), nullptr)（672），并用 mSurfaceControlsWithPendingCallback 队列把 SurfaceControl 与回调配对（674）。三条通道分别是：

  • commit 回调 transactionCallback（389-452）：更新 transformHint、corner radii、frame timestamps，并用 previousReleaseFence 释放更早的 buffer（432-443）；这是 buffer 真正可以回到 client 复用的时刻之一。
  • sync 事务的提交回调 transactionCommittedCallback（348-379）：只用于 BLAST sync 路径，mSyncedFrameNumbers.erase(currFrameNumber) 后若集合空就 flushShadowQueue() 把等待期间堆积的 frame 一次性处理。
  • release 回调 makeReleaseBufferCallbackThunk（467-479）：刻意用 wp<BLASTBufferQueue> 而不是 sp，注释说明「如果 BBQ 已死则什么都不做，buffer 由 client 自己回收」，避免回调延长 BBQ 生命周期。

还有一条反方向的通道：updateBufferReleaseProducer() 通过 setBufferReleaseChannel 把 BufferReleaseChannel 交给 SF（1453-1461），SF 后续直接把 release fence 从该通道送回 client，再用 drainBufferReleaseConsumer() 消费（1463-1475）。注释提醒这必须单独发一个 Transaction，否则一旦 SELinux 拦截 fd 传递，会连带丢掉整包更新。

另外，client 侧的 producer listener 被 AsyncProducerListener 包成异步（1165-1180：AsyncProducerListenerWorker::getInstance().post(...)），注释写的是 emulate one way binder calls，避免 SF 回收 buffer 时把 RT 阻塞住。

sync 事务：唯一会让 RenderThread 停下来等 SF 的路径

BLAST 支持同步事务：client 指定一个 Transaction，要求等它被 SF 提交后再继续。onFrameAvailable 里 syncTransactionSet = mTransactionReadyCallback != nullptr（788）；如果设置了，就进同步分支：

  1. 若复用同一个 mSyncTransaction，先把里面可能残留的 buffer getAndClearBuffer 并 release（795-803）；
  2. 把 mNumFrameAvailable 排空（sync 分支用 acquireAndReleaseBuffer 直接丢，非 sync 分支则 mCallbackCV.wait 等到队列空，812-825）；
  3. 把 frameNumber 记进 mSyncedFrameNumbers，然后 while (acquireNextBufferLocked(mSyncTransaction) == NO_BUFFER_AVAILABLE) mCallbackCV.wait(_lock)（844-850）——这里会阻塞，而且是在 RT 上阻塞；
  4. 给该事务加 commit 回调，如果 mAcquireSingleBuffer 就把 mTransactionReadyCallback 摘下来，在锁外回调 prevCallback(prevTransaction)（854-869）。

为什么这条路径允许阻塞？因为同步事务的使用者（例如 SurfaceView 的同步队列、窗口切 Surface 时的 BLAST sync）必须保证顺序，宁可让生产者等。常规路径则完全不阻塞：apply 是 oneway，RT 立刻返回继续画下一帧。这也是判断「掉帧到底是 SF 慢还是 client 慢」的关键分岔——只有 sync 事务会把 SF 的延迟反向传导到 RT。

与 VSYNC 的关系：buffer 到了也不会马上合成

本阶段完全是被动输入：buffer 什么时候到由 client 决定。setTransactionFlags 是唯一的「叫醒 SF」动作（SurfaceFlinger.cpp:5297-5313）：mTransactionFlags.fetch_or(mask) 之后只有「从无到有」那一次才 mScheduler->resync(...) 并 scheduleCommit(frameHint)。也就是说批量事务只会触发一次 scheduleCommit（SurfaceFlinger.cpp:2508-2514 → mScheduler->scheduleFrame() → MessageQueue 向 VSyncDispatch 注册一次回调），下一次 vsync 才真正处理，事务不会打断正在进行的 commit/composite。

到了 vsync 的 commit 阶段，事务还要过「时间检查」：transactionReadyTimelineCheck（5315-5354）会拒绝 desiredPresentTime 还没到（且在未来 1 秒内）的事务，也会对没有 vsyncId 的事务做 isVsyncValid 节流；frameIsEarly（5523-5541）则判断「这个 vsyncId 预测的 present time 比当前 expectedPresentTime 早太多」，此时事务同样 NotReady，留到下一帧。这解释了为什么「buffer 已经 apply 了，屏幕却要再过一两帧才变」——它在等一个合适的 vsync。

排障：怎么确认 buffer 卡在 client、binder 还是 SF 队列

按层排查：

  1. client 侧：QueuedBuffer - <BBQ name>BLAST#<id> 这个 ATRACE_INT 计数器（BLASTBufferQueue.cpp:203、833-834）在本进程内实时显示 mNumFrameAvailable + mNumAcquired - mPendingRelease.size()；数值持续上涨说明 buffer 积压在 client（SF 没及时 release，或 BBQ 达到 mMaxAcquiredBuffers + 2 上限后拒绝 acquire，578-582）。同步事务卡住时日志里会出现 waiting for available buffer / waiting until no queued buffers。
  2. IPC / SF 入队：trace 里看 setTransactionState（SFTRACE_CALL，5581）与 TransactionQueue 计数器（TransactionHandler.cpp:36、88），后者是 mPendingTransactionCount，长期不下降说明主线程没在 flush。
  3. SF 出队：TransactionHandler:flushTransactions（SurfaceFlinger.cpp:2779）与 Layers: +N -M txns:K 的 instant（2812-2816）能看出每帧处理了多少事务。
  4. 是否被节流：TransactionHandler 会打印 "is waiting on barrier" 的 instant（TransactionHandler.cpp:109-110），表示卡在 TransactionBarrier；dumpsys SurfaceFlinger --latency / --frame-stats 可看 per-layer 的 latch 与 acquire 时间线。

最后提醒：dumpsys SurfaceFlinger --list 里每个 layer 名通常带 [BBQ] 前缀（SurfaceControl.cpp:142），可以用它反查 trace 中的 BBQ 名与 layer 对应关系。

02Scheduler：commit 与 composite

VSyncDispatch 的 timer 线程发 vsyncId，SF 主线程先 commit 再决定要不要 composite

SF 的 vsync 来自 VSyncDispatch：MessageQueue::vsyncCallback 在 dispatch 的 timer 线程上被调用，先用 TokenManager::generateTokenForPredictions 为 (targetWakeupTime, readyTime, vsyncTime) 生成 VsyncId，再通过 Handler::dispatchFrame 用 mFramePending 去重后 sendMessage 到 SF 主线程（这是整条链路里唯一一次线程切换）。主线程 Handler::handleMessage 调 Scheduler::onFrameSignal：构造 FrameTargeter::BeginFrameArgs 给 pacesetter 与各 follower display 调 beginFrame 算出 expectedPresentTime，然后调 ICompositor::commit。commit 返回 false 就只上报 FrameTimeline 的 NotComposited 并直接返回，不做合成；只有返回 true 才继续走 ICompositor::composite，最后对每个 display 调 FrameTargeter::endFrame 收尾。android17 的 native 代码里已经没有 onMessageRefresh（全仓库 grep 无命中），刷新被显式拆成 commit/composite 两个阶段。由于 SF 只在需要时才向 VSyncDispatch 注册回调，没有事务时它根本不会醒——所谓「空转」是没有注册 vsync，而不是空跑循环。

MessageQueue::vsyncCallback()→MessageQueue::Handler::dispatchFrame()→MessageQueue::Handler::handleMessage()→Scheduler::onFrameSignal()→FrameTargeter::beginFrame()→SurfaceFlinger::commit()→SurfaceFlinger::updateLayerSnapshots()→SurfaceFlinger::composite()→FrameTargeter::endFrame()

触发者与线程：一次 vsync 回调要跨两个线程

SF 自己不轮询 vsync，它向 scheduler::VSyncDispatch 注册回调。MessageQueue::initVsyncInternal(dispatch, tokenManager, workDuration) 把 getVsyncSchedule()->getDispatch() 与 TokenManager 装进来（Scheduler.cpp:91-93），onNewVsyncScheduleLocked 创建 VSyncCallbackRegistration 并绑定 &MessageQueue::vsyncCallback，名字就叫 "sf"（MessageQueue.cpp:111-130）。

线程一：vsyncCallback 跑在 VSyncDispatch 的 timer 线程上（MessageQueue.cpp:101-107 的注释明确提到 callback 可能运行在 timer thread，因此析构 registration 必须释放锁后做，否则会死锁）。它做三件事：翻转 TracedOrdinal<int> value = {"VSYNC-sf", 0} 计数器（62 行、MessageQueue.h:130）；在 mVsync.mutex 下更新 lastCallbackTime 并清掉 scheduledFrameTimeOpt（65-69）；用 tokenManager->generateTokenForPredictions({targetWakeupTime, readyTime, vsyncTime}) 生成这次的 VsyncId（71-72）。

线程二：Handler::dispatchFrame 用 mFramePending.exchange(true) 做去重（重复的 vsync 只会排队一次），把 vsyncId/expectedVsyncTime 存进两个 atomic 成员，然后 mQueue.mLooper->sendMessage(...) 把工作甩到 SF 主线程（32-38）。主线程 handleMessage 先清 pending 标志，再调 mQueue.onFrameSignal(...)（44-47）。onFrameSignal 在 MessageQueue 里是纯虚函数（MessageQueue.h:115），实现就是 Scheduler::onFrameSignal——因为 Scheduler : public IEventThreadCallback, android::impl::MessageQueue（Scheduler.h:81）。

所以一次 vsync 处理 = timer 线程算 id 并投递 + 主线程干完整活。这也意味着 vsyncCallback 的耗时不能算进 SF 主线程，排查上要分开看。

按需注册：没有事务时 SF 不注册 vsync，这就是「空转」

MessageQueue::scheduleFrame(workDurationSlack) 是唯一给 VSyncDispatch 排下一拍的地方（191-200）：

const auto workDuration = Duration(mVsync.workDuration.get() - workDurationSlack);
mVsync.scheduledFrameTimeOpt = mVsync.registration->schedule({.workDuration = workDuration.ns(), .readyDuration = 0, .lastVsync = mVsync.lastCallbackTime.ns()});

workDuration 来自 VsyncModulator 的 sfWorkDuration（Scheduler.cpp:416-422 把它放进 BeginFrameArgs），readyDuration 固定 0，lastVsync 用上一次回调时间做相位基准——这就是 SF 与 app 处在同一个 vsync 相位、但工作窗口不同的机制——app 那一侧的 EventThread 复用的正是同一个 VsyncSchedule：std::make_unique<android::impl::EventThread>("app", getVsyncSchedule(), tokenManager, *this, workDuration, readyDuration)（Scheduler.cpp:583-588）。

关键结论：SF 只在需要时注册 vsync。真正触发注册的是事务到达路径 setTransactionFlags（SurfaceFlinger.cpp:5297-5313）里「标志从无到有」那一次 scheduleCommit，以及 commit 内部发现还需要下一拍的各种分支（例如 display mode set pending、HWC 背压，3022-3067）。没有事务、没有 mustComposite 时，scheduleFrame 不会被调用，SF 主线程就停在 waitMessage() 的 mLooper->pollOnce(-1) 上（MessageQueue.cpp:148-168）。

这就是「SF 空转」的准确含义：不是 SF 空跑循环，而是根本没有注册 vsync 回调。反过来说，如果 trace 里看到 SF 每个 vsync 都醒但 commit 一直返回 false，那就是有东西在持续注册 vsync（例如某个动画层的 frame rate 投票、或者 requestNextVsync），需要往上报者查。

BeginFrameArgs 的结构定义在 FrameTargeter.h:134-141，debugPresentTimeDelay 是调试注入 jank 用的。随后对 pacesetter display 调 targeterPtr->beginFrame(beginFrameArgs, *pacesetterPtr->schedulePtr)（424-425）——beginFrame 的作用是把 vsync 时间换算成这个 display 真正可以上屏的 expectedPresentTime；此前 Scheduler 还从 mDebugPresentDelay 取了一次一次性延迟（413-414）。

commit：返回 true 才有资格 composite

这是本阶段最核心的一行（Scheduler.cpp:470-474）：

    compositor.sendNotifyExpectedPresentHint(pacesetterPtr->displayId);
    mSchedulerCallback.onCommitNotComposited();
    return;

ICompositor::commit 的契约写在接口注释里（native/services/surfaceflinger/Scheduler/include/scheduler/interface/ICompositor.h:41-43）：Commits transactions for layers and displays. Returns whether any state has been invalidated, i.e. whether a frame should be composited for each display. 也就是 commit 既做「应用事务」，又回答「这一拍到底要不要合成」。

返回 false 时的三个动作都有含义：sendNotifyExpectedPresentHint 把预期上屏时间提示给 SurfaceControl 的调用方；mSchedulerCallback.onCommitNotComposited() 落到 SurfaceFlinger::onCommitNotComposited()（SurfaceFlinger.cpp:5158-5159）→ mFrameTimeline->onCommitNotComposited()（FrameTimeline.cpp:1432-1439），给当前 DisplayFrame 记一次「commit 了但没合成」并重置它；然后直接 return，不做 composite、不调 endFrame。

SurfaceFlinger::commit 一侧的返回逻辑（2996-3202）：初始化 mustComposite = mMustComposite.exchange(false)（3119），再 mustComposite |= updateLayerSnapshots(...)（3137-3140），中途还有多个 early return false：display 被移除（3022-3032）、mode set 未完成（3035-3057）、HWC 背压且策略要求退让（3059-3067）。最终 return mustComposite && CC_LIKELY(mBootStage != BootStage::BOOTLOADER)（3201）——即使在开机动画之前 mustComposite 为真也不合成。所以「commit 返回 false」不是错误，而是「这一拍没有需要上屏的状态变化」。

composite：只有到这里才碰 GPU / HWC

commit 返回 true 后，Scheduler 重新取一次 pacesetter（注释：pacesetter 可能在 commit 期间变更或新注册，477-481），组装 FrameTargeters（把本帧 presentable 的 display 的 targeter 收进来，483-489），然后调 compositor.composite(pacesetterId, targeters)（501）。

ICompositor::composite 的注释（ICompositor.h:45-48）写明：Composites a frame for each display. CompositionEngine performs GPU and/or HAL composition via RenderEngine and the Composer HAL, respectively. 对应实现是 SurfaceFlinger::composite（3330 起），它开了一个 SFTRACE_ASYNC_FOR_TRACK_BEGIN(..., "Composition", WorkloadTracer::COMPOSITION_TRACE_COOKIE) 的异步 slice，最终把 GPU 合成（RenderEngine）与 HWC 合成分别下发。

合成完有三步收尾（501-509）：sendNotifyExpectedPresentHint、compositor.sample()（RegionSamplingThread 采样，用于 HDR/白点/自适应亮度）、以及遍历每个 targeter 调 endFrame(*resultOpt)。若某个 display 没有返回 CompositeResult，直接 LOG_ALWAYS_FATAL_IF(!resultOpt) 崩掉——这是契约而不是容错。

还有一段调试用的「注入 jank」逻辑：mPacesetterFrameDurationFractionToSkip > 0 时按期望帧时长的一定比例 std::this_thread::sleep_for(skipDuration)，并打 "Injecting jank for %f%% of the frame"（491-499）。这是 SF 自带的 jank 注入开关，线上不会有值，但看 trace 时要知道这段耗时是人为的。

为什么 android17 没有 onMessageRefresh：两段式把「判定」与「执行」拆开

在旧的 SF 里，vsync 消息最终走一个叫 onMessageRefresh 的入口，把所有事情（apply transactions、latch、合成、present）串在一个函数里。android17 的实现里全仓库检索 native/ 已经没有任何 onMessageRefresh 命中；取而代之的是 ICompositor 定义的两段式接口（ICompositor.h:37-58）：configure() / commit() / composite() / sendNotifyExpectedPresentHint() / sample()。

拆开的好处是「判定」与「执行」解耦：commit 只回答「有没有东西要上屏」，而且它可以在不合成的情况下推进状态（例如只 latch 了 buffer 但 damage 为空、或者只有不影响可见内容的几何变化）；composite 才真正分配 GPU/HWC 资源。这让 SF 在空闲时能以「commit 返回 false」的极低成本掠过一拍——这也是为什么 trace 里经常能看到 commit 有 slice 而 Composition 没有。

代价是状态必须在两段之间保持一致：onFrameSignal 在 commit 与 composite 之间重新取 pacesetterFrameTargetPtr（478），并注释说明「pacesetter 可能在 commit 期间变化或新注册」。targeters 也必须在 composite 前重新组装（480-489），否则会用到失效的 pointer。看代码时务必注意这两处「重新取」不是冗余，而是两段式的必然要求。

排障：怎么判断这一拍是「没活干」还是「干不完」

先分清三种情况：

  1. 没活干：trace 里没有 onFrameSignal/commit slice，只有 app 侧的 vsync——说明 SF 压根没被唤醒（没有事务触发 scheduleCommit）。
  2. commit 了但没合成：有 commit slice、没有 Composition slice，且 onCommitNotComposited 被调用。看 SurfaceFlinger::commit 的 early return 分支（3022-3067）与 mustComposite 的来源（mMustComposite.exchange / updateLayerSnapshots 返回值）。
  3. 干不完：commit 或 Composition 的 slice 长度超过 VsyncWorkDuration-sf，或 commit 尾部出现 refresh rate selection、updateInputFlinger 等长尾。

可用的观测点：VSYNC-sf（MessageQueue.h:130，每次回调翻转的计数器，用来数 SF 实际收到几拍）、VsyncWorkDuration-sf（MessageQueue.h:126-127，当前 sfWorkDuration）、commit 自己的 slice 名带 vsyncId（SFTRACE_NAME(Concat(__func__, ' ', vsyncId))，3012）、"Commit"（3068）、"Composition"（3332）、"Refresh Rate Selection"（3174）、以及 follower 背压时的 "Avoiding backpressure for follower display %lu"（459-460）。

一个常见误判：看到 commit 里有 setSfWakeUp 就以为「已经合成」——它只是记账，真正合成在 composite 里，成功与否要看 endFrame 是否被调用。

03commit：事务应用、快照与 latch

updateLayerSnapshots 先构建只读快照、再 latch buffer，最后 doCommitTransactions 翻状态

Scheduler 调 ICompositor::commit 后进入 SurfaceFlinger::commit（SF 主线程，持 mStateLock）。它先往 FrameTimeline 记 setSfWakeUp，然后用 clearTransactionFlags(eTransactionFlushNeeded) 决定本拍要不要 flush，进入 updateLayerSnapshots：flushTransactions 把 binder 线程攒下的 QueuedTransactionState 按 apply token 取出、应用到 LayerLifecycleManager（把 buffer 的 externalTexture merge 进 RequestedLayerState），再在 mStateLock 下构造 LayerSnapshotBuilder::Args 并调用 LayerSnapshotBuilder::update 生成每个 layer 的只读 LayerSnapshot（组合阶段只通过 LayerCompositionState 指针读它）。快照建好之后才做 applyTransactionsLocked（把事务落到 legacy Layer/mCurrentState）、commitTransaction、按 RequestedLayerState 逐个 latchBufferImpl（真正检查 acquire fence 是否 signal、推进 frame timeline），并用 newDataLatched 强制 mustComposite。最后 commitTransactions → commitTransactionsLocked → doCommitTransactions 只做一件事：mDrawingState = mCurrentState。所以「快照是合成输入，latch 是副作用与同步检查」是理解这一阶段的关键。快照与 latch 的先后顺序是这一阶段最容易误读的地方：快照只读 frontend 状态，latch 才检查 acquire fence 并推进 frame timeline。

SurfaceFlinger::commit()→SurfaceFlinger::updateLayerSnapshots()→TransactionHandler::flushTransactions()→LayerLifecycleManager::applyTransactions()→LayerSnapshotBuilder::update()→SurfaceFlinger::applyTransactionsLocked()→Layer::commitTransaction()→Layer::latchBufferImpl()→SurfaceFlinger::commitTransactions()→SurfaceFlinger::doCommitTransactions()

入口：commit 里 updateLayerSnapshots 被调用的位置与前提

SurfaceFlinger::commit(pacesetterId, frameTargets)（native/services/surfaceflinger/SurfaceFlinger.cpp:2996-3202）跑在 SF 主线程，是 Scheduler 两段式里的第一段。它做的前几件事都在为状态推进做准备：先 mFrameTimeline->setSfWakeUp(vsyncId, frameBeginTime, vsyncPeriod 的 Fps, ...) 记账（3130-3133），再 const bool flushTransactions = clearTransactionFlags(eTransactionFlushNeeded)（3135）——这是「本拍到底要不要把 binder 线程攒下的事务刷出来」的唯一判据，然后：

mustComposite |= updateLayerSnapshots(vsyncId, frameBeginTime, expectedPresentTime, flushTransactions, transactionsAreEmpty);

注意三个入参：vsyncId（写进 frame timeline 与 transaction tracing）、frameBeginTime（SF 开始干活的时刻）、expectedPresentTime（latch 判定的目标上屏时间）。transactionsAreEmpty 是出参，随后决定调 sendCallbacks(false /*onCommitOnly*/) 还是 true（3160-3166）——空事务的 commit 回调要尽早发，避免 client 白等一个 present。

函数开头的 SFTRACE_NAME(ftl::Concat(__func__, ' ', ftl::to_underlying(vsyncId))（3012）让 commit 的 slice 名带 vsyncId，这是把 SF 侧与 app 侧同一帧对齐的锚点。updateLayerSnapshots 自己又开了两层 trace："Transaction Handling"（2776）与 "TransactionHandler:flushTransactions"（2779）。

第一段 flushTransactions：从 lockless 队列到 frontend 状态

updateLayerSnapshots（2771 起）只有在 flushTransactions 为真时才做事务处理，顺序被四条注释写得很清楚（2780-2788）：

  1. mTransactionHandler.collectTransactions()：把 binder 线程 push 进 mLocklessTransactionQueue 的事务搬到按 apply token 划分的 mPendingTransactionQueues；
  2. 在 mCreatedLayersLock 下把 mCreatedLayers / mNewLayers / mNewLayerArgs / mDestroyedHandles 搬进 frontend::Update（2792-2801）——注释解释「事务与新建 layer 不共享锁，必须先把 created layers 收出来，否则会应用到还没建好的 layer」；
  3. mLayerLifecycleManager.addLayers(...)、updateDisplayMirrors(...)，然后才 update.transactions = mTransactionHandler.flushTransactions()（2804-2807）；
  4. mLayerLifecycleManager.applyTransactions(update.transactions)（2824）把每个 ResolvedComposerState merge 进 RequestedLayerState，最后 mLayerHierarchyBuilder.update(mLayerLifecycleManager)（2829）刷新层级。

为什么 buffer 在这一步就「到位」了？因为 RequestedLayerState::merge 在 eBufferChanged 分支里直接 externalTexture = resolvedComposerState.externalTexture（native/services/surfaceflinger/FrontEnd/RequestedLayerState.cpp:216-217），而 externalTexture 是 SurfaceFlinger::setTransactionState 在 binder 线程就解析好的（SurfaceFlinger.cpp:5654-5658）。所以 frontend 状态在本帧快照构建之前就已经带着新 buffer。

顺带把 workload hint 与事务追踪也在这里记：mPowerAdvisor->setCommittedWorkload(committedWorkload)（2818）、mTransactionTracing->addCommittedTransactions(...)（2819-2823）、以及一条 instant "Layers: +N -M txns:K"（2812-2816）。

第二段：构建 LayerSnapshot —— 组合阶段的唯一输入

事务进了 frontend 之后，updateLayerSnapshots 才去拿 mStateLock（2837），然后构造 frontend::LayerSnapshotBuilder::Args（2841-2862）：root 是 mLayerHierarchyBuilder.getHierarchy()，layerLifecycleManager 是本帧的 frontend 状态，displays/displayChanges 来自 display 事务，另外还有 forceUpdate（由 frontend_caching_v0 决定）、forceFullDamage、supportsBlur、shiftRoundCornersWhenProtected 等开关。然后：

  • 若启用了 frontend caching，先 mMergeableHierarchyManager.update(...) 与 constructSnapshots(...)（2864-2880）；
  • 统一 mLayerSnapshotBuilder.update(args)（2881-2884，trace 名 "LayerSnapshotBuilder:update"）。

LayerSnapshotBuilder::update（FrontEnd/LayerSnapshotBuilder.cpp:565-574）先给所有 snapshot clearChanges，再走 tryFastUpdate 快路径，否则 updateSnapshots(args) 全量遍历层级；每个 snapshot 通过 merge(*requested, forceUpdate, displayChanges, forceFullDamage, ...) 刷新（405、415、590 三处调用）。

只读性：LayerSnapshot : public compositionengine::LayerFECompositionState（LayerSnapshot.h:70），结构体上方的注释写得很直白——它存的是 CompositionEngine 与 RenderEngine 需要的 layer state，Composition Engine uses a pointer to LayerSnapshot (as LayerFECompositionState*)，RenderEngine 的 LayerSettings 也是从这些字段生成的。因此快照一旦建好，组合阶段就只读不写；所有写入都发生在 builder 的 merge 里。这也是 android17 前端缓存（frontend caching）能复用快照的前提。

第三段：快照之后才 applyTransactionsLocked 与 doCommitTransactions

快照建好之后（2884），updateLayerSnapshots 继续做「把事务真正落到 legacy Layer 与 mCurrentState」的动作：

  1. mustComposite |= applyTransactionsLocked(update.transactions)（2906）。applyTransactionsLocked（5501-5517）对每个事务调 applyTransactionState（5757 起），在 mStateLock 保护下把 client 状态写进 mCurrentState 与 Layer（例如 Layer::setBuffer，Layer.cpp:921-1000）。
  2. traverseLegacyLayers([&](Layer* layer) { layer->commitTransaction(); })（2907）：让每个 legacy layer 提交自己的 pending 状态。
  3. const nsecs_t latchTime = systemTime()（2908）：本拍统一的 latch 时间戳，后面所有 latch 都用它，保证同一帧内的层看到同一个时间基准。
  4. latch 循环（2911-2959，见下一节），newDataLatched 会参与 mustComposite（2988）。
  5. mLayerLifecycleManager.commitChanges()（2977-2980）：把 frontend 的 changes 位清零，准备下一拍。

然后 if (mustComposite) commitTransactions()（2989-2991）。commitTransactions（4039-4050）非常短：mScheduler->modulateVsync({}, &VsyncModulator::onTransactionCommit) 调整 vsync 相位，再 commitTransactionsLocked(clearTransactionFlags(eTransactionMask))——注释强调「清标志要在持 mStateLock 时做，保证提交完成前 mCurrentState 不变」。commitTransactionsLocked（4803-4834）只是把各种「有 layer 增删/子节点变化/input 信息需要更新」的旗标转成 mVisibleRegionsDirty/mUpdateInputInfo，最后调 doCommitTransactions()。

doCommitTransactions（5236-5240）全部内容只有两行：mDrawingState = mCurrentState; 与 mCurrentState.colorMatrixChanged = false;。这行赋值是「状态翻转」的全部含义——mDrawingState 只是主线程自用的状态副本（SurfaceFlinger.h:1443-1445 注释：can only accessed from the main thread），真正的合成输入是前面建好的 LayerSnapshot，而不是 mDrawingState。

latch 循环（2911-2959）遍历的是 mLayerLifecycleManager.getLayers()（frontend 的 RequestedLayerState），再按 id 找 legacy Layer：

几点值得注意：

  • 没有 ready frame 的 layer 不是什么都不做：它会 updateFrameTimelinePastTimestamps 记下 latchTime 与 expectedPresentTime，注释解释这是为了把「因为背压而没 latch 到 buffer」和「真的错过帧」区分开（2935-2939）。
  • fence 在 latch 里才被检查：Layer::latchBufferImpl（Layer.cpp:1506 起）打一条 SFTRACE_FORMAT_INSTANT("latchBuffer %s - %" PRIu64, ...)（1509-1510），然后如果 mDrawingState.buffer && !fenceHasSignaled() 就 SFTRACE_NAME("!fenceHasSignaled()")、mFlinger->onLayerUpdate() 并返回 false（1518-1524）——这就是「acquire fence 在 commit 阶段被检查、但不阻塞等待」的实现。
  • latch 会强制合成：成功 latch 后 newDataLatched = true（2954），而 mustComposite |= ... || newDataLatched（2988）。
  • latch 之后还要读一次 snapshot 的 gameMode 放进 mLayersWithQueuedFrames（2956-2958），供 frame rate 决策使用。

顺序上「先快照、后 latch」是刻意的：快照只需要 frontend 状态（buffer 的 externalTexture 在 2824 行就 merge 进去了），而 latch 涉及 legacy Layer、fence、frame timeline 记账这些带副作用的动作。把无副作用的读取放在前面，可以让快照在加锁窗口内尽早完成，缩短 mStateLock 的持有时间。

时间规则：事务什么时候算 ready

不是所有到了的事务都会在这一拍被应用。flushTransactions 内部会给每个事务跑一遍 filter，SF 注册的关键一个是 SurfaceFlinger::transactionReadyTimelineCheck（5315-5354）：

  • 若 client 指定了 desiredPresentTime（!isAutoTimestamp）且它 >= expectedPresentTime 但又在 1 秒内，就返回 NotReady——事务继续等，打一条 "not current desiredPresentTime" 的 instant；
  • 若事务没有 vsyncId（INVALID_VSYNC_ID）且 !isVsyncValid(expectedPresentTime, originUid)，也 NotReady——这是 frame rate override 的节流；
  • 若 isAutoTimestamp 且 frameIsEarly(expectedPresentTime, vsyncId)，同样 NotReady（frameIsEarly 实现在 5523-5541）。

另一条规则是 shouldLatchUnsignaled（5543-5577）：只有在「本事务只改一个 layer」（numStates == 1）、不是 AutoSingleLayer 的后续事务、且不处于 early/client composition 时，才允许 latch 一个 acquire fence 还没 signal 的 buffer。注释解释了为什么 early/client composition 时要禁止：否则 RenderEngine 会等一个未 signal 的 buffer 而引入 jank。

这两条规则合起来解释了「事务已经 apply 了，为什么这一拍没 latch 到 buffer / 为什么没合成」：它可能在等 desiredPresentTime 或等一个合法的 vsync_id，也可能因为不是单 layer 事务而被拒绝 latch 未 signal 的 buffer。

排障：commit 慢或事务不生效怎么定位

按信号分四层：

  1. 事务有没有进来：对比 TransactionQueue 计数器与 "TransactionHandler:flushTransactions" 的 slice。队列有量但不 flush，说明 clearTransactionFlags(eTransactionFlushNeeded) 没拿到标志位（scheduler 没排这一拍）。
  2. 事务为什么没被应用：看 "not current desiredPresentTime"、"!isVsyncValid"、"!frameIsEarly" 这几条 instant（SurfaceFlinger.cpp:5330-5353）。它们直接告诉你是 desiredPresentTime、frame rate 节流还是 vsyncId 预测导致的 NotReady。
  3. 快照阶段："LayerSnapshotBuilder:update" 的耗时是前端成本的大头；frontend caching 打开时还会有 "MergeableHierarchyManager::update" 与 "MergeableHierarchyManager::constructSnapshots"（2866、2871）。
  4. latch 阶段："latchBuffer %s - %" PRIu64 的 instant（Layer.cpp:1509）能逐层看到 frameNumber；出现 "!fenceHasSignaled()" 说明该层的 acquire fence 还没好，本拍会被跳过。

还有一个高频疑问「为什么 commit 里有一大段持锁」：updateLayerSnapshots 从 2837 行 Mutex::Autolock lock(mStateLock) 一直持到函数末尾，期间包含快照构建、applyTransactionsLocked、latch 与 commitChanges。binder 线程只写 lockless 队列不抢这把锁，但任何非主线程的读（例如 dumpsys、input 查询）都要排队，所以 trace 里 commit 越长，mStateLock 的争用越明显。

最后可以用 dumpsys SurfaceFlinger --layers（或 --proto）对照 RequestedLayerState 与 snapshot 的差异：如果 frontend 已经有 buffer 但合成输入里没有，问题在快照构建；如果两者都有但屏幕没变，问题在 composite/HWC 而不在本阶段。

04第 4 拍：latch 与 acquire fence

SurfaceFlinger 在主线程把 transaction 里的 buffer 变成 drawing state；acquire fence 未 signal 时这一帧就不消费它

SurfaceFlinger 主线程在 vsync 报告的 commit 阶段做 latch：MessageQueue::Handler::handleMessage → Scheduler::onFrameSignal → compositor.commit → SurfaceFlinger::commit → updateLayerSnapshots（native/services/surfaceflinger/SurfaceFlinger.cpp:2771）。每个有 ready frame 的 layer 会被调 latchBufferImpl（2953），把 transaction 里带来的 buffer 认作本帧要显示的内容。核心闸门是 fenceHasSignaled()：drawing state 有 buffer 而 acquire fence 还没 signal 时，打 “!fenceHasSignaled()” trace、调 onLayerUpdate 触发下一次 commit 并返回 false，本帧不消费。latch 成功则记 TimeStats 与 FrameTracer 的 acquire fence、latch 时间，把 SurfaceFrame 以 Presented 状态交给 FrameTimeline；最后按 snapshot.contentDirty 把该 layer 的可见区域并进 output 脏区，供合成阶段决定重绘范围。这一拍只做簿记：不拷贝像素，也不产生 GPU 工作，却决定了本帧到底消费了哪些 buffer；一旦被 fence 挡住，整条流水线就整体往后错一帧，对应用侧来说这里也是 buffer 能否被归还的分水岭。

MessageQueue::Handler::handleMessage()→Scheduler::onFrameSignal()→SurfaceFlinger::commit()→SurfaceFlinger::updateLayerSnapshots()→Layer::latchBufferImpl()→Layer::fenceHasSignaled()→SurfaceFlinger::onLayerUpdate()→Layer::latchBufferStatsAndHandles()→Layer::gatherBufferInfo()→Layer::addSurfaceFramePresentedForBuffer()

谁在什么时候 latch

调用链从 SF 主线程的消息循环开始：MessageQueue::Handler::handleMessage（native/services/surfaceflinger/Scheduler/MessageQueue.cpp:44-48）里 mQueue.onFrameSignal(mQueue.mCompositor, mVsyncId, mExpectedVsyncTime) → Scheduler::onFrameSignal（Scheduler/Scheduler.cpp:411）→ compositor.commit(pacesetterPtr->displayId, targets)（Scheduler.cpp:470）→ SurfaceFlinger::commit（SurfaceFlinger.cpp:2996）→ updateLayerSnapshots（3138 调用，函数本体 2771）。

所以 latch 的执行线程是 SF 主线程，时机是“vsync 报告之后的 commit 阶段”，在合成（compositor.composite，Scheduler.cpp:503）之前。updateLayerSnapshots 的注释与 trace 名字都指向这一步的职责：SFTRACE_NAME_FOR_TRACK(WorkloadTracer::TRACK_NAME, "Transaction Handling")（2775）。binder 线程此时只负责把 transaction 收进队列，真正应用在 applyTransactionsLocked(update.transactions)（2906）与随后的 latch 循环（2911-2959）。

buffer 怎么到 SF：BLAST 之后没有 per-layer BufferQueueConsumer

BLAST 模型下 buffer 不再由 SF 主动从 BufferQueue 取，而是跟着 Transaction 一起到达：Layer::setBuffer(std::shared_ptr<renderengine::ExternalTexture>& buffer, const BufferData& bufferData, ...)（Layer.cpp:921）在应用 transaction 时被调用，buffer handle 与 acquire fence 放在 BufferData 里。这意味着在 SF 里搜 BufferQueueConsumer::acquireBuffer 是搜不到 per-layer 路径的——整个 SF 中唯一还持有 consumer 的是 FramebufferSurface 的 BufferItemConsumer mRendererConsumer（DisplayHardware/FramebufferSurface.h:83），它对应 HWC 的 client target，不是应用图层。

BufferData（native/libs/gui/include/gui/LayerState.h:115-169）是跨进程结构：sp<GraphicBuffer> buffer、sp<Fence> acquireFence、uint64_t frameNumber、producerId、cachedBuffer（client_cache_t）、dequeueTime，以及 releaseBufferListener（sp<ITransactionCompletedListener>，:150）与 releaseBufferEndpoint。这些字段通过 binder parcel 传递（writeToParcel/readFromParcel），GraphicBuffer 走 handle、Fence 走 fd，真正的像素内存不出 binder。

acquire fence 未 signal：整帧不消费

latch 的第一道闸门在 Layer::latchBufferImpl 开头（Layer.cpp:1518-1524）：

若 mDrawingState.buffer 存在但 fenceHasSignaled() 为假，打 SFTRACE_NAME("!fenceHasSignaled()")、调 mFlinger->onLayerUpdate()，然后 return false。

fenceHasSignaled（Layer.cpp:1203-1216）先看 SurfaceFlinger::enableLatchUnsignaledConfig：只要不是 LatchUnsignaledConfig::Disabled 就直接返回 true（不再检查 fence）；否则读 getDrawingState().acquireFence->getStatus() == Fence::Status::Signaled，未 signal 时给 TimeStats 记一笔 incrementLatchSkipped(getSequence(), LatchSkipReason::LateAcquire)。LatchUnsignaledConfig 的注释（SurfaceFlinger.h:189-197）解释了放行条件：单 layer 更新且只有 buffer 变化、且只应用了一个 transaction 时才允许，避免 HWC 收到未 signal 的 fence 而错过呈现。

onLayerUpdate 的实现只有一句：scheduleCommit(FrameHint::kActive)（SurfaceFlinger.cpp:9208-9210），即“这一帧没东西可显示，再排一次 commit”。于是同一个 buffer 会在下一个 vsync 的 commit 里重试。对应用的直接后果是这一帧的内容迟到一帧甚至更久，jank 从 SF 侧被引入。

时间预算：这一拍必须在哪个点前结束

SF 的工作窗口由 Scheduler 给定：Scheduler::onFrameSignal 组装 FrameTargeter::BeginFrameArgs 时带上了 sfWorkDuration（mVsyncModulator->getVsyncConfig().sfWorkDuration）与 hwcMinWorkDuration（Scheduler/Scheduler.cpp:411-424），beginFrame 据此推出该帧的 expectedPresentTime。commit 与 latch 必须在这个 deadline 之前完成，后面的 compositor.composite（Scheduler.cpp:503）才有机会把内容交给 HWC 并在本 vsync 呈现。换言之，latch 是 SF 侧最靠近“输入”的一步，它多花的时间会直接挤占合成与 HWC 的预算。

latch 未通过时（acquire fence 未 signal），onLayerUpdate → scheduleCommit(FrameHint::kActive) 会额外排一次 commit，最早只能在下一个 vsync 的 commit 里重试，等价于该 layer 至少迟到一帧；如果 fence 迟到是间歇性的，就会表现为“偶尔掉一帧”而不持续 jank。反过来，如果 latch 很快但 contentDirty 为假，则会出现“commit 很轻、屏幕上却什么都没变”的现象——两种“没有变化”的成因完全不同：前者是内容没到，后者是内容到了但没被判定为脏，排障时必须分开看。

latch 成功后的三笔账：TimeStats、FrameTracer、FrameTimeline

闸门通过后 latchBufferImpl 继续：latchBufferStatsAndHandles(latchTime, expectedPresentTime, bgColorOnly)（Layer.cpp:1525）→ 备份 oldBufferInfo → mCurrentFrameNumber = mDrawingState.frameNumber → gatherBufferInfo()（1531）。其中 latchBufferStatsAndHandles（1239-1288）做了三件事：

  • TimeStats：setAcquireFence(layerId, frameNumber, acquireFence) 与 setLatchTime(...)（1266-1267），acquire fence 先被包成 FenceTime（1262）。
  • FrameTracer：traceFence(..., FrameEvent::ACQUIRE_FENCE) 与 traceTimestamp(..., FrameEvent::LATCH)（1269-1272），这两个事件是 Perfetto 里对齐 app queue 与 SF latch 的锚点。
  • FrameTimeline：若 mDrawingState.bufferSurfaceFrameTX 非空且还没 Presented，就调 addSurfaceFramePresentedForBuffer(...)（1280-1283）；该函数（461-469）设置 setAcquireFenceTime、setPresentState(Presented, mFrameTimelinePastTimestamps)，再 mFlinger->mFrameTimeline->addSurfaceFrame(surfaceFrame)。

如果 buffer 被更早的 transaction 替换掉，则由 releasePreviousBuffer 打 addSurfaceFrameDroppedForBuffer(...) 记 Dropped（870），这是 SurfaceFrame 的另一半生命周期。

contentDirty 如何变成 output 脏区

latch 只更新 layer 自身，是否要重绘由快照驱动。循环结束后 mLayerSnapshotBuilder.forEachSnapshot(...)（SurfaceFlinger.cpp:2962-2970）：

若 snapshot.isVisible && snapshot.contentDirty，或 !snapshot.isVisible 且 Visibility 刚变，就用 transformedBoundsWithoutTransparentRegion 调 invalidateLayerStack(snapshot.outputFilter, visibleReg)。

contentDirty 定义在 compositionengine/LayerFECompositionState.h:118，LayerSnapshot 继承它（FrontEnd/LayerSnapshot.h:70）。置位点在 FrontEnd/LayerSnapshot.cpp:414（requested.what & layer_state_t::CONTENT_DIRTY || autoRefresh）与 LayerSnapshotBuilder.cpp:337/806。这是本阶段与合成阶段的唯一通路：latch 决定“有什么内容”，contentDirty 决定“要不要重画哪一块”。

release 的两条路：BLAST 回调与 HWC release fence

buffer 被 SF 用完要还给应用，路径有两条且互不替代：

  1.   2. 此外 releasePreviousBuffer（Layer.cpp:853-879）处理“上一帧的 buffer 还没显示就被替换”的情况：EARLY_RELEASE_ENABLED 且存在 mLastClientCompositionFence 时用该 fence（873-878），否则直接用 mDrawingState.acquireFence 回调并 decrementPendingBufferCount()。这条路径决定应用还能拿到几个 buffer，直接连着 BufferQueue 的 slot 供给。

排障：这一拍出问题时看什么

  • 内容迟到一帧：先看 trace 里有没有 “!fenceHasSignaled()”，有则问题在 produce 侧 fence 太晚（GPU 还没画完就把 buffer 交了），而不是 SF 慢。
  • latch 次数正常但屏上不动：查 contentDirty 与 output 脏区，latch 只负责内容，不负责“要不要重画”。
  • 应用 buffer 用尽（dequeue 阻塞）：看 release 路是否漏了——BLAST 路看 “callReleaseBufferCallback”，HWC 路看 present/release fence 是否 signal。decrementPendingBufferCount 与 getMaxAcquiredBufferCountForCurrentRefreshRate（Layer.cpp:722-723）共同决定应用可用的 buffer 数。
  • FrameTimeline 上 SF 帧缺失：确认 bufferSurfaceFrameTX 是否被 Dropped 掉（870），Dropped 的 SurfaceFrame 不会以 Presented 上报。

HWC 还会通过 layerRequests 要求某个 layer 清缓存或改 clear 行为，通过 displayRequests 要求 SF 做整体颜色变换；clientTargetProperty 则告诉 SF 该用什么 dataspace/亮度去准备 client target——这些都会影响下一拍 GPU 合成的输出格式。

validate 之后、present 之前：决策如何兑现

决策落定后，Output::present 继续：prepareFrame()（或预测路径的 prepareFrameAsync()）→ devOptRepaintFlash → finishFrame(std::move(result)) → presentFrameAndReleaseLayers(flushEvenWhenDisabled)（Output.cpp:498-516）。其中 finishFrame（1312-1349）在 usesClientComposition 时 dequeueRenderBuffer + composeSurfaces，把 GPU 合成的 ready fence 通过 mRenderSurface->queueBuffer(...)（1348）交给 HWC 侧（对应 FramebufferSurface::advanceFrame 里的 setClientTarget）。

随后 presentFrameAndReleaseLayers（1726-1798）调 presentFrame()（基类 1828-1834，返回 client target 的 acquire fence；Display::presentFrame 在 Display.cpp:416-453 里再调 hwc.presentAndGetReleaseFences(...) 并取每层 release fence）。这正是 CompositionEngine::present 里 “Waiting on HWC” 那段在等的东西：present 的耗时既包含 HAL 下发，也包含等待 HWC 接管 buffer。

一个常见误区是把 validate 当成“SF 决定一切”。实际上 SF 只提供请求与几何，HWC 可以在 validate 中否决任何一层（改成 CLIENT），也可以只要求改某层的 clear/缓存行为；SF 必须无条件接受并在同一帧内重新组织合成——这正是 previousDeviceRequestedChanges 与预测机制存在的原因。

排障：validate 相关的典型现象

  • 整屏掉到 GPU 合成：看 usesDeviceComposition 是否为 false、以及 HWC 是否把大量 layer 放进 changedTypes；常见原因是格式（如 HDR/10bit）、缩放比例超限、旋转或圆角要求，HWC 无法用 plane 承接。
  • validate 很慢：perfetto 里 chooseCompositionStrategy for <display> slice 会拉长，多屏时尤其明显；注意它可能跑在 mHwComposerAsyncWorker 线程上，不在 SF 主线程。
  • composition type 每帧抖动：会连续出现 CompositionStrategyPredictionMiss（Output.cpp:1272），预测机制失效，validate 无法跳过。
  • 画面缺层/闪黑：检查被 HWC 改成 CLIENT 的层是否真的被 generateClientCompositionRequests 收录（下一拍），以及 clientTargetProperty 指定的 dataspace 是否与实际 buffer 匹配。

06第 6 拍：RenderEngine GPU 合成

凡是 HWC 不肯用 overlay 接的层，都由 RenderEngine 在 GPU 上合进 client target，再交给 HWC 扫出

当 validate 的结果让 usesClientComposition 为真，Output::finishFrame（native/services/surfaceflinger/CompositionEngine/src/Output.cpp:1312）会先 dequeueRenderBuffer 拿到 client target，再调 composeSurfaces（1390）。composeSurfaces 生成 DisplaySettings 与每个 CLIENT layer 的 LayerSettings，命中 ClientCompositionRequestCache 就直接复用上个 buffer（1432-1445），否则调 RenderEngine::drawLayers（1471-1474）并 .get() 等它把命令提交完。RenderEngine 是线程化的：RenderEngineThreaded::drawLayers 把任务丢到 RE 线程并返回 future，SkiaRenderEngine::drawLayersInternal 把 ExternalTexture 包成 SkSurface、waitFence 后逐层 draw，最后 flushAndSubmit 产出一根 GPU fence 作为 ready fence。Output::finishFrame 用 mRenderSurface->queueBuffer(readyFence) 把 buffer 交出去，最终由 FramebufferSurface::advanceFrame 调 HWComposer::setClientTarget 成为 HWC 的 client target。这一拍的成本几乎全在 GPU 上，SF 主线程只负责准备与交接；因此排障时要同时看两条时间线：SF 侧的 dequeue、提交、queueBuffer，以及 GPU 侧的 fence 何时 signal。任何一条变长，下一帧都会更晚开始。这也是为什么 GPU 合成帧常常在 trace 上看着 SF 很快、整体却更慢。

什么时候真的要用 GPU

总开关是上一拍定下的 outputState.usesClientComposition（Display.cpp:306）。它一旦为真，Output::dequeueRenderBuffer（Output.cpp:1371-1388）才会去 mRenderSurface->dequeueBuffer(bufferFence)，失败时打 “Dequeuing buffer for display [%s] failed, bailing out of client composition for this frame” 并放弃本帧 GPU 合成。

调用点有两个：（1） 普通路径在 Output::finishFrame（1312-1349）：updateProtectedContentState → dequeueRenderBuffer → composeSurfaces → mRenderSurface->queueBuffer；（2） 预测路径在 Output::prepareFrameAsync（1225-1286）：它先把 validate 丢给 chooseCompositionStrategyAsync，同时按上一帧的 changes 提前 dequeue + compose，把结果放进 GpuCompositionResult（fence + 可复用的 buffer，见 CompositionEngine/include/compositionengine/impl/GpuCompositionResult.h:24-36）。预测命中时 finishFrame 直接复用 result.fence（1323-1324），省掉一次 dequeue 与一次完整 GPU 合成。

composeSurfaces 的输入与短路

Output::composeSurfaces（Output.cpp:1390-1509）开头三个判断决定了这一拍是否真的跑 GPU：

  1. hasClientComposition = outputState.usesClientComposition，为假时 setExpensiveRenderingExpected(false) 并直接返回空 fd（1397-1405）。这个 TracedOrdinal 会把名字渲染成 “hasClientComposition <display>”，在 trace 上一眼可辨。
  2. tex == nullptr（dequeue 失败）时打 “Buffer not valid for display [%s], bailing out of client composition for this frame” 并返回（1407-1412）。
  3. generateClientCompositionDisplaySettings(tex) 产出 renderengine::DisplaySettings（物理尺寸、clip、outputDataspace、maxLuminance 等），generateClientCompositionRequests(...) 产出 std::vector<LayerFE::LayerSettings> 并收集被 client 合成的 LayerFE*（1416-1427）。

短路点：若 mClientCompositionRequestCache 认为“同样的 buffer id + 同样的 DisplaySettings + 同样的 layer 请求”已经画过，就打 SFTRACE_NAME("ClientCompositionCacheHit")、置 outputCompositionState.reusedClientComposition = true，直接返回已有 buffer 的 fence（1432-1441），完全跳过 GPU。命中失败时打 "ClientCompositionCacheMiss" 并把本帧请求写进 cache（1442-1445）。

RenderEngine：一次跨线程的 GPU 合成

真正画之前，composeSurfaces 先算一次“贵不贵”（1451-1460）：有背景模糊的 layer、或任何一个 layer 的 sourceDataspace != outputDataspace（需要色彩空间转换），就 setExpensiveRenderingExpected(true)，注释说明这是为了让 GPU 提频、保证这帧能赶上 deadline。随后把 LayerFE::LayerSettings 转成 renderengine::LayerSettings（1462-1468），记录 renderEngineStart，调 renderEngine.drawLayers(clientCompositionDisplay, clientRenderEngineLayers, tex, std::move(fd)).get()（1470-1474）。

这里的 drawLayers 是 RenderEngineThreaded 的版本（native/libs/renderengine/threaded/RenderEngineThreaded.cpp:276-298）：它把 bufferFence 的 fd release 出来、把闭包塞进 mFunctionCalls 并 mCondition.notify_one()，返回一个 std::future<FenceResult>。真正干活在 RE 线程：SkiaRenderEngine::drawLayersInternal（skia/SkiaRenderEngine.cpp:885）里 getOrCreateBackendTexture(buffer->getBuffer(), true) 把 client target 包成后端纹理（925）、waitFence(context, bufferFence) 等这块 buffer 可用（928）、getOrCreateSurface(display.outputDataspace) 拿到 SkSurface（930），逐层 draw（含模糊、圆角、色彩转换），最后 flushAndSubmit(context, dstSurface) 得到 fence fd 并 resultPromise->set_value(std::move(drawFence))（1636-1648）。

所以 SF 主线程在 .get() 上等的是“RE 线程完成命令提交”，不是 GPU 执行完成；GPU 的完成由那根 fence 表示，交给后面的 HWC 去等。

GL 与 Vulkan 的边界在哪

SF 与 CompositionEngine 只认 RenderEngine 抽象：virtual ftl::Future<FenceResult> drawLayers(const DisplaySettings&, const std::vector<LayerSettings>&, const std::shared_ptr<ExternalTexture>&, base::unique_fd&&)（native/libs/renderengine/include/renderengine/RenderEngine.h:244）。后端在进程启动时选定：mRenderEngine = renderengine::RenderEngine::create(builder.build())（SurfaceFlinger.cpp:960），由 RenderEngine::create 里的 createInstanceFactory 决定是 GL/Ganesh、Vulkan/Ganesh 还是 Graphite。

差异只体现在 flushAndSubmit 的实现与 fence 产物上：SkiaGLRenderEngine::flushAndSubmit（skia/SkiaGLRenderEngine.cpp:353）与 GaneshVkRenderEngine::flushAndSubmit（skia/GaneshVkRenderEngine.cpp:86）各自返回 base::unique_fd 作为 GPU 完成 fence，再由 sp<Fence>::make(...) 包成 FenceResult（base::expected<sp<Fence>, status_t>，native/libs/ui/include/ui/FenceResult.h:27）。SF 侧代码不感知后端，唯一的可观测差异是 fence 类型（sync_file vs 驱动自有机制）以及 trace 里 RE 内部 slice 的形态。

另一个跨进程/跨进程边界的点：client target 的 AHardwareBuffer/GraphicBuffer 通过 ExternalTexture 交给 RE，若 RE 与应用不在同一进程（OOPR 场景），这层包装背后是真实的 buffer 共享而非拷贝；本阶段源码里没有内存拷贝路径。

client target 怎么变成 HWC 的输入

composeSurfaces 返回的 std::optional<base::unique_fd> 就是 client target 的 ready fence。Output::finishFrame 把它交给 mRenderSurface->queueBuffer(std::move(*optReadyFence), getHdrSdrRatio(buffer))（Output.cpp:1348）。RenderSurface::queueBuffer（CompositionEngine/src/RenderSurface.cpp:201-248）做两件事：

  1. 若 state.usesClientComposition || state.flipClientTarget，调 mNativeWindow->queueBuffer(mNativeWindow.get(), mTexture->getBuffer()->getNativeBuffer(), dup(readyFence))（223-225）把 buffer 交回这条显示内部 BufferQueue 的生产者侧；失败时对非虚拟屏直接 LOG_ALWAYS_FATAL（232）。
  2. 无论哪种情况都调 mDisplaySurface->advanceFrame(hdrSdrRatio)（244）。在 HWC 显示上这就是 FramebufferSurface::advanceFrame（DisplayHardware/FramebufferSurface.cpp:92-128）：mRendererConsumer->acquireBuffer(&item, 0, false, ...) 取回刚 queue 的 buffer（95），HwcSlotTracker::getSlot 决定要不要把 GraphicBuffer 重新下发（117-118），然后 mHwc.setClientTarget(mDisplayId, hwcSlot, item.mFence, hwcBuffer, mDataspace, hdrSdrRatio)（120-121）。

HWComposer::setClientTarget（DisplayHardware/HWComposer.cpp:525-535）只是转给 HWC2::Display::setClientTarget（DisplayHardware/HWC2.cpp:462-470），最终落到 Composer HAL 的 setClientTarget。这条内部 BufferQueue（BufferItemConsumer + Surface，FramebufferSurface.cpp:57-62）是 SF 自己的，与应用图层的 BLAST BufferQueue 无关，别把两者混在一起分析。

三根 fence 与同步语义

这一拍同时存在三根关键的 fence，方向各不相同：

  • bufferFence（进）：client target 上一次被使用后的 acquire fence，RenderSurface::dequeueBuffer 从 mNativeWindow->dequeueBuffer 拿到 fd（RenderSurface.cpp:156），一路传到 SkiaRenderEngine::drawLayersInternal 的 waitFence(context, bufferFence)（928）。RE 线程在这里阻塞，直到这块 buffer 真的可以被写。
  • draw fence（出）：flushAndSubmit 的产物（SkiaRenderEngine.cpp:1636），也就是 composeSurfaces 返回、queueBuffer 里 dup(readyFence) 交给 BufferQueue 的那根（RenderSurface.cpp:223-225），再作为 item.mFence 成为 HWC 的 client target acquire fence。
  • present fence（回）：HWC presentDisplay 之后由 Display::presentFrame 取回（CompositionEngine/src/Display.cpp:432-438），在 Output::presentFrameAndReleaseLayers（Output.cpp:1742-1784）里变成每个 layer 的 release fence；FramebufferSurface::onFrameCommitted 还会把它与上一帧的 acquire fence 合并（Fence::merge("FramebufferSurface-Acquire+Present", ...)，FramebufferSurface.cpp:135-142）后才 release buffer。

另外两处记账：TimeStats::recordRenderEngineDuration(renderEngineStart, FenceTime(fence))（Output.cpp:1495-1502）把 GPU 合成耗时记进 timestats；ADPF 打开时 setHintSessionGpuStart/setHintSessionGpuFence（1481-1493）把 GPU fence 报给调度器。每个被 client 合成的 layer 还会 setWasClientComposed(fence)（1504-1506），供上层查询它的完成状态。

排障：GPU 合成变慢或变多时看什么

  • GPU 合成比例异常：先看 validate 侧（上一拍）是否把该层改成了 CLIENT；再看 ClientCompositionCacheHit 是否消失——cache miss 增多意味着每帧都要重画。
  • SF 主线程卡在 .get()：composeSurfaces 里的 drawLayers(...).get() 在等 RE 线程，RE 线程又被 waitFence 卡住时，原因是 client target 的 bufferFence 太晚——往往来自上一帧 GPU 还没画完。
  • queueBuffer 直接 fatal：RenderSurface::queueBuffer 对非虚拟屏的失败是 LOG_ALWAYS_FATAL("ANativeWindow::queueBuffer failed with error: %d")（RenderSurface.cpp:232），线上表现为 SF 崩溃而不是掉帧。
  • 画面颜色/亮度不对：看 clientTargetProperty 指定的 dataspace 是否被正确应用到 DisplaySettings.outputDataspace，以及 RE 是否因此走了色彩转换（这会同时触发 expensiveRendering）。
  • 保护内容：updateProtectedContentState（Output.cpp:1351-1369）决定是否把 RenderSurface 设为 protected；若 RE 不支持保护内容，该路径会退化，表现为黑屏而非报错。

07present：HWC 提交与 fence 回传

SurfaceFlinger 主线程把这一拍交给 HWC：先 validate 拿到 composition 变更，再 present 拿到 present fence 与逐 layer release fence

本阶段是“这一帧终于被交给显示硬件”的一拍，发起者是 SurfaceFlinger 主线程：Scheduler::onFrameSignal 在 vsync 后依次调用 ICompositor::commit / composite（Scheduler.cpp:501），SurfaceFlinger::composite 里执行 mCompositionEngine->present(refreshArgs)（SurfaceFlinger.cpp:3448），再由 Output::presentFrameAndReleaseLayers（Output.cpp:1726）调用 Output::presentFrame（Output.cpp:1828；物理显示器的实现在 native/services/surfaceflinger/CompositionEngine/src/Display.cpp:416）。present 之前先 validate：Display::chooseCompositionStrategy → HWComposer::getDeviceCompositionChanges（HWComposer.cpp:537），HWC 可以合并成 presentOrValidate 一次往返，也可以分成 validate + present 两次。真正的展示调用是 HWComposer::presentAndGetReleaseFences（HWComposer.cpp:658）：先 sleep_until(earliestPresentTime) 避免过早呈现，再 hwcDisplay->present(&lastPresentFence) 拿到 present fence，随后 getReleaseFences 拿到每个 HWC layer 的 release fence。HWC HAL 之下的 DRM/KMS 提交与面板点亮不在 AOSP 树内，源码中未体现；这里是应用侧一切“present 时间”数据的源头。整段跑在 SF 主线程上，与 app 的 RenderThread 无关；线程若被 present 阻塞，下一拍的 vsync 处理会整体后移。

一、谁触发、在哪个线程、present 在链路里的位置

触发者是 vsync 之后的 SF 主循环：Scheduler::onFrameSignal()（native/services/surfaceflinger/Scheduler/Scheduler.cpp:411）先 compositor.commit() 把这一拍的事务合入 drawing state，再 compositor.composite()（Scheduler.cpp:501）。SurfaceFlinger::composite()（SurfaceFlinger.cpp:3330）组装 CompositionRefreshArgs 并调用 mCompositionEngine->present(refreshArgs)（SurfaceFlinger.cpp:3448）。

这一整段跑在 SurfaceFlinger 主线程上，与 app 侧的 RenderThread 完全无关：后者只负责把 buffer 用 Transaction 递进来（BLAST），latch 与合成都在这里发生。CompositionEngine::present() → 每个 output 的 Output::present() → presentFrameAndReleaseLayers()（native/services/surfaceflinger/CompositionEngine/src/Output.cpp:1726），函数体里先 auto frame = presentFrame()，再 mRenderSurface->onPresentDisplayCompleted() 释放 GPU 合成的 client target。

presentFrame() 是虚函数：基类 Output::presentFrame()（Output.cpp:1828）只填 clientTargetAcquireFence，物理显示器的实现是 compositionengine::impl::Display::presentFrame()（native/services/surfaceflinger/CompositionEngine/src/Display.cpp:416），它额外调用 hwc.presentAndGetReleaseFences() 并填充 presentFence 与 layerFences。这就是本阶段的边界：过了这一层就是 HWC HAL。

为什么 SF 自己不能直接写显存：HWC 是 vendor 实现，SF 只能通过 IComposer 下发 layer 组合（composition）与 present 命令，硬件是否走 overlay、是否做色彩管理、何时真正扫出这一帧，都由 HWC 与内核驱动决定。SF 侧能拿到的承诺只有两个 fence：present fence 与 per-layer release fence。

二、validate 与 present 是两个 HAL 往返，且可以合并

present 之前必须让 HWC 知道这一帧的 layer 组合：Display::chooseCompositionStrategy()（native/services/surfaceflinger/CompositionEngine/src/Display.cpp:248）调用 HWComposer::getDeviceCompositionChanges()（HWComposer.cpp:537）。后者先判断能否跳过 validate：若 HWC 不支持 expected present time、或当前时刻已过 earliestPresentTime，就允许 skip（HWComposer.cpp:562-577）。

能 skip 时走 hwcDisplay->presentOrValidate()：HWC 若返回 state == 1 表示“present 已顺便完成”，此时立刻 getReleaseFences、把 present fence 存进 displayData.lastPresentFence，并把 validateWasSkipped 置真（HWComposer.cpp:581-596）。后续 presentAndGetReleaseFences() 看到 validateWasSkipped 只执行 executeCommands() 然后返回，不会再 present 一次（HWComposer.cpp:668-675）。

不能 skip 时退回 hwcDisplay->validate()（HWC2.cpp:515），随后读 getChangedCompositionTypes / getRequests / getClientTargetProperty 并 acceptChanges()（HWComposer.cpp:608-631）。也就是说一帧可能有两次 HAL 往返（validate + present），也可能是合并的一次——trace 上要按 HwcValidateDisplay 与 HwcPresentDisplay 两个 slice 区分。

三、present 那一次调用做了什么

HWComposer::presentAndGetReleaseFences()（HWComposer.cpp:658）有三段：第一段，若 validateWasSkipped 为真，只 executeCommands() 刷掉挂起的 HWC 命令并回报 presentError；第二段，若有 earliestPresentTime，std::this_thread::sleep_until() 显式睡到该时刻（HWComposer.cpp:676-679），这是 SF 侧唯一一处主动阻塞；第三段，hwcDisplay->present(&displayData.lastPresentFence) 拿 present fence，再 getReleaseFences(&releaseFences) 拿每层 release fence，并整体替换 displayData.releaseFences。

HWC2::Display::present()（HWC2.cpp:413）只是把 mComposer.presentDisplay(mId, &presentFenceFd) 的 int32 错误码转成 hal::Error，再把 fd 包成 sp<Fence>；真正跨进 HAL 的是 AidlComposer::presentDisplay()（AidlComposerHal.cpp:748）：持共享锁、writer->get().presentDisplay(displayId) 写命令、execute(display) 下发给 composer HAL、最后 reader->get().takePresentFence(displayId) 取回 fd 并移交所有权。

因此 present fence 的所有权链是：HWC service 创建 fd → AidlComposer 取回并置 -1 表示已接管 → HWC2::Display 包 Fence → HWComposer 存 DisplayData::lastPresentFence → Display::presentFrame 读出后放进 FrameFences::presentFence。之后 HWComposer::clearReleaseFences() 清空逐层表，防止下一帧误用旧 fence。

阻塞语义要分清：源码里唯一显式阻塞是 sleep_until(earliestPresentTime)；presentDisplay() 这个 HAL 调用本身是否阻塞在上一帧 present fence 上，取决于 vendor HWC 实现，源码中未体现。所以 trace 上 present 很慢时，先看是 sleep 还是 HAL。

顺带说明 FrameFences::clientTargetAcquireFence 的来源：只有 usesClientComposition 为真（有 layer 需要 GPU 合成）时才从 mRenderSurface->getClientTargetAcquireFence() 取，代表 RenderEngine 画完 client target 的 acquire fence；device composition 全 HWC 时它是 NO_FENCE。

四、HWC 以下的边界：DRM/KMS、面板与 fence 类型

HWC HAL 之下是 vendor 的 display driver（DRM/KMS、DSI 等），AOSP 树里没有这部分实现：AidlComposer::presentDisplay() 之后只通过 execute(display) 把命令下发到 IComposer service，再由 service 与内核交互，源码中未体现具体提交方式。可验证的边界就是 present fence 这个 fd：它由 HWC service 生成，signal 表示“这一帧已经被硬件接收并将在下一个刷新周期点亮”。

present fence 与 release fence 是两种东西：lastPresentFence 只有一个、代表整帧上屏；releaseFences 是 HWC2::Layer* → sp<Fence> 的映射，代表“该 layer 的上一块 buffer 何时可以还给生产者”。它们都由 HWC 在 present 时一起交出，但 signal 时刻不同——release fence 晚于（或等于）present fence。

“retire fence”在本版本的 HWC2/AIDL 接口里没有对应 API：HWComposer.h:557 只在注释里把 lastPresentFence 描述为 “signals when the last set op retires”，LegacyFramebufferSurface.h:108 还留着 HWC1 时代的 retire fence 注释。GPU 合成时 client target buffer 的“退役”是用 present fence 与 acquire fence 合并表达的（FramebufferSurface.cpp:130-148，Fence::merge("FramebufferSurface-Acquire+Present", ...)），这部分留给 stage-08 展开。

面板侧的另一个边界是刷新率与 present 目标的匹配：SF 把 expectedPresentTime 与 frameInterval 一并传给 validate（HWComposer.cpp:584-592），HWC 用它们决定“这一帧是否已经太晚、要不要推迟到下一个刷新周期”。如果模式切换或 doze 导致 interval 变化，validate/present 的时序判断也会随之改变。

五、观测手段与排障入口

Perfetto 上先看 SF 主线程的三个 slice：Composition（SurfaceFlinger::composite 的 async track）、HWComposer::presentAndGetReleaseFences（函数名 SFTRACE_CALL）、wait for earliest present time（HWComposer.cpp:677）。若 present 慢但 sleep 很短，问题在 HWC HAL；若 sleep 很久，说明 SF 把这一帧刻意推迟到 earliestPresentTime。

HAL 侧有 HwcPresentDisplay <id>（AidlComposerHal.cpp:750）与 HwcValidateDisplay / HwcPresentOrValidateDisplay（同文件 884/915）三个 slice，配合 NextFrameInterval <n>_Hz（HWComposer.cpp:580）可以确认这一帧的预期刷新率与是否走了 skip-validate。

dumpsys 侧：adb shell dumpsys SurfaceFlinger 的 display 段会打印 HWC 的 present fence 时间与 HW_VSYNC_* counter；dumpsys SurfaceFlinger --latency 给出 desired/actual present 直方图；adb shell dumpsys SurfaceFlinger --displaysync（若编译开启）可看 vsync 配置。property service.sf.present_timestamp 反映 present 时间是否来自可信 fence（SurfaceFlinger.cpp:1125）。

六、常见误解

误解一：present 返回就代表上屏。present fence 只是 HWC 给出的“将在下一次刷新点亮”的承诺，真正的点亮时刻是 fence signal 时间；presentAndGetReleaseFences() 返回时 fence 往往还没 signal。

误解二：一次 composite 必然对应一次 present HAL 调用。validateWasSkipped 为真时 present 已在 validate 阶段完成，本阶段的函数只 executeCommands；这种“合并往返”在 trace 上表现为没有 HwcPresentDisplay 而只有 HwcPresentOrValidateDisplay。

误解三：release fence 越早越好。HWC 的 release fence 必须等该 buffer 不再被 display 读取，提前 release 会让生产者覆写正在扫描的 buffer，表现为撕裂或花屏。

一、present 之后发生了什么：一次同步的收尾

SurfaceFlinger::composite() 里 present 调用返回后还要做一串收尾：记 mCompositionCoverage、mScheduler->onCompositionPresented(presentTime)（可能立刻 schedule 下一拍）、然后 onCompositionPresented(pacesetterId, frameTargeters, presentTime)（SurfaceFlinger.cpp:3517-3522）。注意这里是同步调用，不是 post 到别的线程，所以 present fence 的分发与 composition 收尾都在 SF 主线程的同一段代码里完成。

onCompositionPresented()（SurfaceFlinger.cpp:3775）开头遍历 frameTargeters：对每个 display getHwComposer().getPresentFence(id)（stage-07 存的 lastPresentFence），对 pacesetter 调 mTransactionCallbackInvoker.addPresentFence(presentFence)（SF:3787）。这一步决定了应用侧 TransactionCompletedListener 最终拿到的 presentFence 是哪一个。

接着 targeter->setPresentFence(std::move(presentFence)) 把 fence 交给 Scheduler 的 FrameTargeter（用于 follower display 背压判断与 present latency 统计），若 fence 有效就放进 presentFences map。最后 mFrameTimeline->setSfPresent(...)（SF:3822）交给 FrameTimeline。

还有一个容易被忽略的细节：onCompositionPresented() 的第三个形参 presentStartTime 在函数体里一次都没有被使用（grep 函数体只能命中签名行），真正的 presentTime 是函数内部 TimePoint::now() 取的（SF:3817）。因此 FrameTimeline 的 SF actual end time 反映的是“收尾这一刻”，而不是 composite 进入时刻。

二、present fence 的三种状态与分类

第一类是可靠 present fence：mHasReliablePresentFences = !getHwComposer().hasCapability(Capability::PRESENT_FENCE_IS_NOT_RELIABLE)（SurfaceFlinger.cpp:983-984），并写进 property service.sf.present_timestamp（SF:1125）。为真时 presentLatency = mPresentLatencyTracker.trackPendingFrame(compositeTime, pacesetterPresentFenceTime)（SF:3830-3832），CompositorTiming 里带上实测 present latency。

第二类是 HWC 声明不可靠：此时 presentFence 可能是 NO_FENCE 或不可信，SF 在 Layer::onCompositionPresented() 里退回 getPresentTimestamp()，并用 now - ((now - presentTimestamp) % vsyncPeriod) 把时间戳吸附到 vsync 网格上（Layer.cpp:1478-1499），再 mTimeStats->setPresentTime。

第三类是 fence 有效但尚未 signal：setSfPresent 照常把它压进 mPendingPresentFences，等到之后某一拍 flushPendingPresentFences() 发现它已 signal 才真正结算（FrameTimeline.cpp:2095-2143）。这就是 FrameTimeline 滞后的机制来源。

还要区分 present fence 与 GPU composition done fence：gpuCompositionDoneFences 只在 display->getState().usesClientComposition 为真时取 renderSurface->getClientTargetAcquireFence()（SF:3795-3800），它代表 RenderEngine 画完 client target 的时刻，与整帧 present 不是一回事。

addPresentFence 只是登记：application 侧的 presentFence 要等到 SF 下一轮 TransactionCallbackInvoker::sendCallbacks() 才随 transactionStats.presentFence 发出去（RT 文档 stage-09 已从客户端角度讲过），本阶段只负责把 pacesetter 的那个 fence 放进 invoker，避免多 display 时 app 拿到 follower 的 fence。

三、FrameTimeline：请求-实际两套时间线与滑动窗口

FrameTimeline::setSfPresent()（FrameTimeline.cpp:1420）只做四件事：setActualEndTime(sfPresentTime)、setGpuFence(gpuFence)、把 (presentFence, mCurrentDisplayFrame) emplace_back 进 mPendingPresentFences、flushPendingPresentFences()，最后 finalizeCurrentDisplayFrame()。

finalizeCurrentDisplayFrame()（FrameTimeline.cpp:2145）维护一个 mMaxDisplayFrames 大小的 mDisplayFrames 滑动窗口（FrameTimeline.h:672/681，默认 64 帧），超窗就 pop_front，然后为下一拍新建 DisplayFrame。所以同一个 present fence 的结算可能要等好几拍，历史帧才被丢弃。

flushPendingPresentFences() 的核心是顺序假设：present fence 按提交顺序 signal。它先找第一个已 signal 的索引 getFirstSignalFenceIndex()（FrameTimeline.cpp:2084）；该索引之前的 pending fence 一律当作错误，用 Fence::SIGNAL_TIME_INVALID 结算；从该索引开始逐个 SurfaceFrame::onPresent(signalTime, ...) 并 trace(...)，遇到 PENDING 立即 break。这保证了 FrameTimeline 的 present 时间单调递增。

四、retire：buffer 什么时候真的可以还给生产者

present fence signal 意味着这一帧已经被硬件接收，但某个 layer 的旧 buffer 是否还能被覆写，取决于该 layer 的 release fence。对 HWC device composition，release fence 由 getReleaseFences() 给出，经 FrameFences::layerFences 传到 Output::presentFrameAndReleaseLayers()，逐个 layer->getLayerFE().setReleaseFence(releaseFence)（Output.cpp:1747-1785）。

对 GPU composition，client target buffer 的“退役”需要同时等 acquire fence 与 present fence：FramebufferSurface::onFrameCommitted()（FramebufferSurface.cpp:130-149）用 Fence::merge("FramebufferSurface-Acquire+Present", mPreviousFrameData->mFence, mHwc.getPresentFence(mDisplayId)) 合成一个 fence 再 releaseBuffer。这正是“retire fence”的现代表达方式。

调用链是 Output::presentFrameAndReleaseLayers() 里 mRenderSurface->onPresentDisplayCompleted()（Output.cpp:1744）→ RenderSurface::onPresentDisplayCompleted()（RenderSurface.cpp:250-252）→ mDisplaySurface->onFrameCommitted() → FramebufferSurface::onFrameCommitted()。注意它只释放上一帧的 FrameData，当前帧要等下一帧 present 后才退役。

本版本 HWC2/AIDL HAL 没有 retire fence API：HWComposer.h:557 的注释把 lastPresentFence 描述为 “signals when the last set op retires”，说明 retire 语义已经并入 present fence；HWC1 时代的 retire fence 只剩 LegacyFramebufferSurface.h:108 这类历史注释，源码中未体现对应 HAL 接口。

虚拟显示走另一条路：VirtualDisplaySurface::onFrameCommitted()（native/services/surfaceflinger/DisplayHardware/VirtualDisplay/VirtualDisplaySurface.cpp:306）在 GPU display 或 CompositionType::Gpu 时直接 return（GPU 合成在 onRenderFrameAvailable 里已经完成），否则用 mHWC.getPresentFence(halDisplayId) 并把 render buffer 的 acquire fence 与 present fence Fence::merge("VD Render Acquire/Present", ...) 后再 releaseBuffer（同文件 325-340）——与 FramebufferSurface 的物理屏 retire 逻辑同构。

六、常见误解

误解一：setSfPresent() 之后 FrameTimeline 就有这一帧的 present 时间。实际要等 fence signal 且被后续一次 flush 处理；setSfPresent 只负责入队与封存 display frame。

误解二：present fence 的顺序一定与提交顺序一致。代码明确假设一致，并把“先提交却后 signal”的 fence 当错误处理（SIGNAL_TIME_INVALID），这种情况下 FrameTimeline 上会出现 present 时间为 invalid 的帧。

误解三：retire fence 是独立对象。本版本只有 present fence + release fence，GPU 合成时二者被 Fence::merge 合并后才用于释放 client target，不要假设存在 HAL 级 retireFence。

误解四：mFrameTimeline 与 JankTracker 是一回事。前者负责时间线与分类（DisplayFrame/SurfaceFrame、expected vs actual），后者只是把已分类的 gui::JankData 按 listener 分发出去；两者由 SurfaceFrame::onPresent() 串起来，但生命周期与线程都不同。

一、release 的两条路：binder 回调与 fd 通道

Layer::callReleaseBufferCallback()（Layer.cpp:711）是 SF 通知客户端“某块 buffer 可以还了”的唯一出口，但它内部有两条并行的路径：listener->onReleaseBuffer(callbackId, fence, currentMaxAcquiredBufferCount, false)（Layer.cpp:731-733）走 ITransactionCompletedListener binder；mBufferReleaseChannel->writeReleaseFence(callbackId, fence, currentMaxAcquiredBufferCount)（Layer.cpp:738-739）走共享内存/fd 通道。

为什么两条都要走：前者兼容旧客户端（app 的 TransactionCompletedListener::onReleaseBuffer 直接回调 Java/Kotlin 层），后者是 BLAST 时代为降低 binder 压力新增的通道，BLAST 在 dequeue 里直接 epoll 读它，不必等 binder 线程。任何只观察其中一条的排障都会漏掉另一半。

进入函数先做两个短路：if (!listener && !mBufferReleaseChannel) return;（Layer.cpp:714-716），说明没有注册监听也没有通道时静默返回；releaseFence 为空时用 Fence::NO_FENCE（Layer.cpp:721）。随后用 ReleaseCallbackId{buffer->getId(), framenumber} 组装回调标识，并从 SF 拿 currentMaxAcquiredBufferCount = mFlinger->getMaxAcquiredBufferCountForCurrentRefreshRate(mOwnerUid)（Layer.cpp:722-723，实现于 SurfaceFlinger.cpp:9338）。

这个 count 是 BLAST 侧决定“扣住几块 buffer 再还”的输入：SF 在低刷新率时会调低它，让 BLAST 多扣几块以避免延迟上升。也就是说 release 的节奏不是恒定的，会随刷新率与 ownerUid 的策略变化。

两个通道的失败模式也不同：binder 路径受 app 的 Binder 线程池与回调执行时长影响，channel 路径受 SELinux（fd 传递）与 epoll 唤醒影响。SF 侧 writeReleaseFence 失败只打 ALOGD（Layer.cpp:742-756），不会重试，因此 channel 一旦失效，只能靠 binder 路径兜底。

二、从 present 到 release：谁在什么时机调用它

调用点有三类。第一类是 Layer::onCompositionPresented() 之后紧跟着的 Layer::releasePendingBuffer()（Layer.cpp:814）：它把 mDrawingState.callbackHandles 补上 bufferReleaseChannel、transformHint、cornerRadii、dequeueReadyTime、currentMaxAcquiredBufferCount（Layer.cpp:815-822），然后 mFlinger->getTransactionCallbackInvoker().addCallbackHandles(...) 并清空（Layer.cpp:833-836）。

第二类是 buffer 被提前替换或 layer 销毁：Layer::releasePreviousBuffer() 在新 buffer 到来但旧 buffer 还没 presented 时直接 callReleaseBufferCallback（Layer.cpp:862-874），Layer::~Layer() 里也会调一次（Layer.cpp:172-176）——注释说明析构时收到 EPIPE/ECONNRESET 是预期行为，不要当错误报警。

第三类是异步截图/WebView 等旁路（SurfaceFlinger.cpp:8344 的 attachReleaseFenceFutureToLayer、MergeableHierarchy.cpp:110），它们用 prepareReleaseCallbacks(ftl::Future<FenceResult>, layerStack) 把未来才产生的 fence 先登记到 CallbackHandle，等 fence 就绪再回填。

真正写回应用的时机在 TransactionCallbackInvoker::sendCallbacks()：它先把 mBufferReleases 里的 fence 写入各自的 BufferReleaseChannel（TransactionCallbackInvoker.cpp:158-170），再按 ON_COMMIT / ON_COMPLETE 分发事务回调；ON_COMPLETE 分支里若 surfaceStats.previousReleaseCallbackId 有效，还会顺手把客户端的 release 回调在同一轮 IPC 里执行掉。

releasePendingBuffer 之所以把 dequeueReadyTime 一起填进 handle，是因为应用侧要用它计算“这块 buffer 从 dequeue 到可再次 dequeue”的真实周期（BLAST 的 dequeueTime 会随 setBuffer 进 Transaction，最终出现在 SF 的 SurfaceControlStats 统计里）。

三、应用侧：dequeue 阻塞如何被 release 唤醒

BLAST 的 BufferQueue 在应用进程内，dequeue 找不到 free slot 时会进 BBQBufferQueueProducer::waitForBufferRelease()（BLASTBufferQueue.cpp:1302）：它先 mBufferReleaseReader->clearInterrupts()，再 UnlockGuard 释放 BufferQueue 锁，然后才 readBlocking() 等 release channel 的数据——这个“先清中断再解锁”的顺序是关键，否则会漏掉解锁瞬间到达的 release。

读到 release 后它调 bbq->releaseBufferCallback(id, fence, maxAcquiredBufferCount)，再调 getWaitForBufferReleaseCallback() 把本次阻塞时长报给 Choreographer（用于 buffer stuffing 恢复，见 RT 文档 stage-07/09 的 onWaitForBufferRelease），最后返回 OK 让 BufferQueueProducer 重新检查 free slot。

真正把 slot 变 free 的是 BufferQueueConsumer::releaseBuffer()（BufferQueueConsumer.cpp:509）：校验 slot 仍在 acquired 状态、mSlots[slot].mFence = releaseFence、mBufferState.release()，把 slot 从 mActiveBuffers 移到 mFreeBuffers，然后 mCore->notifyBufferReleased() 在锁内唤醒等锁者；listener->onBufferReleased() 特意放在解锁之后调用，避免生产者回调进来再次加锁造成死锁（BufferQueueConsumer.cpp:587-589）。

所以一次完整的“buffer 回流”是：SF present → release fence → callReleaseBufferCallback → (binder / channel) → BLAST waitForBufferRelease → releaseBufferCallback → BufferQueueConsumer::releaseBuffer → onBufferReleased → BufferQueueProducer 的 dequeue 返回。任何一环慢，都会表现为应用侧 dequeue 变长、甚至 SkippedFrameReason::NoBuffer。

还有一处容易忽略的顺序：notifyBufferReleased() 在 BufferQueue 锁内唤醒等锁者，而 onBufferReleased() 在解锁后调用；如果生产者监听器同步回调进 BufferQueue（比如直接 dequeue），就依赖这个“锁外回调”的约定，否则会自死锁。

四、jank 闭环：FrameTimeline 分类 + JankTracker 分发

present 结算后 SurfaceFrame::onPresent()（FrameTimeline.cpp:1052）被调用：它把 mActuals.presentTime 写好，调 classifyJankLocked(...) 得到 jank type 与 deadline/present 偏差，再用 calculateJankSeverity(...) 算出 mJankSeverity/mJankScore，然后 mTimeStats->incrementJankyFrames(...) 累加到 dumpsys 统计，并组装 gui::JankData（frameVsyncId、jankTypeLegacy/Experimental、presentDelayNs、jankScore、scheduled/actual app frame time）。

分发只在 mPredictionState != PredictionState::None 时发生（FrameTimeline.cpp:1071-1072）：也就是说没有 vsync prediction 的帧只做统计、不产生 JankData。JankTracker::onJankData()（native/services/surfaceflinger/Jank/JankTracker.cpp:62）在没有注册 listener（sListenerCount == 0）时直接返回，否则通过低优先级 BackgroundExecutor 投递，按 layerId 找到 listener 才入队缓存。

这条链解释了“FrameTimeline 数据滞后一拍到数拍”的完整原因：SF present → setSfPresent 入队 → 后续某拍 fence signal 后 flushPendingPresentFences 结算 → SurfaceFrame::onPresent 分类 → JankTracker 分发 → 应用侧的 FrameTimeline/JankData 回调。每一段都可能跨一个 vsync。

注意 SF 侧 jank 的“迟到”不是 bug：finalizeCurrentDisplayFrame() 在 setSfPresent 结尾就把 display frame 封存了，present 时间只能后续补；而 mDisplayFrames 只保留 64 帧（FrameTimeline.h:681），查询太久远的数据本来就查不到。

jank 分类的输入里 displayFrameJankTypeLegacy 与 Experimental 两套是并存的：classifyJankLocked 用 display frame 的判定结果作为基础，再叠加本 surface frame 自己的 deadline/present 偏差；最终 gui::JankData 同时携带 legacy 与 experimental 两个字段供不同版本的采样工具读取。

六、常见误解

误解一：release 回调只走 binder。实际上 callReleaseBufferCallback 同时写 channel，BLAST 优先走 channel；只 hook binder 会看到“回调没来”的假象。

误解二：release fence 一定非空。releaseFence 为空时用 Fence::NO_FENCE，buffer 立即可复用；把它当同步点会误判时序。

误解三：buffer 释放后应用立刻能 dequeue。BLAST 的 mPendingRelease 还会按 currentMaxAcquiredBufferCount 扣住若干块，且 producer throttling 与 BufferQueue 的 free list 水位都会影响实际可用时机。

误解四：jank 数据实时可得。FrameTimeline 要等 present fence signal 才结算，JankTracker 还要等 listener 注册，应用在帧刚画完时问“这帧 jank 了吗”永远拿不到答案。

03 / COMPOSITION PATHS

HWC overlay，还是 GPU client composition？

commit 之后的 Composite 阶段，CompositionEngine 把图层组织成 OutputLayer，然后让 HWC 选择每个图层的合成方式。 能直接 scanout 的图层走 device composition（overlay）；HWC 不支持的图层集合需要 RenderEngine 先画到 client target。

VALIDATE → COMPOSE → PRESENT
DEVICE vs CLIENT

Device composition（HWC overlay）

  • HWC 直接把图层 buffer 叠到显示硬件；SF 不必把整屏画到 GPU target。
  • 路径：chooseCompositionStrategy → getDeviceCompositionChanges / HWC2::Display::validate → presentDisplay。
  • 通常最快，但受图层数量、格式、缩放、HDR、保护内容等限制。
  • 失败/不支持时回退到 client composition。

GPU client composition

  • CompositionEngine 让 RenderEngine 先在一个 client target 上合成图层。
  • 路径：Output::composeSurfaces → RenderEngine::drawLayers → setClientTarget → present。
  • GPU 合成耗时直接加在 present 之前，是 SF jank 的常见来源。
  • 合成完成后仍需 HWC present；不是“画完就上屏”。

ALayerSnapshot：commit 的只读产物

commit 把事务应用到 mDrawingState，生成只读 LayerSnapshot 供 composite 使用。这样合成决策与 HWC 交互不必回读可变的 layer 状态。

Bacquire fence 决定能不能 latch

buffer 到达不代表可以合成；Layer::latchBufferImpl 必须等 acquire fence signaled。fence 未到，SF 不会阻塞等待，而是跳过这一帧并请求下一次合成。

Cpresent 之后还有很长的异步尾巴

presentDisplay 返回不代表像素已可见；present fence 决定上屏，retire fence 决定扫描完成，buffer release 才能回到 producer。FrameTimeline 把这些信号串成端到端时间线。

把 GPU 合成放进时间轴：打开慢帧演示，观察 RenderEngine client composition 变慢后越过 8.3ms SF 预算、present 晚于 16.7ms，本帧只等下一个 HW VSYNC。
