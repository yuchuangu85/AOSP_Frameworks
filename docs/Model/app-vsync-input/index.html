01 / FRAME ORDER

L1199–1211

先修正一个常见误解：INPUT 是 Choreographer 的第一个 callback 阶段，但所有输入并不是等到这个阶段才首次进入 APP。普通 fd 事件可能即时分发；批量 MotionEvent 通常在 CALLBACK_INPUT 以 frameTimeNanos 为边界消费。

INPUT：把输入处理结果交给 APP

INPUT 阶段不执行 View 的 measure/layout/draw。它处理事件队列并调用 ViewRootImpl 的输入分发入口，APP 代码可以在监听器和 View 回调中修改状态、启动动画或请求后续绘制。

当前证据Choreographer 标记 input handling start，然后调用 CALLBACK_INPUT。边界CALLBACK_INPUT 是批量输入的帧边界，不是全部输入的唯一入口。
关键结论：INPUT 完成只代表事件链返回 handled；即使 APP 调用了 invalidate，真正的新像素仍要经过 TRAVERSAL、RenderThread、GPU、BufferQueue 和下游显示路径。
02 / TWO INPUT ENTRANCES

普通输入和批量输入走两条入口

InputEventReceiver.cpp
L418–635 · ViewRootImpl.java L11453–11541

入口 A：InputChannel fd 可读，可能即时分发

NativeInputEventReceiver.handleEvent() 以 consumeBatches=false、frameTime=-1 消费。KeyEvent、非批量 MotionEvent 等转成 Java InputEvent 后调用 dispatchInputEvent，进入 WindowInputEventReceiver.onInputEvent() 和 processRawInputEvent()。它可能发生在 VSYNC 之前。

fd readable → Native consume(false)
dispatchInputEvent → WindowInputEventReceiver
processRawInputEvent → enqueueInputEvent

入口 B：批量 MotionEvent，通常对齐下一次 VSYNC

Native 发现 pending batch 时回调 onBatchedInputEventPending。普通路径注册 Choreographer CALLBACK_INPUT；下一次 doFrame 的 INPUT 阶段调用 consumeBatchedInputEvents(frameTimeNanos)，再处理 ViewRootImpl 队列。

pending batch → onBatchedInputEventPending
scheduleConsumeBatchedInput → CALLBACK_INPUT
consume(true, frameTime) → doProcessInputEvents
unbuffered 分支：如果 View 或 APP 请求 unbuffered input，ViewRootImpl 会取消批量调度并调用 consumeBatchedInputEvents(-1)，不等下一次 VSYNC。

05 / APP EFFECTS

APP 在 INPUT 回调里实际可以做什么

框架调用顺序确定
APP 内部副作用由代码决定

改变交互状态

onTouch、onKey、onClick 可以修改 ViewModel、选中态、焦点、滚动位置、文本或业务状态。performClick() 还会触发点击音效、OnClickListener、无障碍和 Autofill 通知。

请求重绘

invalidate() 设置 DIRTY / INVALIDATED 标记，并把 damage 向父 View 传播。它通常影响后续 Draw/DisplayList，不等于立即写屏幕像素。

请求布局或启动动画

requestLayout() 设置 FORCE_LAYOUT 并向父链传播；postOnAnimation() 或 Animator 注册后续 ANIMATION 回调。两条路径不要和 invalidate 混为一谈。

07 / BOUNDARIES

三个“完成”不是同一个完成

INPUT 完成

ViewRootImpl 返回 handled / not handled，并完成 InputEventReceiver 回传。它证明事件链结束。

TRAVERSAL 完成

APP 可能完成 measure、layout、DisplayList 录制，并把工作交给 RenderThread。它仍不等于 GPU 已完成。

显示完成

还要经过 buffer queue、BLAST、SF latch、合成、HWC present 和 fence。源码不能直接证明面板某一行何时发光。
