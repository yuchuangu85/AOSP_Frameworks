ANDROID 17 · SOURCE-BACKED FRAME EXPLAINER

App VSYNC 后，ANIMATION 到底做了什么？

动画不是“每帧自动移动 View”。源码真正做的是：按帧时钟唤醒到期动画，求出当前值，再由不同 Animator 把值写入监听器、对象属性或 ViewPropertyAnimator 的目标。

源码快照：24bc82b5d主线：Choreographer / AnimationHandler / ValueAnimator范围：普通 UI-thread 动画与 View 属性
01 / FRAME ORDER

ANIMATION 位于 INPUT 之后、TRAVERSAL 之前

Choreographer.java
L1199–1211

同一个 doFrame 中，Choreographer 先跑 INPUT，再标记动画阶段并执行 CALLBACK_ANIMATION，随后才进入 INSETS_ANIMATION 和 TRAVERSAL。输入回调中启动的动画，可能在同一个 doFrame 的后续 ANIMATION 阶段被处理，前提是回调已到期并进入 AnimationHandler。

ANIMATION：只负责推进动画状态，不负责把像素送到屏幕

AnimationHandler 使用 Choreographer 的帧回调作为时钟。每次 pulse 收到 frameTime 后，遍历已注册的 AnimationFrameCallback，只调用已过 start delay 的动画。动画回调内部才计算 fraction、插值和目标值。

当前证据Choreographer 在 CALLBACK_ANIMATION 前调用 markAnimationsStart。重要边界动画值更新、View 属性变化、GPU 完成、屏幕 present 是不同事件。
核心结论：ANIMATION 完成后，APP 只是拿到了本帧的动画值。这个值是否触发 invalidate、requestLayout、RenderNode 更新，以及何时进入 GPU，要看具体 Animator 和属性 setter。

ValueAnimator 主要提供时间和值。它不会知道你的 ViewModel、View 或业务对象应该如何更新，除非 APP 注册 listener 或使用 ObjectAnimator 等目标型 Animator。

05 / APP EFFECTS

APP 在动画回调里实际可以做什么

动画更新不是显示完成

更新业务数据

APP 可以在 AnimatorUpdateListener 中更新 ViewModel、进度、计数器或自定义渲染状态。监听器执行在动画所属的 App UI Looper 上。

更新绘制属性

修改 alpha、translation、rotation、scale 等属性，通常走 View/RenderNode 的绘制属性路径；它不等于重新 measure/layout。

更新布局属性

如果每帧修改 LayoutParams、尺寸或父约束，可能触发 requestLayout，导致后续 Traversal 进入 measure/layout。

不要混淆：动画正在运行、动画值已更新、View 属性已写入、Traversal 完成、GPU 完成、屏幕已显示，都是不同状态。

07 / BOUNDARIES

四个“完成”不是同一个完成

动画 pulse 完成

AnimationFrameCallback 已被调用，ValueAnimator 可能更新了 fraction 和监听器。

属性更新完成

ObjectAnimator 或 ViewPropertyAnimator 已调用目标 setter；属性可能进入 RenderNode 或布局请求路径。

Traversal 完成

后续 View 树可能完成 measure、layout、draw 或 DisplayList 录制；仍不等于 GPU 完成。

显示完成

还要经过 RenderThread、GPU、BufferQueue、SF、HWC 和 present fence。
