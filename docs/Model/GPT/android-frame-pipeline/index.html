    Read the model correctly

    先建立这些正确的心智模型

    • 调度不是绘制：invalidate / requestLayout 通常只标记状态、合并请求并安排 traversal，不会立即把像素画到屏幕。
    • UI、RT、GPU 是不同执行者：RenderThread 是应用进程里的原生线程，不是独立进程。UI 可在同步完成后继续工作，GPU 仍可异步运行。
    • VSync 不止一种视角：硬件节拍校准预测模型；APP 和 SF 的软件唤醒有不同工作预算与时相。它们不必同时到达，也不是一个方法逐层转发。
    • 现代普通窗口经过 BLAST：应用侧消费 BufferQueue，再通过 SurfaceControl 事务把 GraphicBuffer 与 fence 交给 SF；不要照搬旧版 SF 直接作为应用 BQ consumer 的图。
    • 生产、就绪、呈现是三件事：queueBuffer 可携带尚未 signal 的 fence。SF/HWC 收到新 buffer 也不代表屏幕已切换。
    • 流水线跨帧重叠：图中聚焦 F，其生产期间屏幕仍显示 F−1。实际还可能同时准备 F+1，延迟不固定为一或两个刷新周期。

    边界、分支与常见问题

    为什么仅 invalidate 可能没有 measure / layout？

    尺寸和位置不变时，主要是失效区域 / RenderNode 内容更新。只有布局请求、窗口大小变化等需要时才重测重排。完整场景显式包含 requestLayout 和内容变化，不把“刷新”误当成每次必经三遍历。

    所有 View 每帧都会重新执行 onDraw 吗？

    不会。硬件加速保留 RenderNode / DisplayList；未变的子树可复用。translation、alpha 等属性更新还可能只改变渲染属性，RenderThread 动画也可不逐帧唤醒 UI。本模型选择内容失效的普通 View 分支。

    三缓冲、16.67ms、扫描方向是固定的吗？

    都不是。槽位数量和背压策略由实现 / 配置决定；16.67ms 只是 60Hz 的周期；90/120Hz、VRR 与帧率覆盖会改变预算。扫描采用从上到下的教学抽象，真实面板方向、传输、响应时间及 present fence 语义依设备而异。

    为什么 GPU 晚完成会错过一帧，而不是立即阻塞 SF？

    该场景选择“acquire fence 未就绪，当前轮不 latch”的保守分支。当前源码也存在受配置约束的 latch-unsignaled 优化；某些路径可传递未就绪 fence 给下游。不能把该动画当成所有设备的唯一等待策略。

    Commit、frame complete、present fence 有什么区别？

    Choreographer CALLBACK_COMMIT 是同一次 doFrame 的最后一类回调。HWUI 提交 / frame complete 回调描述各自 CPU/GPU 阶段；SurfaceControl 的提交与完成通知也各有语义。present fence 表达 HAL 的呈现时序，release fence 约束 buffer 何时可安全复用，均不等于所有像素已被人眼看见。

    这里没有展开哪些路径？

    窗口创建 / WMS relayout 与首次 Surface 分配只在说明中涉及，不按每帧固定步骤演出；不展开软件 Canvas、SurfaceView 独立 Surface、TextureView、视频解码、受保护内容、多屏 / 镜像、截图、HWC 厂商内部驱动及面板电气细节。它们不是不存在，而是不属于选定的普通硬件加速 View 主线。
