普通窗口中的 100 个 View 通常仍画入同一个窗口 buffer；SF 看到的是 Window 对应的 Layer 和 buffer，不会重新调用每个 View 的 onDraw。

三个“完成”边界
APP / RT 完成DisplayList、RenderNode 和 GPU buffer 生产工作已推进。
SF latch 完成Layer 选择并采纳某个 buffer；不等于已合成或已显示。
present fence 完成框架取得显示提交依赖；不等于面板每个像素同时发光。
release 完成旧 buffer 的使用依赖回传；不等于它一定曾经显示。
阅读原则：每个阶段都区分输入事务、拥有者、处理线程、输出状态和下一步依赖；View 数量只在 APP/RT/GPU 侧间接影响工作，独立 Surface 和 Layer 才直接改变 SF 图层集合。

11 · 收到 SF 的 VSYNC 回调：从预测唤醒到主线程 frame signal

SF 收到事务或更新请求后置 eTransactionFlushNeeded；Scheduler 为 sf 回调计算预测唤醒点。MessageQueue::vsyncCallback 收到目标 VSYNC、wakeup 和 ready 时间，dispatchFrame 合并消息，SF 主 Looper 最终进入 onFrameSignal。

输入应用/BLAST 事务、HWC 校准样本、其它合成请求。APP 关联View 数量不决定 SF 唤醒次数；事务合并、目标帧率、模式和 SF 调度决定本段。

06 / FINAL BOUNDARIES

这份文档可以证明什么，不能证明什么

可以从源码解释

事务如何进入队列、何时检查目标时间和 fence、LayerSnapshot 如何更新、Output 如何选择合成路径、present/release fence 如何被记录。

必须结合运行时 trace

某个具体 App 的 View 数量导致了多少 GPU 时间、某层本帧是否真正可见、某个 buffer 是否被替换或丢弃、实际线程是否晚调度。

源码不能直接证明

厂商 HWC 内部策略、DRM/KMS 细节、面板扫描顺序，以及某一行像素实际发光的物理时间。

最终边界：应用 View 树、RenderThread/GPU、窗口 buffer、BLAST 事务、SF Layer、OutputLayer、HWC 合成输入、present fence 和 release fence 是一条因果链上的不同对象，不能用一个“frame done”状态替代全部证据。
