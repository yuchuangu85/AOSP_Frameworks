App VSYNC 后，INSETS_ANIMATION 到底做了什么？

它不是普通属性动画的另一个名字。它把系统窗口 Insets 的变化聚合起来，在每帧向 View 树分发一份合并状态，让 APP 同步处理 IME、系统栏、手势区域和内容布局。

01 / FRAME ORDER

INSETS_ANIMATION 位于 ANIMATION 之后、TRAVERSAL 之前

Choreographer.java
L331–344 · L1199–1211

INPUT 和普通 ANIMATION 都可能改变 Insets；系统需要先收集这些变化，再用一次统一的 View 树回调分发合并后的 Insets。

INSETS_ANIMATION：一帧只向 View 树发一次合并进度

InsetsController 应用各 runner 的变化，计算整体 WindowInsets，然后调用 ViewRootInsetsControllerHost.dispatchWindowInsetsAnimationProgress。多个 Insets 类型同时运行时，APP 仍收到一次 progress 回调。

当前证据Choreographer 注释说明需要 gather all inset animation updates。边界它携带 WindowInsets、runningAnimations 和层级分发状态，不是单个 float fraction。
核心结论：INSETS_ANIMATION 的产物是“当前整体 WindowInsets + 正在运行的 Insets 动画列表”，不是一个普通 ValueAnimator 数值。

05 / APP EFFECTS

APP 的典型操作会影响哪些后续阶段

Insets 回调不是自动布局

平移内容

在 onPrepare 保存起始 translation，在 onProgress 根据 Insets 更新 translationX/Y，让内容跟随 IME 或系统栏移动。

返回修改后的 Insets

onProgress 可以返回 WindowInsets.inset() 后的实例，表示某部分 Insets 已被当前 View 消费或用于偏移/裁剪。

改变 padding / layout

APP 也可以更新 padding、可见性或尺寸，但每帧 requestLayout 会把工作推入后续 Traversal。

生命周期顺序：onPrepare 保存起始状态；onStart 读取 bounds；onProgress 每帧同步内容；onEnd 清理临时状态和提交最终状态。

07 / BOUNDARIES

Insets 回调完成不等于布局和显示完成

onProgress 完成

APP 已收到整体 WindowInsets，并可能返回修改后的 Insets；View 树还可能未重新布局。

Traversal 完成

后续阶段才根据 padding、translation、requestLayout 和 apply insets 执行 View 树工作。

显示完成

还要经过 RenderThread、GPU、BufferQueue、SurfaceFlinger、HWC 和 present fence。
