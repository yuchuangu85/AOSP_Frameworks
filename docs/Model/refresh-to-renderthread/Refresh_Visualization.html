01requestLayout 只是“登记”

它不会立即 measure，只置脏标记并向上冒泡。真正的遍历由 ViewRootImpl 合并、Choreographer 预约，等 VSYNC 才执行。

02同步屏障让 traversal 抢先

scheduleTraversals 用 postSyncBarrier() 把 traversal 插到所有同步消息之前；没有它，doFrame 可能被业务 Handler 消息拖后。

03draw 只负责录制

UI 线程的 draw 把绘制指令写进 RenderNode 的 DisplayList，真正 GPU 回放发生在 RenderThread；交棒点是 syncAndDrawFrame()。

01触发：requestLayout/invalidate

两条不同的脏链路：FORCE_LAYOUT 沿父链上行，DIRTY 沿父链合并成一块脏区

UI 线程上任何要改界面的动作最终归为两条链路。requestLayout() 是"尺寸/位置可能要变"：View.requestLayout 清 measure 缓存、查 requestLayoutDuringLayout（布局中请求要走特殊通道）、置 PFLAG_FORCE_LAYOUT 与 PFLAG_INVALIDATED，然后沿 mParent 上行，直到 ViewRootImpl.requestLayout 置 mLayoutRequested 并调 scheduleTraversals()。invalidate() 是"内容变了、尺寸没变"：View.invalidateInternal 检查一堆位（PFLAG_DRAWN/PFLAG_HAS_BOUNDS/PFLAG_INVALIDATED/DRAWING_CACHE_VALID），清 PFLAG_DRAWN、置 PFLAG_DIRTY，再把脏矩形交给 mParent.invalidateChild；硬件加速下 ViewGroup.onDescendantInvalidated 会走"忽略矩形、只置 DIRTY 位"的快路径并一路冒泡到 ViewRootImpl.invalidate()。两者都只是置位 + 调度，绝不立即 measure/ draw——真正的测量、布局、绘制发生在下一次 traversal。注意两条链路都不产生任何跨进程调用：它们只在本进程内改位与调度，真正的跨进程动作要等 traversal 走到 relayoutWindow 与 DrawFrameTask。

View.requestLayout()→ViewGroup.requestLayout()→ViewRootImpl.requestLayout()→ViewRootImpl.scheduleTraversals()→View.invalidate()→View.invalidateInternal()→ViewGroup.onDescendantInvalidated()→ViewRootImpl.invalidate()

两条链路最终都汇到同一个 scheduleTraversals()，所以一次 traversal 可能同时承担 measure/layout 和 draw。区分它们只影响「这一帧要不要重新测量布局」，不影响「会不会调度一帧」。

requestLayout 的细节：为什么它会清 measure 缓存

View.requestLayout()（View.java:28723-28753）依次做：

  1. relayout tracing 开关打开时打一条 instant，并打印调用栈（28724-28728）——这是线上抓「谁在疯狂 requestLayout」的入口；
  2. if (mMeasureCache != null) mMeasureCache.clear()：measure 结果按 MeasureSpec 缓存（mMeasureCache 是 LongSparseLongArray，View.java:28799），布局请求意味着缓存失效；
  3. 布局中请求的检查：仅当 mAttachInfo.mViewRequestingLayout == null（说明是本 view 发起而不是父链递归上来）且 viewRoot.isInLayout() 时，调 viewRoot.requestLayoutDuringLayout(this)，返回 false 就直接 return（28732-28742）；
  4. 置位：mPrivateFlags |= PFLAG_FORCE_LAYOUT 与 |= PFLAG_INVALIDATED（28744-28745）；
  5. 冒泡：if (mParent != null && !mParent.isLayoutRequested()) mParent.requestLayout()（28747-28749）。

第五步的 !mParent.isLayoutRequested() 是短路优化：父节点已经置了 FORCE_LAYOUT 就不再往上走，因为它的祖先必然也已经置了。这也是为什么一次布局里 N 个子 view 请求布局，冒泡总次数不会退化成 O(N×深度)。

isLayoutRequested() 在 View 侧实现为 (mPrivateFlags & PFLAG_FORCE_LAYOUT) == PFLAG_FORCE_LAYOUT（View.java:25972-25974），在 ViewRootImpl 侧则是 mLayoutRequested 字段（ViewRootImpl.java:2850-2853）——父链顶端的那一环换了实现，这是冒泡能终止的原因。

invalidate 的细节：位运算决定要不要真的脏

View.invalidate() 只是 invalidate(true)，后者调 invalidateInternal(0, 0, mRight - mLeft, mBottom - mTop, invalidateCache, true)（View.java:21449-21451）。invalidateInternal 先过两道闸：mGhostView 存在就转发、skipInvalidate() 为真就直接返回（21455-21462）。

然后是一个大条件（21468-21471），任意一项成立才继续：

  • (PFLAG_DRAWN | PFLAG_HAS_BOUNDS) 两位都置——本 view 已经被画过且有 bounds，脏才有意义；
  • invalidateCache && PFLAG_DRAWING_CACHE_VALID——绘制缓存还有效，需要连带失效；
  • (mPrivateFlags & PFLAG_INVALIDATED) != PFLAG_INVALIDATED——还没被标脏过；
  • fullInvalidate && isOpaque() != mLastIsOpaque——不透明度变了，旧内容不可信。

条件成立后：mLastIsOpaque = isOpaque()、mPrivateFlags &= ~PFLAG_DRAWN（21472-21475），置 PFLAG_DIRTY（21477），若 invalidateCache 再置 PFLAG_INVALIDATED、清 PFLAG_DRAWING_CACHE_VALID（21479-21482），最后把矩形交给父节点：p.invalidateChild(this, damage)（21487-21491）。

PFLAG_DRAWN 会在 View.draw() 开头被重新置上：mPrivateFlags = (privateFlags & ~PFLAG_DIRTY_MASK) | PFLAG_DRAWN（View.java:25494-25495）。所以「DRAWN 位」的语义是「本帧已经画过、并且没有新的脏标记」，清它就是为了让下一次 invalidate 不被上面的条件挡掉——这是同一个 view 一帧内多次 invalidate 的合并机制。

硬件加速下的另一条快路径：onDescendantInvalidated

硬件加速且本 view 有 DisplayList 时，invalidateViewProperty 会走快路径（View.java:21543-21554 分支判断 isHardwareAccelerated() && mRenderNode.hasDisplayList()），父链上的传递也换成 ViewGroup.onDescendantInvalidated(View child, View target)（ViewGroup.java:6201-6232）。

这个函数的注释把设计说得很清楚：HW-only, Rect-ignoring damage codepath —— 我们在这里不处理矩形，因为 RenderThread 的原生代码会为 HWUI 绘制的所有内容计算 damage（6202-6207）。它只做三件事：

  1. 把子节点的 PFLAG_DRAW_ANIMATION 合并到自己身上（6210）；
  2. 若 target.mPrivateFlags & ~PFLAG_DIRTY_MASK 非零，就懒置 PFLAG_DIRTY 并清 PFLAG_DRAWING_CACHE_VALID（6212-6219）；
  3. 若自己是 LAYER_TYPE_SOFTWARE，升级成一次完整 invalidate（PFLAG_INVALIDATED | PFLAG_DIRTY，并把 target 改成自己），因为软件层必须重画；然后 mParent.onDescendantInvalidated(this, target) 继续上行（6222-6231）。

它最终到达 ViewRootImpl.onDescendantInvalidated（ViewRootImpl.java:2856-2861），后者只看 PFLAG_DRAW_ANIMATION 决定 mIsAnimating = true，然后调 invalidate() 走全屏脏。所以 HW 路径下矩形信息在 Java 侧被丢弃，damage 由 RT/Skia 重新计算——这与 SF 侧 stage 的 damage 语义是两套东西。

ViewRootImpl：两条链路的汇合点与线程检查

ViewRootImpl.requestLayout()（ViewRootImpl.java:2842-2848）非常短：

if (!mHandlingLayoutInLayoutRequest) { checkThread(); mLayoutRequested = true; scheduleTraversals(); }

mHandlingLayoutInLayoutRequest 是「第二次布局中」的标记，为真时直接丢弃请求（见 requestLayoutDuringLayout 的注释：第一次布局中的请求会被记录并在本帧补一次布局，第二次布局中再来的请求要 post 到下一帧，避免死循环）。

ViewRootImpl.invalidate()（2864-2869）：先把整块窗口区域标脏 mDirty.set(0, 0, mWidth, mHeight)，再 if (!mWillDrawSoon) scheduleTraversals()。mWillDrawSoon 在 performTraversals 开头置 true（3954）、结尾置 false（4824），所以正在跑 traversal 期间的 invalidate 不会重复调度——这是合并的关键。

脏矩形进入系统还有一条老路径 invalidateChildInParent（2887-2915）：checkThread()、dirty == null 就退化成整窗 invalidate、dirty.isEmpty() && !mIsAnimating 就丢弃，否则按 mCurScrollY/mTranslator/mAttachInfo.mScalingRequired 调整后 invalidateRectOnScreen(dirty)。

线程检查有两套：checkThread()（12136-12141）直接抛 CalledFromWrongThreadException（消息里带期望线程名与实际线程名）；checkThreadCompat()（12171 起）按 ChangeId 决定抛异常还是只打一条 WTF 日志，用于渐进式收紧。scheduleTraversals 用的是后者，requestLayout/invalidateChildInParent 用的是前者。

为什么不会立即 measure：位与调度是两件事

所有 requestLayout/invalidate 都只做「置位 + 可能调度」，没有一处直接调 measure() 或 draw()。真正的执行要等 Choreographer 的 CALLBACK_TRAVERSAL 触发 performTraversals（ViewRootImpl.java:3924），再由它依次 performMeasure/performLayout/performDraw。

位的生命周期可以串成一条线：

  • requestLayout 置 PFLAG_FORCE_LAYOUT → View.measure 用它决定是否跳过缓存（View.java:28801-28815）→ View.layout 末尾清掉它（26092）；
  • invalidate 清 PFLAG_DRAWN、置 PFLAG_DIRTY → View.draw 开头清 DIRTY、置回 DRAWN（25495）。

所以「这一帧要不要重新布局」只看 FORCE_LAYOUT 是否还在，「要不要重绘」只看 DIRTY 位与脏区是否为空。二者互不替代：只请求布局不改内容时，如果尺寸没变，draw 仍然会跑（因为 traversal 是原子的，布局后总会走绘制，只是脏区可能为空而提前返回）。

边界：硬件加速层、属性动画、非 UI 线程

三条容易踩的边界：

  1. 属性动画：ViewPropertyAnimator/RenderNodeAnimator 改的是 RenderNode 的属性（alpha/translation/scale 等），不走 invalidate() 的位运算，而是 invalidateViewProperty → 父链 invalidateChildInParent 或 onDescendantInvalidated；纯 RenderNode 属性的动画在 RT 上自驱（对应 RT 专题的 requiresUiRedraw），不需要 UI 每帧参与。
  2. 硬件加速层：LAYER_TYPE_SOFTWARE 的父层会让 onDescendantInvalidated 升级成完整 invalidate（6222-6227）；hasDisplayList() 为假（尚未录制过 DisplayList）时走慢路径 invalidate(false)（21544-21553）。
  3. 非 UI 线程：checkThread() 会抛异常，正确做法是 postInvalidate()（走 Handler 投递到 UI 线程再 invalidate）。ViewRootImpl.requestLayout() 只在 !mHandlingLayoutInLayoutRequest 时才 checkThread，所以布局中的请求由 requestLayoutDuringLayout 的 mLayoutRequesters 列表接管。

一个常见误解：以为 requestLayout() 会「清掉父链上的缓存」——它只清自己的 mMeasureCache，父节点的缓存失效是父节点自己收到 requestLayout 时清自己的。

!坑点与边界
误以为 requestLayout() 会立刻 measure：它只置 PFLAG_FORCE_LAYOUT 并调度，真正的 measure 在下一个 vsync 的 performTraversals 里；所以循环里连续调用 N 次 requestLayout 只会产生一次布局。
误以为 invalidate() 一定会重绘：invalidateInternal 有四个条件组成的闸门（View.java:21468-21471），一个都不满足时直接返回，连父链都不会冒泡。
误以为 requestLayout 会连带清父节点缓存：它只清自己的 mMeasureCache（28730），父节点缓存由父节点自己的 requestLayout 清理。
误以为布局中调用 requestLayout 一定生效：第二次布局中（mHandlingLayoutInLayoutRequest）的请求会被丢弃并 post 到下一帧，这是防死循环的设计（ViewRootImpl.java:5527-5535）。

02调度：scheduleTraversals 与同步屏障

置 mTraversalScheduled、postSyncBarrier、注册 CALLBACK_TRAVERSAL——都不执行，只排队

ViewRootImpl.scheduleTraversals() 是整条 UI 刷新链路的收口：它先 checkThreadCompat()，然后在 mTraversalScheduled 为 false 时做三件事——postTraversalBarrier() 往主线程 MessageQueue 插一个同步屏障（同步消息被挡住、异步消息可穿过，从而保证 traversal 抢在已排队的普通消息之前执行），mChoreographer.postVsyncCallback(Choreographer.CALLBACK_TRAVERSAL, mTraversalCallback) 把一次性的 VsyncCallback 塞进 Choreographer 的 CALLBACK_TRAVERSAL 队列并请求下一帧 vsync，notifyRendererOfFramePending() + pokeDrawLockIfNeeded() 通知 RenderThread 与 WMS 帧即将到来。android17 已经没有 mTraversalRunnable 字段，traversal 入口改成了实现 Choreographer.VsyncCallback 的 TraversalCallback，它的 onVsync(FrameData) 只做一件事：doTraversal(frameData.getFrameTimeNanos())。doTraversal 里再清 mTraversalScheduled、removeTraversalBarrier()，然后才 performTraversals。屏障用 AtomicLong 管理，避免并发（错误用法下）留下永久屏障卡死主线程。换句话说，这一阶段的全部价值在于排序：用一个同步屏障加一条异步消息，把 traversal 精确插到「本轮 UI 消息之后、下一拍 vsync 之前」。

ViewRootImpl.requestLayout()→ViewRootImpl.scheduleTraversals()→ViewRootImpl.postTraversalBarrier()→Choreographer.postVsyncCallback()→ViewRootImpl.notifyRendererOfFramePending()→ViewRootImpl.doTraversal()→ViewRootImpl.removeTraversalBarrier()→ViewRootImpl.performTraversals()

触发者与位置：谁调 scheduleTraversals

直接调用者只有两类：ViewRootImpl.requestLayout()（ViewRootImpl.java:2846）与 ViewRootImpl.invalidate()（2867）；另外 surface/窗口属性变化也会直接走到它。它必须在 UI 线程执行：入口第一行是 checkThreadCompat()（3308），比 requestLayout 用的 checkThread() 宽松（按 ChangeId 决定抛异常还是只打一条 WTF）。

函数体只有一个 if（3309-3334）：!mTraversalScheduled 时才进入，进入后立刻把它置 true——所以同一帧内 N 次 requestLayout/invalidate 只会产生一次调度，这是第一层合并。第二层合并是 mWillDrawSoon（invalidate 里判断），第三层是 Choreographer.mFrameScheduled（stage-03 详述）。

mTraversalScheduled 是 public boolean（ViewRootImpl.java:758），注释里明确它「not safe for concurrent access」，这也是为什么配套的屏障要用 AtomicLong 兜底。

同步屏障：为什么 traversal 必须抢占普通消息

代码里那段长达 13 行的注释（3311-3328）是理解同步屏障的关键，它给了可验证的公开 API 契约：

textView.setText("Hello, world!");
textView.getHandler().post(new Runnable() { public void run() { reportNewTextWidth(textView.getWidth()); } });

注释说这段代码被定义为正确，而负责保证它的是 MessageQueue 的同步屏障机制：任何在 scheduleTraversals 之后 post 的普通消息，都保证在 traversal 跑完之后才执行（异步消息除外）。如果 traversal 只是一个普通消息，它会被排到那条 post 之后，getWidth() 就会读到旧值。

MessageQueue.postSyncBarrier() 的语义（见 base/core/java/android/os/CombinedDeliMessageQueue/MessageQueue.java:1220-1246）是：插入一个屏障后，同步消息停止派发，异步消息（Message.isAsynchronous()）继续执行，直到用同一个 token 调 removeSyncBarrier；注释还警示「必须成对调用，否则应用大概率会 hang」。Choreographer 自己投递的 MSG_DO_FRAME/MSG_DO_SCHEDULE_VSYNC/MSG_DO_SCHEDULE_CALLBACK 都带 msg.setAsynchronous(true)（Choreographer.java:640、934、944），所以屏障拦不住它们——这就是屏障加异步消息的组合拳。

版本注意：android17 的 base/core/java/android/os/ 下没有单一的 MessageQueue.java，而是 LegacyMessageQueue/CombinedMessageQueue/CombinedDeliMessageQueue 三个变体目录各自一份实现（构建时如何选择哪一份，源码树内未体现）；它们的 postSyncBarrier 契约一致。

屏障的原子管理：为什么需要一个 AtomicLong

postTraversalBarrier()（3355-3367）不是简单地存一个 int：

  • mAtomicTraversalBarrier 为 false 时走老路径：mTraversalBarrier = mQueue.postSyncBarrier()（3365），字段注释直接写「not safe for concurrent access」（759）；
  • 为 true 时用 AtomicLong mTraversalBarrierAtomic（771）做 getAndSet(newBarrier)，若拿到的旧值不是 UNSET_TRAVERSAL_BARRIER（Long.MAX_VALUE，369），说明这次设置覆盖了一个尚未移除的屏障，责任在本次调用方，所以要主动 removeSyncBarrier((int) oldBarrier)（3359-3363）。

字段注释解释了动机（761-770）：这是为了降低 view root 数据竞争的影响——在竞态访问下多次添加屏障不会导致一个屏障永久留在队列里，把线程活活卡死。removeTraversalBarrier()（3369-3380）是对称的：原子地把值换回 UNSET_TRAVERSAL_BARRIER，拿到旧值才真正 removeSyncBarrier，从而保证「只移除自己设置的那一个」。

这里有一个真实的风险边界：如果屏障被设置了却没移除（例如 traversal 里抛异常且 doTraversal 的 removeTraversalBarrier() 没跑到），主线程的同步消息会永远不派发，表现就是UI 卡死但 vsync 还在来。这也是为什么 unscheduleTraversals()（3337-3345）存在——取消调度时必须同时 removeTraversalBarrier() 与 Choreographer.removeVsyncCallback(...)。

postVsyncCallback：只是入队，不执行

第三个动作是把 traversal 挂到 Choreographer：mChoreographer.postVsyncCallback(Choreographer.CALLBACK_TRAVERSAL, mTraversalCallback)（3330-3331）。Choreographer.postVsyncCallback(int, VsyncCallback)（Choreographer.java:676-682）转调 postCallbackDelayedInternal(callbackType, callback, VSYNC_CALLBACK_TOKEN, 0)，后者做两件事（622-644）：

  1. mCallbackQueues[callbackType].addCallbackLocked(dueTime, action, token)——入队，dueTime = now + 0；
  2. 因为 dueTime <= now，立刻 scheduleFrameLocked(now) 请求下一帧 vsync（这一步在 stage-03 展开）。

注意 callbackType 是 CALLBACK_TRAVERSAL = 3（351），mCallbackQueues 是按 type 分开的 5 条队列，索引 0..4 对应 CALLBACK_TRACE_TITLES 里的 input/animation/insets_animation/traversal/commit（313-315）。这也解释了为什么 doFrame 里能按固定顺序取回调（stage-04）。

关键结论：scheduleTraversals 返回时，traversal 一次都没执行。它做的全是「置位 + 入队 + 插屏障 + 唤醒 RT/WMS」，CPU 时间几乎为零，真正的重活留到下一个 vsync 的 doFrame。这也是「为什么 UI 线程卡顿时，requestLayout 本身看起来很快」的原因。

android17 没有 mTraversalRunnable：TraversalCallback 取代了它

老版本里 ViewRootImpl 有一个 mTraversalRunnable（实现 Runnable），通过 Choreographer.postCallback(CALLBACK_TRAVERSAL, mTraversalRunnable, null) 提交。run() 里调 doTraversal()。android17 换成了 VsyncCallback 体系：

final class TraversalCallback implements Choreographer.VsyncCallback {
    @Override public void onVsync(Choreographer.FrameData frameData) {
        doTraversal(frameData.getFrameTimeNanos());
    }
}
final TraversalCallback mTraversalCallback = new TraversalCallback();

（ViewRootImpl.java:11445-11451）VsyncCallback 的接口注释（Choreographer.java:1537-1556）说明了动机：回调载荷 FrameData 携带多个候选帧的信息，让调用方可以按延迟要求挑合适的那一帧；data 只在 onVsync 内有效，不能带出去用。这比 Runnable 多了一个参数化帧时间的能力。

对排查的影响：trace 里 Choreographer#doFrame 之后不再有以 mTraversalRunnable 命名的片段，traversal 的执行区间按 type 命名为 traversal（CALLBACK_TRACE_TITLES）。找 traversal 起点要看 Choreographer#doFrame → traversal → performTraversals 这条链。

doTraversal：清标志、移屏障、再进 performTraversals

doTraversal(long frameTimeNanos)（3347-3353）只有三行有效代码：

if (mTraversalScheduled) { mTraversalScheduled = false; removeTraversalBarrier(); performTraversals(frameTimeNanos); }

三个细节值得注意：

  • 先清标志再干活：mTraversalScheduled = false 在最前面，保证 performTraversals 期间如果有代码调 requestLayout，能重新调度下一帧（而不是被已置位的标志挡住）。
  • 屏障必须最先移除：removeTraversalBarrier() 在 performTraversals 之前，否则 traversal 里任何需要等主线程同步消息的操作都会死锁。
  • 参数只有一个帧时间：frameTimeNanos 来自 FrameData.getFrameTimeNanos()，它在 Choreographer 里已经过 jitter 修正（stage-04），所以 performTraversals 拿到的是「本帧的动画基准时间」。

另外 performTraversals 自己还有一道早退：mNumPausedForSync > 0 时直接 return 并记 mLastPerformTraversalsSkipDrawReason = "paused_for_sync"（3940-3951）——BLAST sync 期间不遍历。host == null || !mAdded 也会早退（3935-3938）。

与 RenderThread / WMS 的边界

scheduleTraversals 最后两个调用是跨组件的通知，都不阻塞：

  • notifyRendererOfFramePending()（3265-3269）：若 mAttachInfo.mThreadedRenderer != null，调 mThreadedRenderer.notifyFramePending()。注释说明用途是让 ThreadedRenderer 知道「马上要来一帧」，用来调整离屏（RT 自驱）动画的调度。
  • pokeDrawLockIfNeeded()（2771 起）：与 WindowManager 的 draw lock 相关，用于保证本帧能在 WMS 的等待窗口内完成——具体实现在该方法内部，属于 WMS 交互而非渲染栈。

这两步都不涉及 binder 同步调用（notifyFramePending 是本地调用），真正的跨进程动作发生在 performTraversals 里的 relayoutWindow（IWindowSession）与 DrawFrameTask 提交时。所以在 trace 上，scheduleTraversals 几乎看不到耗时，但它决定了下一帧的时间起点。

排障：屏障泄漏与重复调度的识别

三个高价值检查点：

  1. 主线程卡死但 vsync 仍在来：典型是同步屏障泄漏。可在 MessageQueue 的 dump 里看到队头是一个 target=null 的屏障消息（postSyncBarrier 投递的 Message 不带 target），后面的同步消息都不派发。此时检查 doTraversal 是否因异常没走到 removeTraversalBarrier()。
  2. traversal 被重复调度：如果 trace 里同一个 vsync 出现两次 performTraversals 或一次 vsync 出现多次 doFrame，先看 mTraversalScheduled/mFrameScheduled 是否被错误清零；unscheduleTraversals 与 scheduleTraversals 不配对也会造成重复。
  3. traversal 被普通消息插队：说明屏障没插成功（postSyncBarrier 返回 -1 或 mAtomicTraversalBarrier 路径异常）。表现是「setText 之后 post 的 runnable 读到了旧宽度」这类公开 API 契约被破坏。

可观测点：trace 里 Choreographer#doFrame 下的 traversal 片段（CALLBACK_TRACE_TITLES）、performTraversals 的起止时间、以及 ViewRootImpl 的 mLastPerformTraversalsSkipDrawReason（3949、3965 等赋值的字符串原因，可通过 dumpsys 或调试日志看到跳过原因）。

03请求 VSYNC：Choreographer 到 SF

一次请求走三层去重：mFrameScheduled、mWaitingForVsync、vsyncRequest，最后变成 binder oneway

scheduleTraversals 里调完 postVsyncCallback 后，Choreographer.postCallbackDelayedInternal 因为 dueTime <= now 立刻调 scheduleFrameLocked(now)。scheduleFrameLocked 用 mFrameScheduled 做第一层去重（一帧只请求一次），然后按当前线程是否是 Looper 线程分流：是就直接 scheduleVsyncLocked()，否则投一条 setAsynchronous(true) 的 MSG_DO_SCHEDULE_VSYNC 到消息队列最前面。scheduleVsyncLocked 只有一行实质代码：mDisplayEventReceiver.scheduleVsync()。这条调用穿三层：Java DisplayEventReceiver.scheduleVsync → JNI nativeScheduleVsync → native DisplayEventDispatcher::scheduleVsync；后者用 mWaitingForVsync 做第二层去重，然后 mEventConnection->requestNextVsync() 发一次 binder oneway 给 SF 的 EventThread。EventThread::requestNextVsync 用 vsyncRequest 状态机做第三层去重（None→Single），threadMain 只在有连接请求时才向 VSyncDispatch 注册一次定时器，唤醒时刻由 (workDuration, readyDuration, lastVsync) 反推——这就是 VSYNC phase offset 落到代码里的地方。需要强调：请求本身不携带任何帧内容，它只是向 SF 声明「我下一拍想要一个 vsync」；能不能拿到、什么时候拿到，由 SF 的 EventThread 与 VSyncDispatch 决定。

链条从 stage-02 的 postVsyncCallback 继续：Choreographer.postCallbackDelayedInternal（Choreographer.java:622-644）在 synchronized (mLock) 里入队后，因为 dueTime <= now（delay 为 0），立刻调 scheduleFrameLocked(now)。所以「请求 vsync」是入队的副作用，而不是单独一步。

如果 dueTime > now（带延迟的回调），走的是另一条分支：mHandler.sendMessageAtTime(msg, dueTime)，消息带 setAsynchronous(true)（638-641），等到期时由 doScheduleCallback（1275-1284）再决定要不要 scheduleFrameLocked。两条分支都保证「只有到期的回调才会拉起一帧」。

注意 mFrameScheduled 的复位点在 doFrame 里：mFrameScheduled = false（Choreographer.java:1187），与 mLastFrameTimeNanos 的更新在同一段 synchronized (mLock) 内。所以「一帧只请求一次 vsync」的窗口是「从上一次 doFrame 取走标志到本帧 doFrame 清标志」。

scheduleFrameLocked：两条分支与一层去重

scheduleFrameLocked(long now)（919-948）的结构是：

  1. if (!mFrameScheduled) { mFrameScheduled = true; ... }——第一层去重，同一帧内重复调用只有第一次生效；
  2. if (USE_VSYNC) 时看线程：isRunningOnLooperThreadLocked() 为真（Looper.myLooper() == mLooper，1296-1298）就直接 scheduleVsyncLocked()；否则投 MSG_DO_SCHEDULE_VSYNC 并用 sendMessageAtFrontOfQueue 插到队首（933-935）。
  3. else（无 vsync 的调试模式）按 sFrameDelay 算 nextFrameTime 并投 MSG_DO_FRAME（937-946）。

为什么要分线程？scheduleFrameLocked 可能在非 UI 线程被调用（例如某个后台线程 post 了回调），而 DisplayEventReceiver.scheduleVsync() 依赖 native 侧的线程状态与 Looper，直接在错误的线程调会破坏 FD 与 Looper 的绑定。所以非 Looper 线程只能把「去请求 vsync」这件事排队到 UI 线程，且要用队首 + 异步消息插队。

sendMessageAtFrontOfQueue 与 setAsynchronous(true) 的组合意味着：这条消息既会插到所有消息之前，也不受同步屏障影响——即使 scheduleTraversals 已经插了屏障，它也照样执行。

第三层去重：EventThread 的 vsyncRequest 状态机

EventThread::requestNextVsync(connection)（native/services/surfaceflinger/Scheduler/EventThread.cpp:417-428）先 mCallback.resync(IEventThreadCallback::ResyncCaller::RequestNextVsync)，再在 mMutex 下改状态：

状态机含义：None 表示没在等 vsync，收到请求变 Single（只要一个）；已经是 Single 时重复请求是幂等的（不改任何东西）；SingleSuppressCallback 是「已经发过一拍但回调被抑制」的中间态，此时再请求会恢复成 Single。这就是「一次请求只发一次」在 SF 侧的实现。

顺带一个与监视相关的事实：requestNextVsync 里那行 mCallback.resync(...) 会触发 Scheduler 检查是否需要把定时器重新对齐到硬件 vsync——所以「App 请求 vsync」这个动作本身就可能引起一次 resync，这也是为什么突发大量请求会让 vsync 时间线抖动。

threadMain 的排程：只有有人要 vsync 才武装定时器

EventThread::threadMain（530-635）是 EventThread 自己的线程循环。与本阶段相关的三段：

  1. 遍历连接算 vsyncRequested |= connection->vsyncRequest != VSyncRequest::None（555-571）；

  3. 根据 mVSyncState && vsyncRequested 决定状态：为真则 updateState(State::VSync)（或 SyntheticVSync），为假则 updateState(State::Idle)（578-593）。

没有任何连接请求 vsync 时，EventThread 会 cancel 定时器并 mCondition.wait(lock) 睡下去（611-612）——这就是「没有动画的 App 不产生 vsync 负载」的机制。反向地，只要有连接把 vsyncRequest 置成 Single，条件变量被 notify，循环重新武装一次定时器。

循环末尾还有一个防驱动异常的保护：mCondition.wait_for 超时（SyntheticVSync 16ms / VSync 1000ms）时会伪造一个 vsync 事件并打 "Faking VSYNC due to driver stall"（614-630）——线上看到这条日志说明 display 驱动卡住了。

VSYNC phase offset：唤醒时刻是怎么算的

「App 的 vsync 比真正上屏时刻早多少」由 phase offset 决定，代码路径是：SF 创建 app EventThread 时传入 configs.late.appWorkDuration 与 configs.late.sfWorkDuration（SurfaceFlinger.cpp:5218-5220），SF 自己那条 MessageQueue 则用 configs.late.sfWorkDuration（5225）。这两个 duration 来自 VsyncConfiguration：

sfOffsetToDuration(sfOffset, vsyncDuration) = vsyncDuration - sfOffset
appOffsetToDuration(appOffset, sfOffset, vsyncDuration) = vsyncDuration + (sfOffset - appOffset)

（native/services/surfaceflinger/Scheduler/VsyncConfiguration.cpp:146-158，若结果小于一个 vsync 周期会再补一个周期。）EventThread 把 mWorkDuration/mReadyDuration 通过 mVsyncRegistration.schedule/update 交给 VSyncDispatch，最终落到 VSyncDispatchTimerQueueEntry::schedule（VSyncDispatchTimerQueue.cpp:90-118）：

nextVsyncTime = tracker.nextAnticipatedVSyncTimeFrom(max(lastVsync, now + workDuration + readyDuration), ...)
nextWakeupTime = nextVsyncTime - workDuration - readyDuration
nextReadyTime = nextVsyncTime - readyDuration

也就是说 wakeup = vsync − workDuration − readyDuration、ready = vsync − readyDuration。对 App 来说 workDuration = appWorkDuration、readyDuration = sfWorkDuration，所以 App 在「vsync 前 (appWorkDuration + sfWorkDuration)」被唤醒、在「vsync 前 sfWorkDuration」拿到 ready 时间——这就是常说的 App/SF 两段相位。

定时器到点后 VSyncDispatchTimerQueue::timerCallback（334-379）在 timer 线程里挑出到期的 entry 并调 callback->callback(vsyncTimestamp, wakeupTimestamp, deadlineTimestamp)；EventThread 注册的 callback 就是 createDispatchCallback() 里的 lambda（EventThread.cpp:895-899），直接转成 EventThread::onVsync(vsyncTime, wakeupTime, readyTime)（472-481）把事件塞进 mPendingEvents。

排障：vsync 请求丢了还是被合了

四个检查点，按代价从低到高：

  1. 本进程请求了几次：trace 里数 Choreographer#scheduleVsyncLocked 的个数（每个 trace 一个），与 Choreographer#doFrame 的个数对比。前者远大于后者说明有大量重复请求被 mFrameScheduled 合并了（正常），或者有代码在疯狂调 scheduleFrameLocked。

FrameDisplayEventReceiver.onVsync：为什么不直接跑 doFrame

onVsync（Choreographer.java:1594-1635）先打 "Choreographer#onVsync <vsyncId>" 的 trace，然后：

  1. 若 timestampNanos > now（未来时间戳），修正成 now 并在 DEBUG_JANK 下打警告（1607-1615）——这是对 graphics HAL 时间基错误的兜底；
  2. mHavePendingVsync 为真时只打警告不重复处理（1617-1624），否则置 true——第四层去重（前三层在 stage-03）；
  3. 把 mTimestampNanos/mFrame 存字段，mLastVsyncEventData.copyFrom(vsyncEventData)（1626-1628）；
  4. Message msg = Message.obtain(mHandler, this); msg.setAsynchronous(true); mHandler.sendMessageAtTime(msg, timestampNanos / TimeUtils.NANOS_PER_MS)（1629-1631）。

为什么绕一圈？注释（1602-1606）写得很清楚：防止 vsync 事件把消息队列饿死；如果队列里没有比 frame time 更早的消息，vsync 会被立即处理，否则先处理那些更早的消息。用 sendMessageAtTime 而不是 sendMessageAtFrontOfQueue，正是为了让「vsync 之前就该跑的普通消息」先跑——这与 stage-02 里屏障保证「traversal 之后的消息」后跑的语义正好互补。

run()（1638-1641）只有两行：mHavePendingVsync = false; doFrame(mTimestampNanos, mFrame, mLastVsyncEventData);——所以真正执行 doFrame 的线程就是该 Handler 所在的 Looper 线程，也就是 UI 线程。

doFrame 前半段：buffer stuffing、jitter 与帧时间修正

doFrame(long frameTimeNanos, int frame, VsyncEventData vsyncEventData)（1074 起）开场就做两件事：

  • updateBufferStuffingState(...) 返回 NONE/OFFSET/DELAY_FRAME（1086-1104）：OFFSET 时把 offsetFrameTimeNanos 减一个 frameInterval；DELAY_FRAME 时直接 scheduleVsyncLocked() 后 return，故意丢这一帧来消化积压的 buffer（注释："Intentional frame delay to help reduce queued buffer count"）。
  • FrameTimeline timeline = mFrameData.update(offsetFrameTimeNanos, vsyncEventData)（1107）并把 trace 名拼上 timeline.mVsyncId（1109-1110）。

接着在 synchronized (mLock) 里做核心校验：

  1. if (!mFrameScheduled) { traceMessage("Frame not scheduled"); return; }（1114-1117）——没有待处理帧就直接返回，这是「空 vsync」的出口；
  2. jitter 修正（1123-1156）：jitterNanos = startNanos - frameTimeNanos，若 >= frameIntervalNanos 说明 UI 线程来晚了，就把 frameTimeNanos 对齐到 startNanos - (jitterNanos % frameIntervalNanos)，skippedFrames = jitterNanos / frameIntervalNanos，超过 SKIPPED_FRAME_WARNING_LIMIT 就打那条著名的 "Skipped N frames! The application may be doing too much work on its main thread."（1131-1136），并置 resynced = true 后重算 timeline（1153-1155）；
  3. frameTimeNanos < mLastFrameTimeNanos 时 scheduleVsyncLocked() 后 return（1158-1169）——帧时间倒退（可能因为上一拍被跳）就等下一拍；
  4. mFPSDivisor > 1 时按 frameIntervalNanos * mFPSDivisor 过滤（1171-1181），这是降帧率的调试/省电手段。

校验通过后写 FrameInfo：mFrameInfo.setVsync(intendedFrameTimeNanos, frameTimeNanos, vsyncEventData.preferredFrameTimeline().vsyncId, vsyncEventData.preferredFrameTimeline().deadline, startNanos, vsyncEventData.frameInterval, frameTimeNanos)（1183-1186），然后 mFrameScheduled = false、更新 mLastFrameTimeNanos/mLastFrameIntervalNanos 并 mLastVsyncEventData.copyFrom(...)（1187-1190）。

relayout 只更新几何，真正把几何写进 SurfaceControl 的是客户端的 mTransaction（ViewRootImpl.java:1455 创建）。relayoutWindow 里有两处典型用法：

  • 拖拽 resize：mPendingDragResizing 且 mSurfaceSize 与 frame 不一致时，用 mTransaction.setWindowCrop(mSurfaceControl, mWinFrameInScreen.width(), mWinFrameInScreen.height())（10375-10376）把全屏 surface 裁到内容大小，避免露出旧内容。
  • drawing 被禁用：!HardwareRenderer.isDrawingEnabled() 时 window layer 没有有效 buffer，会 setWindowCrop(mSurfaceControl, mSurfaceSize.x, mSurfaceSize.y).apply()（10381-10382），让输入仍能命中窗口；这是少数在 relayout 里直接 apply 的分支，其余都是 applyTransactionOnDraw 延迟到绘制时提交。

WMS 侧对同一个 SurfaceControl 的透明性设置走 WindowStateAnimator.setOpaqueLocked（WindowStateAnimator.java:460：mWin.getPendingTransaction().setOpaque(mSurfaceControl, isOpaque)），和客户端的 Transaction 是两条独立的事务流：客户端的 mTransaction 由 applyTransactionOnDraw（ViewRootImpl.java:13748）在绘制时提交，WMS 的 pending transaction 由 SF 侧 applySurfaceChangesTransaction 应用。理解这一点才能解释“为什么 relayout 返回了但屏上还没变”。

deadline 与边界

relayout 是 UI 线程上少数会真正阻塞在 binder 上的步骤之一（同步路径）。它必须在 Choreographer 分配的 traversal 预算内完成，因为后面还有 measure、layout、draw 录制要跑，全部要在 FrameInfo[FRAME_DEADLINE] 之前结束。同步 relayout 一慢，后面的窗口就被压缩；异步 relayout 虽然不阻塞，但如果 WMS 侧处理延迟导致 syncSeqId 没能在本帧回来，客户端会在 cancelDraw/mNumPausedForSync 处跳过本帧（3793-3805、3943-3952）。

边界上要注意：relayout 的返回不等于窗口已经可见或已经上屏。WMS 只是把 frame/insets/SurfaceControl 状态算好并通过 performSurfacePlacement 排了事务，真正的 layer 位置由 SurfaceFlinger 在下一个合成周期应用。客户端后续的 measure/layout 只依赖 frame，不依赖 binder 之外的东西。

排障：relayout 相关现象的定位方法

用 MeasureSpec 把窗口约束传下去算出尺寸，再用两趟 layout 把位置定下来——多一趟就多一份掉帧风险

performTraversals 在 relayout 之前先调 measureHierarchy（base/core/java/android/view/ViewRootImpl.java:3625），它用 getRootMeasureSpec（5704）把窗口约束翻译成根节点的 MeasureSpec：MATCH_PARENT 给 EXACTLY(windowSize)，WRAP_CONTENT 给 AT_MOST(windowSize)，其它给 EXACTLY(指定值)；然后 performMeasure（5472）在一段 "measure" trace 里调 mView.measure，View.measure（base/core/java/android/view/View.java:28787）先查 mMeasureCache（key 是宽高 spec 拼成的 long），未命中才走 onMeasure，并置 PFLAG_LAYOUT_REQUIRED。relayout 回来后如果 frame 变了会再 measure 一次，随后 performLayout（5538）在一段 "layout" trace 里调 host.layout(0,0,mw,mh)；View.layout（View.java:26040）先 setFrame、再 onLayout。若 layout 期间有 view 调 requestLayout，performLayout 会清标志、置 mHandlingLayoutInLayoutRequest、再跑第二趟 measure+layout；第二趟里还在请求的，只能 post 到下一帧。它同时也是 View 世界里唯一能“用约束换结果”的地方：同样的像素尺寸，可以由完全不同的树、以完全不同的代价算出来。它本质上是一场关于预算的分配：预算越紧，越要避免无谓的第二趟。

MeasureSpec 从哪来：窗口约束翻译成 32 位整数

measure 的根约束来自 measureHierarchy 里的两次 getRootMeasureSpec（ViewRootImpl.java:3651-3653、3679-3682）。getRootMeasureSpec(windowSize, measurement, privateFlags)（5704-5730）的映射规则是：MATCH_PARENT → MeasureSpec.makeMeasureSpec(windowSize, EXACTLY)；WRAP_CONTENT → AT_MOST(windowSize)；其它具体数值 → EXACTLY(rootDimension)。MeasureSpec 本身把 mode 放在高 2 位、size 放在低 30 位，View.measure 里就把它当成一个 long 的 key 用（(long) widthMeasureSpec << 32 | heightMeasureSpec，View.java:28798）。

为什么 WRAP_CONTENT 的对话框要测两次（3637-3675）：大屏上不希望一个只有一行文字的对话框拉满全屏，所以先按 config_prefDialogWidth 的小尺寸测一次，若结果带 MEASURED_STATE_TOO_SMALL 就取 (baseSize+desiredWindowWidth)/2 再测一次；两次都不满足才落入 !goodMeasure 分支用整个窗口尺寸测（3678-3695）。这是“measure 可能跑多次”的第一个来源。

performMeasure 与 View.measure：缓存、forceLayout 与补测

performMeasure（5472-5485）非常薄：包一段名为 "measure" 的 trace、调 mView.measure(childWidthMeasureSpec, childHeightMeasureSpec)，再把结果存进 mMeasuredWidth/mMeasuredHeight（供 relayout 的 requestedWidth/Height 使用），并清掉 mViewMeasureDeferred。真正复杂的是 View.measure：

  • 先按 optical insets 调整 spec（28788-28795，只影响光学边界）。
  • 算 forceLayout（看 PFLAG_FORCE_LAYOUT）与 needsLayout（spec 变了且不满足 EXACTLY 且尺寸没对上，28806-28813），二者都不成立时直接跳过 onMeasure。
  • 查 mMeasureCache（LongSparseLongArray，key 是宽高 spec，value 是宽高结果）：命中则 setMeasuredDimensionRaw 并置 PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT（28845-28850），让 View.layout 在真正摆放前补一次 onMeasure（View.java:26041-26050）。
  • 未命中才带 onMeasure trace 调 onMeasure，最后校验 PFLAG_MEASURED_DIMENSION_SET 是否被置位，否则抛 IllegalStateException（28854-28859）。

这些标志位（PFLAG_FORCE_LAYOUT/PFLAG_LAYOUT_REQUIRED/PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT）就是“同一帧里 measure 和 layout 如何互相补偿”的全部机制。

layout：先 setFrame 再 onLayout，两趟上限怎么来的

performLayout（5538-5611）先置 mInLayout = true，包一段名为 "layout" 的 trace，然后 host.layout(0, 0, host.getMeasuredWidth(), host.getMeasuredHeight())（5554）。View.layout（View.java:26040-26100）做三件事：（1） 若有 PFLAG3_MEASURE_NEEDED_BEFORE_LAYOUT 先补测（26041-26050）；（2） setOpticalFrame 或 setFrame 把 l/t/r/b 落到 mLeft/mTop/... 并返回是否变化（26057-26058）；（3） 若 changed 或 PFLAG_LAYOUT_REQUIRED 还在，就调 onLayout(changed, l, t, r, b) 并清标志（26060-26077）。ViewGroup.layout（ViewGroup.java:6590-6599）多一层保护：如果正在做 transition 且 isChangingLayout()，就把这次 layout 记成 mLayoutCalledWhileSuppressed，等 transition 结束再补。

两趟上限：回到 performLayout，host.layout 返回后若 mLayoutRequesters 非空（说明 layout 期间有人调了 requestLayout），用 getValidLayoutRequesters 过滤出仍有 PFLAG_FORCE_LAYOUT 的 view，置 mHandlingLayoutInLayoutRequest = true 后重新 requestLayout + measureHierarchy + host.layout（5565-5584）。这是第二趟，也是最后一趟：第二趟里任何新的请求都会被 requestLayoutDuringLayout 返回 false（走下一帧），并在 5588-5604 被 getRunQueue().post(...) 推迟。源码注释明确写了“posted to the next frame to avoid possible infinite loops”。

requestLayoutDuringLayout：为什么 layout 里 requestLayout 是危险动作

requestLayoutDuringLayout（5519-5536）的逻辑就是两句话：（1） 把发起者记进 mLayoutRequesters；（2） 若当前不在第二趟（!mHandlingLayoutInLayoutRequest）就放行，让它在第二趟里被处理；若已经在第二趟，则返回 false，View.requestLayout 随后会把它 post 到下一帧。

所以 requestLayout 在 layout 中并非被禁止，而是被“限流”：一帧最多两趟 measure/layout，超过的推到下一帧。这条约束是 Android 保证 layout 收敛（不会无限重排）的核心。副作用是：如果某个自定义 ViewGroup 每趟都让子 View 请求 layout，它会稳定地在下一帧再触发一次 traversal，形成持续两帧周期的高开销。

measure/layout 与 relayout、draw 的先后关系

performTraversals 里这一拍被夹在两件事中间：前面是 relayout（4241），后面是 draw（4903 调 performDraw）。完整顺序是：

  1. measureHierarchy（4099）用旧 frame 推的 desiredWindowWidth/Height 先测一版；
  2. relayoutWindow（4241）把尺寸交给 WMS 并取回真实 frame；
  3. frame 变了就再 performMeasure（4556-4599，含 lp.horizontalWeight/verticalWeight 情形下的“再测一次”）；
  4. performLayout（4638）用最终 mWidth/mHeight 摆放；
  5. performDraw（4903）录制 DisplayList。

这意味着 measure/layout 的输入可能迟于最开始那次 measure，一次 traversal 里 measure 跑 2~3 次是正常的；判断“测量是否浪费”要看是否有重复的 measure slice 且 spec 未变（那才是 mMeasureCache 没挡住或 PFLAG_FORCE_LAYOUT 被误设）。

deadline：这一拍为什么最容易吃掉 jank 预算

measure 与 layout 都在 UI 线程、都在 FrameInfo[PERFORM_TRAVERSALS_START] 与 FrameInfo[DRAW_START] 之间，必须赶在 FrameInfo[FRAME_DEADLINE] 之前结束，否则这一帧会被 FrameTimeline 记为 jank。它们的耗时特征与绘制不同：

  • 与节点数线性相关：ViewGroup.measureChildren（ViewGroup.java:7111-7123）对每个非 GONE 子 view 调 measureChild，后者用 getChildMeasureSpec 扣掉 padding 再递归；布局嵌套越深，递归越深。
  • WRAP_CONTENT 是放大器：它会让父容器对子 view 用 AT_MOST 测一遍、必要时再按实际尺寸测第二遍，子树的 measure 次数翻倍。
  • 两趟 layout 是乘法项：第二趟会重新 measureHierarchy + layout 整棵树，等于一帧里跑了两遍 traversal 的主体。

因此线上“UI 线程卡在 measure/layout”的典型原因不是代码慢，而是树太深、wrap_content 太多、或者有 ViewGroup 反复触发 requestLayout。

排障：怎么确认是 measure 还是 layout 在吃时间

  • trace 里 measure 与 layout 是一对兄弟 slice（5476、5552），先看哪个更长；再往下看 onMeasure/onLayout（ViewTraversalTracingStrings.java:49-51 定义的 tag）定位到具体 View 类名。
  • 日志里出现 “requestLayout() improperly called by … during layout: running second layout pass”（5575-5576）就说明有一趟额外的 measure+layout，直接对应一次性能回退。
  • 第二趟仍不收敛时会出现 “… during second layout pass: posting in next frame”（5598-5599），意味着每帧都会重复一次 traversal，属于严重问题。
  • 对比 FrameInfo[PERFORM_TRAVERSALS_START] 与 FrameInfo[DRAW_START]（FrameInfo.java:83-86）可得到“measure+layout+其余逻辑”的总时长，与 measure+layout 两个 slice 的差值就是 traversal 里其它开销。

canvas.drawRenderNode(...) 不是把子树的绘制指令“拷贝”进根 DisplayList，而是在根 DisplayList 里放一个引用子 RenderNode 的绘制条目；真正的树结构与层级由 RenderNode 之间的父子关系表达。这就是“DisplayList 树”而不是“一条扁平指令流”的原因。

View.updateDisplayListIfDirty：脏才重录，软层走位图

View.updateDisplayListIfDirty（View.java:24306-24395）的判定是三个条件的或：PFLAG_DRAWING_CACHE_VALID 为 0、!renderNode.hasDisplayList()、mRecreateDisplayList（24313-24315）。三者都不成立时直接标脏位返回，不做任何录制。

需要重录时还有一次短路：renderNode.hasDisplayList() && !mRecreateDisplayList 时只 dispatchGetDisplayList() 让子树复用已有 DisplayList（24318-24324）。否则进真正录制：width = mRight - mLeft、height = mBottom - mTop（24331-24332），renderNode.clearStretch()，beginRecording(width, height)（24339），然后分两条：

  • LAYER_TYPE_SOFTWARE：buildDrawingCache(true) 拿到 Bitmap，canvas.drawBitmap(cache, 0, 0, mLayerPaint)（24342-24347）——软件层本质是把内容先画进位图，再作为一张图参与硬件合成。
  • 普通路径：computeScroll()、canvas.translate(-mScrollX, -mScrollY) 并清脏位，然后若 PFLAG_SKIP_DRAW 置位就只 dispatchDraw(canvas)（无背景的容器快路径），否则 draw(canvas)（24348-24369）。

最后 finally 里 renderNode.endRecording() 与 setDisplayListProperties(renderNode)（24376-24379）——后者把 alpha/transform/clip 等 View 属性写到 RenderNode 上，这些属性在 RT 的 prepareTree 里才会被消费。

软件路径与硬件路径的本质差别

软件路径在 drawSoftware（6395-6460）里：mSurface.lockCanvas(dirty) 拿到一块可写的 buffer，canvas.drawColor(0, PorterDuff.Mode.CLEAR) 必要时清屏，mView.draw(canvas) 直接把绘制指令写进这块内存，最后 surface.unlockCanvasAndPost(canvas) 提交。这条路径没有 DisplayList、没有 RenderNode、没有 RenderThread，脏区就是传进去的 dirty，绘制与提交都在 UI 线程完成。

硬件路径则只产出数据结构：RenderNode 树 + 每层的 DisplayList + 属性；UI 线程不碰像素，也不计算最终 damage。两者的分界就是 isHardwareEnabled()（6260）：它本质上在问“这个窗口是否挂着 ThreadedRenderer 且有有效 surface”。理解这一点才能正确解释“为什么硬件路径下 UI 线程几乎没有 GPU 相关耗时”。

damage 与 pixel 都不在这一拍产生

本阶段最容易误解的是“draw 会算出脏区”。实际上：UI 只是把 mDirty 当作“要不要跑这一趟”的开关，进入硬件路径后立刻 dirty.setEmpty()（6278）。真正的帧级脏区来自 RT 侧 prepareTree 中 DamageAccumulator 的累积，RenderNode 上记录的属性变化、动画值、DisplayList 重录都会在那里变成 damage。

因此本阶段的可观测产物只有三样：RenderNode 树的结构变化、DisplayList 的重录次数、以及 mRootNode 是否被重新录制（mRootNodeNeedsUpdate）。像素什么时候出现、出现在哪块区域，要等 RT 的 draw 与 SF 的合成。

ThreadedRenderer.draw（827-859）在 updateRootDisplayList 之后调 attachInfo.mViewRootImpl.getUpdatedFrameInfo()（846）。getUpdatedFrameInfo（ViewRootImpl.java:723-732）做的是“合并”：

Choreographer 已经填好了 vsync 相关槽位（FRAME_TIMELINE_VSYNC_ID、INTENDED_VSYNC、VSYNC、FRAME_DEADLINE、FRAME_START_TIME、FRAME_INTERVAL、ANIMATION_TIME 等，见 FrameInfo.setVsync 111-119），而 ViewFrameInfo.populateFrameInfo（ViewFrameInfo.java:45-49）只补三样：FLAGS、DRAW_START、INPUT_EVENT_ID，随后 reset() 清空避免污染下一帧。

postAndWait：UI 线程在这里真正被挂起

RenderProxy::syncAndDrawFrame（RenderProxy.cpp:237-239）只转一手：return mDrawFrameTask.drawFrame();。DrawFrameTask::drawFrame（DrawFrameTask.cpp:72-80）做三件事：把 mSyncResult 重置为 SyncResult::OK；记 mSyncQueued = systemTime(SYSTEM_TIME_MONOTONIC)（76）；调 postAndWait()。

postAndWait（82-87）就是交棒点：

AutoMutex _lock(mLock);
mRenderThread->queue().post([this]() { run(); });
mSignal.wait(mLock);

先把 run() 投进 RenderThread 的 TaskQueue，再在条件变量 mSignal 上等待。此时 UI 线程的状态是“已把工作交出去、但还不能继续做下一帧的 traversal”，直到 RT 侧的 run() 调 unblockUiThread()（DrawFrameTask.cpp:219-222）mSignal.signal() 才被唤醒。是否提前放行取决于 syncFrameState 是否需要 UI 线程配合（后面 RT 专题展开）。

边界：UI 阻塞窗口里 RT 在做什么

post 之后、run() 真正执行之前，任务只是躺在 TaskQueue 里，RT 可能正在处理上一帧的绘制或动画。这段排队时间是可观测的：run() 的第一件事就是 mContext->setSyncDelayDuration(systemTime(SYSTEM_TIME_MONOTONIC) - mSyncQueued)（93），也就是“从 UI 交棒到 RT 开始同步”的延迟，随后会被记进 FrameInfo 的 SyncQueued→SyncStart 区间。

因此“UI 线程在 postAndWait 阻塞”并不等于“RT 正在为这帧干活”：

  • RT 空闲：阻塞时间 ≈ syncFrameState（prepareTree）时长。
  • RT 正在画上一帧：阻塞时间 = 上一帧剩余工作 + 本帧 prepareTree，这就是经典的“UI 被 RT 拖住”。
  • RT 侧发现 surface 丢了/不能画：syncResult 里带 SYNC_LOST_SURFACE_REWARD_IF_FOUND，UI 侧会强制下一次 relayout（ThreadedRenderer.java:849-855）。

本阶段的边界就到 mSignal.wait() 为止：之后发生的一切（syncFrameState、prepareTree、Skia 提交、BLAST queueBuffer）都不在 UI 线程。

换句话说，UI 线程在这一刻之后就只能等：它能观测到的只有返回值与两个时间戳（交棒时刻、被唤醒时刻）。任何“顺手再做点事”的优化念头都必须放到交棒之前实现，一旦进入 mSignal.wait()，UI 侧已无牌可打。这也是为什么所有 UI 线程优化最终都落在减少 invalidate、简化 View 树、收敛 measure/layout 这三件事上。

返回值：SyncResult 位掩码如何影响下一帧

DrawFrameTask::drawFrame 返回 mSyncResult，它在 syncFrameState 里被置位（RT 侧）。ThreadedRenderer.draw 只关心两个位：

  • SYNC_LOST_SURFACE_REWARD_IF_FOUND：surface 丢了，于是 mForceNextWindowRelayout = true 并 requestLayout()（849-855），下一帧会重新 relayout 拿新 SurfaceControl。
  • SYNC_REDRAW_REQUESTED：RT 需要再画一帧，于是 mViewRootImpl.invalidate()（856-858）。

此外 RT 侧还可能带 SYNC_FRAME_DROPPED、SYNC_CONTEXT_IS_STOPPED、SYNC_REDRAW_REQUESTED 等位，它们通过 mSyncResult 一次性回传，避免多次跨线程往返。这个设计让 UI 线程只需要一次阻塞就能拿到“这一帧到底怎么了”的全部结论。

deadline：交棒晚了会怎样

从 Choreographer 分配 vsync 到 UI 完成 traversal 有明确预算（FrameInfo[FRAME_DEADLINE]）。本阶段处在预算末端：measure、layout、draw 录制都已完成，剩下的是把树同步给 RT 并让 RT 产出 buffer。如果 mSignal.wait 太长，RT 拿到树的时刻就已接近 deadline，绘制与提交必然赶不上这个 vsync——FrameTimeline 上表现为 SyncStart 偏晚、FrameCompleted 超过 FrameDeadline。

反过来说，UI 线程这一端唯一能优化的是减少交棒前后自身的工作（录制量、无效 invalidate、冗余 traversal）；一旦进入 mSignal.wait，UI 线程本身已经没有可优化项，只能靠缩短 RT 的 syncFrameState 或降低 RT 队列排队。

排障：交棒阶段的观测与常见误解

  • 看 UI 阻塞时长：perfetto 上 UI 线程在 nSyncAndDrawFrame/postAndWait 的原地等待（jstack 里是 DrawFrameTask.postAndWait 的 wait），与 RT 侧 DrawFrames <vsyncId> slice 的起点对齐即可算出排队延迟。
  • 看排队延迟：setSyncDelayDuration(systemTime - mSyncQueued)（93）会进入 FrameInfo 的 SyncQueued→SyncStart，dumpsys gfxinfo / FrameTimeline 可见。
  • 看长度断言：JNI 里 UI_THREAD_FRAME_INFO_SIZE 不匹配是 LOG_ALWAYS_FATAL，Java 侧 FrameInfo 与 native FrameInfo.h 不同步会直接 crash 而不是 jank。
  • 误解一：syncAndDrawFrame 返回就代表帧画完了——不是，它只代表树同步与任务提交阶段告一段落，buffer 是否产出要看 RT 侧结果。
  • 误解二：UI 线程阻塞是 RT 慢——也可能只是 RT 队列里还有上一帧；两者在 trace 上是不同区间。
