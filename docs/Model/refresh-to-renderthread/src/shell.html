ONE UI FRAME · EIGHT STAGES

一句话版本：requestLayout() 置 PFLAG_FORCE_LAYOUT|PFLAG_INVALIDATED， invalidate() 置 PFLAG_INVALIDATED；两者沿父链冒泡到 ViewRootImpl， 被 mTraversalScheduled 合并成一次 traversal。UI 线程插入同步屏障，并通过 Choreographer.postVsyncCallback(CALLBACK_TRAVERSAL) 预约 APP VSYNC。 VSYNC 到达后 doFrame 按 INPUT→ANIMATION→INSETS_ANIMATION→TRAVERSAL→COMMIT 派发， traversal 进入 performTraversals()：relayoutWindow 向 WMS 要窗口 frame/insets， measure/layout 自顶向下遍历，draw 把绘制指令录进 RenderNode 的 DisplayList， 最后 syncAndDrawFrame() 把 FrameInfo 与显示列表投给 RenderThread。

01requestLayout 只是“登记”

它不会立即 measure，只置脏标记并向上冒泡。真正的遍历由 ViewRootImpl 合并、Choreographer 预约，等 VSYNC 才执行。

02同步屏障让 traversal 抢先

scheduleTraversals 用 postSyncBarrier() 把 traversal 插到所有同步消息之前；没有它，doFrame 可能被业务 Handler 消息拖后。

03draw 只负责录制

UI 线程的 draw 把绘制指令写进 RenderNode 的 DisplayList，真正 GPU 回放发生在 RenderThread；交棒点是 syncAndDrawFrame()。

03 / WAIT POINTS & MERGES

这条链上，UI 线程到底在等什么

刷新链的耗时不只是 measure/layout/draw。同步屏障、VSYNC、WMS binder、两趟 layout 与 RT 交棒都是明确的等待/合并点； 看 trace 时要把它们分开。

VSYNC 等待通常占掉这一帧的大部分墙钟时间；真正在 UI 线程上执行的是 scheduleTraversals、doFrame/traversal、WMS relayout、measure/layout、draw 录制与交棒前等待。

A同步屏障：让 traversal 插队

scheduleTraversals() 在 MessageQueue 上插入 sync barrier，使 Choreographer 的 traversal 回调优先于普通同步消息执行；doTraversal 时移除屏障。否则一条业务 Handler 消息就可能把这一帧拖过截止线。

B两趟 layout 的边界

layout 过程中再次 requestLayout() 会触发第二趟 layout；ViewRootImpl 有 mHandlingLayoutInLayoutRequest 上限，第二趟仍触发就推迟到下一帧，避免无限循环。

Cdraw 只是录制，交棒才阻塞

UI 的 draw 只把绘制指令录进 DisplayList；syncAndDrawFrame 才进入跨线程同步点。RT 的 GPU 回放与 swap 在下一站，不在本页范围。
