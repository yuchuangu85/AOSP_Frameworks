渲染不是一条直线，
而是一条被 VSYNC 驱动的流水线

应用进程负责“生产”一帧，SurfaceFlinger 负责“消费并合成”一帧，显示硬件在固定的节拍上扫描输出。 真正决定体验的，不是某一段代码有多快，而是每一段能否在 VSYNC 截止时间前完成交接。

APP PROCESS → SF PROCESS → DISPLAY
ONE FRAME · TWO BOUNDARIES

一句话版本：UI 线程把“需要重绘”变成一次 traversal 预约；Choreographer 等到 APP VSYNC 才执行它； measure/layout 之后，draw 只是把绘制指令录进 RenderNode 的 DisplayList； RenderThread 提交 GPU 命令，应用侧 BLAST 消费 BufferQueue，并把 GraphicBuffer 与 acquire fence 通过 Transaction 交给 SurfaceFlinger； SF 在目标 SF VSYNC 相位检查事务并合成、交给 HWC；present fence 描述异步呈现完成，旧 buffer 的归还与安全复用由 release 路径和 fence 依赖控制。 本页默认 appWorkDuration + sfWorkDuration ≤ 一个周期，APP 绘制与 SF 合成落在同一帧内；实际相位由设备配置决定（见“相位的意义”）。

01为什么必须等 VSYNC？

普通 View 更新由 Choreographer 对齐节拍并合并请求；是否撕裂还取决于 buffer 交接与显示同步，不能说离开 VSYNC 就必然撕裂。这里用请求 → APP 唤醒 → SF 接纳事务 → 显示节拍表示流水线主链。

02draw 不等于画完

UI 线程的 draw 只负责把绘制指令记录为 DisplayList；RenderThread 的 CanvasContext::draw 才真正提交 GPU，并通过 BufferQueue 把 buffer 交给 SF。

03卡顿是“交接失败”

一帧掉落，往往不是某段代码慢，而是 queueBuffer 晚于 SF 的取帧时刻，或 SF 合成超过预算。看 trace 时要找“哪一段越过了哪个 VSYNC”。

    03 / LATENCY MODEL

    上屏延迟：那 2~3 个 VSYNC 花在哪了

    把每一段的交接时间相加，就得到从“用户操作/业务调用”到“像素可见”的延迟。它不是单个函数的耗时，而是流水线中每个等待点的总和。

    T_visible ≈ Σ QUEUEING + Σ WORK
    60 HZ → 16.67 MS / TICK
    T0 · 触发requestLayout / invalidate
    0 ms
    APP VSYNCChoreographer.doFrame → traversal 开始
    16.7 ms
    APP 工作 + queueBuffermeasure / layout / record / GPU / BLAST
    ≈ 25 ms
    SF VSYNC · 合成 + presentAPP 唤醒 + appWorkDuration
    ≈ 28 ms
    DISPLAY VSYNC · V2 上屏present fence · 开始扫描输出
    33.3 ms
    V3 · 后续帧呈现旧 buffer 的 release fence signal 示例
    ≈ 50 ms

    上图仅是一组累计延迟示例，不是固定 2~3 拍的保证。事务未赶上接纳时机可能延后；acquire fence 晚于唤醒时，仍需结合未完成 latch 条件与后续 GPU 依赖判断。release 回传可以早于这里画出的 signal 时刻，重新 dequeue 也不等于可立即覆盖像素。

    A为什么不是“越快越好”，而是“对齐节拍”

    显示控制器按固定周期扫描 framebuffer。若在扫描中途替换内容会撕裂；若生产完成得太晚，SF 只能重复上一帧。VSYNC 把连续时间离散化，所有生产者/消费者都对齐到同一组节拍上。

    B三缓冲买到的是“生产窗口”，不是“零延迟”

    本页选择三个 slot 作为直观示例；真实容量由 maxAcquiredBufferCount、maxDequeuedBufferCount、异步模式与配置共同决定。更多可用 buffer 能增加流水线重叠，也可能增加排队延迟，并不固定多一拍。

    C相位的意义：相位差 = appWorkDuration，由配置决定

    APP 与 SF 的唤醒点都从同一个预期上屏时刻倒推，二者相差 appWorkDuration。appWorkDuration + sfWorkDuration ≤ 一个周期时（如本页的 8.3ms + 8.3ms），APP 画完、SF 同周期合成、下一拍上屏；本帧赶不上 SF 唤醒才顺延一个周期。

    配置来源：代码默认是 PhaseOffsets（周期 ≥15ms 时 app = sf = 1ms，高刷时 app = 2ms、sf = 1ms），换算后 APP 唤醒到上屏 60Hz 约 2P、高刷约 3P；设置 debug.sf.use_phase_offsets_as_durations 后改用 WorkDuration，运行时还可被 DisplayModeSpecs.workDuration 覆盖，VsyncModulator 会在 late / early / earlyGpu 之间切换。真机用 dumpsys SurfaceFlinger --vsync 查看。

    实际队列主状态为 FREE → DEQUEUED → QUEUED → ACQUIRED → FREE，另有 SHARED 模式。现代窗口的消费者是应用侧 BLAST；SF latch 与显示不是 BufferQueue slot 状态。下面保留主链示意，但把队列所有权与 SF 的使用分开：release 可把 slot 归还，下一次写入仍须遵守随 dequeue 返回的 fence。

    04 / JANK & DEADLINES

    掉帧：不是“慢”，而是“晚于截止线”

    本例的 appWorkDuration 为约 8 ms，不是 60Hz 设备的统一预算。错过事务接纳时机可能延后显示，但“晚显示”与“从未显示而被丢弃”不同；GPU fence 晚于 SF 唤醒也不必然错过呈现。真实 jank 还需 FrameTimeline 的预测、阈值与状态共同判断。

    FRAME TIMELINE + TRACE
    区分接纳、呈现、丢弃与依赖等待

    UI 线程：traversal 超预算

    • 层级过深 / 重复 measure：performMeasure 与 performLayout 耗时上升。
    • 绘制指令过多：draw 录制 DisplayList 变慢，RenderNode 树过大。
    • 主线程被 Input、Binder、业务逻辑占用，doFrame 被推迟。
    • 典型证据：Choreographer#doFrame 或 traversal 回调变长，随后出现 skipped frame 告警。

    RenderThread / GPU：绘制与提交超预算

    • GPU 负载过高（过度绘制、大图、复杂 Shader），CanvasContext::draw 拉长。
    • dequeueBuffer 等不到 free slot：队列被 SF 占满，生产者阻塞。
    • queueBuffer 晚于本帧 SF 相位：BLAST Transaction 只能等下一帧 SF 相位。
    • 典型证据：DrawFrame / GPU completion / BufferQueueProducer#queueBuffer 越过 SF VSYNC 相位与 DISPLAY V2。

    SurfaceFlinger：合成超预算

    • client composition 过多（GPU 合成），RenderEngine 耗时增加。
    • 事务因 acquire fence 未就绪留队，或先 latch 后在后续合成 / 呈现路径等待依赖。
    • 主线程被其它事务/回调占用，错过本次 refresh。
    • 典型证据：SF 的 commit / latch / composite / present 跨越 VSYNC。

    Buffer 与背压

    • 三缓冲被占满，app 的 dequeueBuffer 阻塞，UI 线程反过来被拖慢。
    • SF 长时间不 release，生产者没有空闲 slot。
    • 典型证据：结合实际队列容量、持有数量与 fence 状态检查 queueBuffer/dequeueBuffer 等待。

    把掉帧放进时间轴：打开“掉帧演示”，UI 线程的 measure/layout 与绘制时间被拉长，queueBuffer 越过本帧 SF VSYNC 相位与 DISPLAY V2，原本应在 V2 显示的帧要等下一帧 SF 相位合成、到 V3 才上屏，V2 只能重复上一帧。

    05 / OBSERVABILITY

    怎么在真机上看到这条流水线

    看 trace 的顺序建议：先确认“哪一帧”掉了（FrameTimeline / gfxinfo），再定位“哪一段”越过了哪个 VSYNC（Choreographer / DrawFrame / SF / HWC），最后才去优化具体代码。

    PERFETTO · FRAME TIMELINE
    DUMPSYS · TRACE TAGS
    采集一帧级 trace perfetto
    adb shell perfetto -o /data/misc/perfetto-traces/frame.perfetto-trace \
  -t 10s sched freq idle binder_driver \
  gfx view wm am surfaceflinger

    把 trace 拉回本地后用 Perfetto UI 打开；优先展开 Choreographer、DrawFrame、BufferQueue、SurfaceFlinger、HWC 的 slice。

    FrameTimeline / gfxinfo frame stats
    adb shell dumpsys gfxinfo <package> framestats
adb shell dumpsys SurfaceFlinger --timestats -dump
adb shell dumpsys SurfaceFlinger --latency <layer-name>

    framestats 给出每一帧各阶段耗时；SurfaceFlinger 的 timestats / latency 用于确认 present 与掉帧，而不是只看 app 侧。

    VSYNC 与刷新率 scheduler
    adb shell dumpsys SurfaceFlinger --vsync
adb shell dumpsys SurfaceFlinger --scheduler
adb shell dumpsys display

    看当前 display 的刷新率、vsync period、phase offset 与 layer 状态；判断是否是 SF 侧错过了取帧节拍。

    View 侧确认 view hierarchy
    adb shell dumpsys activity top
adb shell dumpsys gfxinfo <package> reset
adb shell dumpsys gfxinfo <package>

    结合 hierarchy 深度、invalidate 次数与 janky frames 比例，判断问题来自 measure/layout 还是绘制指令。
