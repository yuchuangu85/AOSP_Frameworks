01为什么必须等 VSYNC？

普通 View 更新由 Choreographer 对齐节拍并合并请求；是否撕裂还取决于 buffer 交接与显示同步，不能说离开 VSYNC 就必然撕裂。这里用请求 → APP 唤醒 → SF 接纳事务 → 显示节拍表示流水线主链。

02draw 不等于画完

UI 线程的 draw 只负责把绘制指令记录为 DisplayList；RenderThread 的 CanvasContext::draw 才真正提交 GPU，并通过 BufferQueue 把 buffer 交给 SF。

03卡顿是“交接失败”

一帧掉落，往往不是某段代码慢，而是 queueBuffer 晚于 SF 的取帧时刻，或 SF 合成超过预算。看 trace 时要找“哪一段越过了哪个 VSYNC”。

    01触发与调度：requestLayout 到 VSYNC

    UI 线程把一帧内的所有视图变更折叠成一次 traversal，再挂到下一拍 VSYNC 上

    一帧始于 UI 线程的 View.requestLayout()：清 mMeasureCache、置 PFLAG_FORCE_LAYOUT|PFLAG_INVALIDATED，沿 mParent 链冒泡到 ViewRootImpl，置 mLayoutRequested 并调 scheduleTraversals()。后者以 mTraversalScheduled 做闸门，先 postTraversalBarrier() 插同步屏障，再 postVsyncCallback(CALLBACK_TRAVERSAL, mTraversalCallback) 排队并异步申请 VSYNC。VSYNC 到达后 doFrame() 按 input、animation、insets_animation、traversal、commit 执行，TraversalCallback.onVsync(FrameData) 调 doTraversal() 解屏障进入 performTraversals()。本阶段不做 measure/draw，只负责合并与对齐。

    View.requestLayout()→ViewRootImpl.isInLayout() -> ViewRootImpl.requestLayoutDuringLayout(view)→View.mParent.requestLayout() // 沿父链冒泡，父节点已 requested 则短路→ViewRootImpl.requestLayout()→ViewRootImpl.scheduleTraversals()→ViewRootImpl.postTraversalBarrier() -> MessageQueue.postSyncBarrier()→Choreographer.postVsyncCallback(Choreographer.CALLBACK_TRAVERSAL, mTraversalCallback)→Choreographer.postCallbackDelayedInternal() -> scheduleFrameLocked() -> DisplayEventReceiver.scheduleVsync()→Choreographer.FrameDisplayEventReceiver.onVsync() // VSYNC 到达→Choreographer.doFrame()→Choreographer.doCallbacks(Choreographer.CALLBACK_TRAVERSAL)→ViewRootImpl.TraversalCallback.onVsync(FrameData)→ViewRootImpl.doTraversal(frameTimeNanos)→ViewRootImpl.performTraversals(frameTimeNanos)

    触发者：requestLayout 与 invalidate 是两条不同的链路

    UI 线程上一切视图变更最终只归结为两个诉求：重新布局和重新绘制。两者的入口不同，但在 ViewRootImpl 汇合。

    View.requestLayout()（View.java:28723）对本 View 做三件事：

    • 清空测量缓存 if (mMeasureCache != null) mMeasureCache.clear();（View.java:28730），保证下次 measure() 不命中过期结果；
    • 置位 PFLAG_FORCE_LAYOUT（0x00001000，View.java:2882）与 PFLAG_INVALIDATED（0x80000000，View.java:3000），见 View.java:28744-28745；
    • 向上冒泡：if (mParent != null && !mParent.isLayoutRequested()) mParent.requestLayout();（View.java:28747-28749）。

    冒泡的终止条件就是 isLayoutRequested()。ViewGroup 没有重写它，仍回落到 View.isLayoutRequested()（View.java:25972），检查的正是 PFLAG_FORCE_LAYOUT；ViewRootImpl 则把它重写为直接返回 mLayoutRequested（ViewRootImpl.java:2850-2853）。所以一次自底向上的冒泡在到达 ViewRootImpl.requestLayout() 后就把 mLayoutRequested 置 true 并停下，兄弟分支因为父节点已经 requested 而被短路。这是同一帧内成百上千次 requestLayout() 只产生一次 traversal 的第一层合并。

    invalidate() 走另一条路：View.invalidate()（View.java:21431）转调 invalidate(true)，再转 invalidateInternal(0, 0, mRight - mLeft, mBottom - mTop, invalidateCache, true)（View.java:21453）。它清 PFLAG_DRAWN（View.java:2864，清除点在 View.java:21474），置 PFLAG_DIRTY（View.java:2921，置位点在 View.java:21477），在 invalidateCache 为真时置 PFLAG_INVALIDATED 并清 PFLAG_DRAWING_CACHE_VALID，然后把脏矩形 damage 交给父容器 p.invalidateChild(this, damage)。硬件加速窗口（绝大多数情况）走快路径：ViewGroup.invalidateChild() 检测到 attachInfo.mHardwareAccelerated 后直接 onDescendantInvalidated(child, child) 并 return（ViewGroup.java:6245-6248），沿父链上传到 ViewRootImpl.onDescendantInvalidated()，再调 ViewRootImpl.invalidate()（ViewRootImpl.java:2864）；只有软件绘制时才逐级走 invalidateChildInParent() 累积脏区。ViewRootImpl.invalidate() 做的是：mDirty.set(0, 0, mWidth, mHeight); 并 if (!mWillDrawSoon) scheduleTraversals();。

    关键区别：requestLayout() 让 mLayoutRequested 为真，决定这一帧要不要 measure/layout；invalidate() 只写 mDirty，决定要不要 draw。两者都只调 scheduleTraversals()，都不会立刻执行任何测量或绘制。

    为什么不立刻 measure：把一帧对齐到 VSYNC

    如果 setText() 内部同步跑一遍 measure/layout/draw，那么一帧里 100 次属性修改就是 100 次全树遍历，而且绘制可能落在两个 VSYNC 之间，导致画面撕裂，或多个帧的内容被塞进同一个 buffer。AOSP 的做法是把一帧内的所有变更折叠成一次 traversal，并把它对齐到显示器的 VSYNC，这件事由 Choreographer 承担。

    完整调度链（除 scheduleVsync 外全部在本进程 UI 线程上同步执行）：

    1. ViewRootImpl.requestLayout()（ViewRootImpl.java:2842）：if (!mHandlingLayoutInLayoutRequest) { checkThread(); mLayoutRequested = true; scheduleTraversals(); }。
    2. ViewRootImpl.scheduleTraversals()（ViewRootImpl.java:3307）：mTraversalScheduled 是唯一的合并闸门，只有它为 false 时才置 true 并真正发帧。
    3. 先 postTraversalBarrier() 挂同步屏障，再 mChoreographer.postVsyncCallback(Choreographer.CALLBACK_TRAVERSAL, mTraversalCallback)（ViewRootImpl.java:3329-3331），最后 notifyRendererOfFramePending() 与 pokeDrawLockIfNeeded()。
    4. Choreographer.postVsyncCallback(int, VsyncCallback)（Choreographer.java:676）转调 postCallbackDelayedInternal()，把回调按 dueTime 插入 mCallbackQueues[callbackType] 的单向链表，然后 scheduleFrameLocked()。
    5. scheduleFrameLocked() 只在 !mFrameScheduled 时才 scheduleVsyncLocked()，进而 mDisplayEventReceiver.scheduleVsync()（Choreographer.java:918-931）。这是第二层合并：同一帧内 1000 次 scheduleTraversals() 也只会申请一次 VSYNC。底层是 native DisplayEventReceiver 经 BitTube 与 SurfaceFlinger 通信，这是本阶段唯一的跨进程交互，但它是异步的，不阻塞 UI 线程。
    6. VSYNC 到达后 FrameDisplayEventReceiver.onVsync() 把帧事件投递到 UI 线程的 FrameHandler，进入 Choreographer.doFrame()（Choreographer.java:1074）。
    7. doFrame() 按固定顺序执行回调队列（Choreographer.java:1201-1211）：CALLBACK_INPUT 之后是 CALLBACK_ANIMATION 与 CALLBACK_INSETS_ANIMATION，然后是 CALLBACK_TRAVERSAL，最后 CALLBACK_COMMIT。这个顺序保证输入先改变状态、动画先更新属性，最后才遍历视图树。
    8. ViewRootImpl.TraversalCallback.onVsync(FrameData) 取 frameData.getFrameTimeNanos() 调 doTraversal()，后者清 mTraversalScheduled、removeTraversalBarrier()，再进入 performTraversals(frameTimeNanos)。

    android17 与旧版本的重要差异：本仓库中已不存在 mTraversalRunnable 与 TraversalRunnable implements Runnable，取而代之的是 final class TraversalCallback implements Choreographer.VsyncCallback（ViewRootImpl.java:11445），回调签名是 void onVsync(@NonNull FrameData data)。Choreographer.postCallback(int, Runnable, Object)（Choreographer.java:590）仍然存在，但 traversal 不再走 Runnable 通道。按旧版本记忆去 grep mTraversalRunnable 会一无所获。

    同步屏障：让 traversal 抢在所有同步消息之前

    仅仅做到“下一个 VSYNC 执行”还不够。UI 线程是一个 MessageQueue，如果应用在 requestLayout() 之后又 Handler.post() 了 200 条同步消息，traversal 必须抢在它们前面执行，否则官方 API 契约就不成立。ViewRootImpl.java:3311-3328 那段注释明确写着这是 load-bearing 的行为，并给出了判定用例：setText() 之后 post() 的任务必须能看到新文本测量后的宽度。

    机制是同步屏障：mQueue.postSyncBarrier() 往队列插入一条 target == null 的特殊消息。MessageQueue.next() 一旦取到 msg.target == null，就跳过所有普通同步消息，只在链表中查找 msg.isAsynchronous() 为真的消息继续执行（CombinedMessageQueue/MessageQueue.java:982-988）。Choreographer 投递帧回调时对消息调用了 setAsynchronous(true)，所以 traversal 消息一定能穿过屏障优先执行。

    屏障必须成对释放：doTraversal() 中的 removeTraversalBarrier()（ViewRootImpl.java:3350）与 postTraversalBarrier()（ViewRootImpl.java:3355）配对。一旦泄漏，UI 线程上所有同步消息永久阻塞，表现是彻底卡死而不是单纯掉帧。

    android17 变化：ViewRootImpl 新增 mAtomicTraversalBarrier（ViewRootImpl.java:773，取自 Flags.atomicTraversalBarrier()）与 AtomicLong mTraversalBarrierAtomic（ViewRootImpl.java:771，未设置时值为 UNSET_TRAVERSAL_BARRIER = Long.MAX_VALUE，见 ViewRootImpl.java:369）。开启时用 getAndSet 原子替换屏障 token，并负责移除被覆盖的旧屏障，避免并发下 token 互相踩踏造成泄漏；未开启时才退回旧的 int mTraversalBarrier（ViewRootImpl.java:759，注释直言 not safe for concurrent access）。另外本仓库的 MessageQueue 已经从单文件拆成 base/core/java/android/os/CombinedMessageQueue/MessageQueue.java、base/core/java/android/os/CombinedDeliMessageQueue/MessageQueue.java 与 base/core/java/android/os/LegacyMessageQueue/MessageQueue.java，根目录的 base/core/java/android/os/MessageQueue.java 不存在，这是一个很容易踩空的路径陷阱。

    traversal 进行中再次 requestLayout：两趟上限与推迟到下一帧

    View.requestLayout() 的第一步就在检查是否正在布局（View.java:28732-28741）：只有 mAttachInfo.mViewRequestingLayout == null（即本次是请求源头而不是冒泡途中的父节点）时才查 viewRoot.isInLayout()，并调用 viewRoot.requestLayoutDuringLayout(this)；返回 false 就直接 return，连 PFLAG_FORCE_LAYOUT 都不置。

    ViewRootImpl.requestLayoutDuringLayout()（ViewRootImpl.java:5519）的规则是两趟上限：

    1. 第一趟 layout（mHandlingLayoutInLayoutRequest == false）中收到请求，就记入 mLayoutRequesters 并返回 true，允许请求继续冒泡；
    2. performLayout() 在 host.layout() 之后检查 mLayoutRequesters，若仍有真正还需要布局的 View（getValidLayoutRequesters()），就打印 Log.w("View", "requestLayout() improperly called by ... during layout: running second layout pass")，置 mHandlingLayoutInLayoutRequest = true（ViewRootImpl.java:5569），再跑一遍 measureHierarchy() 与 host.layout()；
    3. 第二趟中再来的请求返回 false，并通过 getRunQueue().post() 挪到下一帧，日志变成 during second layout pass: posting in next frame。

    同时 ViewRootImpl.requestLayout()（ViewRootImpl.java:2842-2848）在 mHandlingLayoutInLayoutRequest == true 时整段被跳过，所以第二趟不会再次 scheduleTraversals()，不会无限递归。这解释了为什么在 onLayout 里改布局只在同一帧多付一趟 layout 的开销，而不是死循环；代价是这一帧的布局时间翻倍，很容易顶穿 VSYNC deadline。

    与 VSYNC 的关系：deadline、jitter 与掉帧

    doTraversal(frameTimeNanos) 的入参就是 VSYNC 时间戳。Choreographer.doFrame() 用它计算 jitter：若 System.nanoTime() - frameTimeNanos >= frameIntervalNanos，说明这一帧已经错过自己的 VSYNC，代码把 frameTime 对齐到最近一个周期的边界，当 skippedFrames = jitterNanos / frameIntervalNanos 达到 SKIPPED_FRAME_WARNING_LIMIT（系统属性 debug.choreographer.skipwarning，默认 30，Choreographer.java:178-179）时才打印 Log.i(TAG, "Skipped N frames! The application may be doing too much work on its main thread.")（Choreographer.java:1133）。也就是说默认要连续错过 30 拍（60Hz 下约 0.5 s）才会有这条日志，少量掉帧不会出现在 logcat 里，要靠 trace 或 FrameMetrics 观察。

    本阶段自身几乎不耗时（置位、入队、一次 scheduleVsync），它的价值在于把后续 measure/layout/draw 精确对齐到某一个 VSYNC，并把该帧的 vsyncId、deadline、expectedPresentTime 记录进 FrameTimeline（mFrameData.update()，Choreographer.java:1107），供 FrameInfo 的 jank 统计与 perfetto 关联。ViewRootImpl.TraversalCallback 拿到的 FrameData 就是这套数据的新载体，取代了旧版本裸传 frameTimeNanos 的方式。

    观测上要抓住两个时间差：requestLayout 发生时刻到 doFrame 开始，这是等 VSYNC 的时间，正常不超过一个刷新周期；以及doFrame 开始到 traversal slice 结束，这是 app 侧真实工作量，必须小于到 deadline 的预算。前者大说明变更来得太晚、本帧赶不上，后者大说明 measure/layout/draw 本身太重。

    观测手段

    • atrace / perfetto：Choreographer#doFrame <vsyncId>（Choreographer.java:1109-1110）是帧起点，slice 名里带 vsyncId，可与 FrameTimeline 对齐；traversal（CALLBACK_TRACE_TITLES[3]，Choreographer.java:313-315，实际 trace 在 Choreographer.java:1245）是 traversal 回调自身的区间；Choreographer#scheduleVsyncLocked 标记申请 VSYNC 的时刻；requestLayoutTracing（View.java:28724-28727）在开启 relayout tracing 时会带上调用栈，直接定位谁在 requestLayout。
    • dumpsys：ViewRootImpl#dump 会打印 mTraversalScheduled=，为 true 时还会附带 (barrier=...)（ViewRootImpl.java:10746-10748），可以直接判断是否挂着一帧没跑以及当前屏障 token。注意 dump 打印的是旧的 int mTraversalBarrier；mAtomicTraversalBarrier 开启时屏障 token 记在 mTraversalBarrierAtomic 里，mTraversalBarrier 不再更新，此时 barrier= 的值不能用来判断屏障泄漏。

    SF 侧状态机：VSyncRequest 与“请求一次只发一次”

    EventThread::requestNextVsync()（EventThread.cpp:417）先 mCallback.resync(...) 让调度器与硬件重新对齐，再加锁改状态：None → Single 并 mCondition.notify_all() 唤醒 threadMain；若当前是 SingleSuppressCallback 则改回 Single。第二分支对应“上一拍的 vsync 已派发出去、调度器还在为下一拍保持唤醒”的场景。

    真正的派发判定在 EventThread::shouldConsumeEvent()（EventThread.cpp:669-693）。这是“请求一次 vsync 只发一次事件”的实现位置：VSyncRequest::Single 命中一次 vsync 后并不归零，而是降级为 SingleSuppressCallback 并返回 true；下一拍再进来时 SingleSuppressCallback 分支把状态清成 None 并返回 false，于是不会重复投递。枚举注释把这个设计讲得很直白：Single “wakes up for the next two frames to avoid scheduler overhead”，SingleSuppressCallback “only wakes up for the next frame”。也就是说多出来的一拍只唤醒、不派发，目的是让 State::VSync 多维持一帧，避免反复 schedule()/cancel() 定时器带来的开销；如果 app 在这期间又请求，则被 requestNextVsync 拉回 Single 重新获得派发资格。

    定时器 vs 硬件：VSyncDispatchTimerQueue 与 VSyncPredictor

    EventThread 的 schedule() 最终进入 VSyncDispatchTimerQueueEntry::schedule()（VSyncDispatchTimerQueue.cpp:90）。这是“下一拍到底在哪一刻、什么时候唤醒线程”的唯一决策点：先算 nextVsyncTime = tracker.nextAnticipatedVSyncTimeFrom(max(lastVsync, now + workDuration + readyDuration), committedVsync)，再算 nextWakeupTime = nextVsyncTime - workDuration - readyDuration、nextReadyTime = nextVsyncTime - readyDuration，最后 mTimeKeeper->alarmAt(...) 把定时器设到 nextWakeupTime。

    workDuration 就是相位偏移的现代表达：它表示“线程要在 vsync 之前多久被叫醒并干完活”。Scheduler::setVsyncConfig()（Scheduler.cpp:802）把 config.appWorkDuration 作为 workDuration、config.sfWorkDuration 作为 readyDuration 喂给 app EventThread（setDuration(config.appWorkDuration, config.sfWorkDuration)），再把 config.sfWorkDuration 作为 SF 合成线程自己的 workDuration。也就是说：app 的唤醒提前量 = appWorkDuration + sfWorkDuration，前半段留给 app 画帧，后半段留给 SF 合成。这两个字段来自 VsyncConfiguration 的 VsyncConfigSet，分 early / earlyGpu / late 三套（VsyncModulator 依场景切换）。当前 debug.sf.use_phase_offsets_as_durations=false（默认）时工厂创建的是 impl::PhaseOffsets（SurfaceFlingerDefaultFactory.cpp:47-53），把 ro.surface_flinger.vsync_event_phase_offset_ns / ro.surface_flinger.vsync_sf_event_phase_offset_ns 以及 debug.sf.early_phase_offset_ns、debug.sf.high_fps_late_app_phase_offset_ns 等属性换算成 sfWorkDuration = vsyncDuration − sfOffset、appWorkDuration = vsyncDuration + (sfOffset − appOffset)（VsyncConfiguration.cpp:120-145、174-195）。头文件里 PhaseOffsets 被注明为 “old implementation … considered as deprecated”；属性置 true 时改用 impl::WorkDuration，直接把配置当 duration 并反算 offset（sfDurationToOffset/appDurationToOffset，VsyncConfiguration.cpp:275-288），且此时若仍设置上述 phase offset 属性会 LOG_ALWAYS_FATAL（validateSysprops()，同文件 245-275）。

    迟到的请求怎么处理：adjustVsyncIfNeeded()（同文件 132 行）拦两种情况——alreadyDispatchedForVsync（mLastDispatchTime 与目标 vsync 距离小于 mMinVsyncDistance，同一拍不能派发两次）和 nextVsyncTooClose（目标离上一拍不足一个 currentPeriod），两者都会让预测器从 mLastDispatchTime + 偏移 重新取“再下一拍”，即整体顺延一个周期而绝不挤在同一拍上。若目标比已 armed 的还晚（wouldSkipAVsyncTarget/wouldSkipAWakeup），则保持原 armed 计划不抖动。

    定时器补偿 vsync 的意义：硬件 vsync 是离散脉冲，若每次都等脉冲到了才干活，整条流水线必然晚一个周期，来不及在下一拍合成。因此需要“在预测出的未来 vsync 之前 N 微秒主动醒来”的能力，这就是 VSyncDispatchTimerQueue 存在的理由。timerCallback()（VSyncDispatchTimerQueue.cpp:334）在定时器到点时对每个 armed entry 判 wakeupTime < mIntendedWakeupTime + mTimerSlack + lagAllowance（lagAllowance = max(now − mIntendedWakeupTime, 0)，吸收线程被延迟唤醒的时延），再回调 EventThread::onVsync(vsyncTime, wakeupTime, readyTime)（EventThread.cpp:472）把 makeVSync() 推进 mPendingEvents。定时器负责“准点唤醒”，VSyncPredictor 负责“下一拍是哪一刻”，硬件 vsync 负责纠偏：HWC 回调进 SurfaceFlinger::onComposerHalVsync()（SurfaceFlinger.cpp:2535）→ Scheduler::addResyncSample()（Scheduler.cpp:978，VsyncTimeSource::HwVsyncCallback）→ VsyncSchedule::addResyncSample() → VSyncReactor::addHwVsyncTimestamp()（VSyncReactor.cpp:201）→ VSyncPredictor::addVsyncTimestamp()（VSyncPredictor.cpp:146）用环形缓冲 + 线性回归更新 period/slope，样本不足时以 idealPeriod 锚定。驱动卡死时 threadMain 还有兜底：mState == State::VSync 时 wait_for(1000ms) 超时会打印 “Faking VSYNC due to driver stall” 并伪造一个 vsync（State::SyntheticVSync 下是 16ms）。

    03VSYNC 送达：onVsync→doFrame

    BitTube 唤醒 UI 线程，一次 vsync 变成五段严格排序的回调：input → animation → insets → traversal → commit

    SF 的 app EventThread 在 dispatchEvent() 里为每个消费者补上 frameInterval 并生成多组 FrameTimeline，然后 EventThreadConnection::postEvent() 通过 BitTube（socketpair）把 DisplayEventReceiver::Event 写出去。app 侧的 native Looper 在 epoll 上等到 fd 可读，DisplayEventDispatcher::handleEvent() 一次性排空管道、只保留最后一个 vsync，再 dispatchVsync() → JNI → Java DisplayEventReceiver.dispatchVsync() → FrameDisplayEventReceiver.onVsync()。onVsync 不直接绘制，而是把 timestampNanos 转成一条异步 Message 投给 FrameHandler，由 UI 线程的 Looper 在 doFrame() 里执行：先算 jitter、必要时 resync 到下一拍、填 FrameInfo，再依次 doCallbacks(CALLBACK_INPUT) → CALLBACK_ANIMATION → CALLBACK_INSETS_ANIMATION → CALLBACK_TRAVERSAL → CALLBACK_COMMIT。vsyncId 全程跟随：SF 的 TokenManager 生成，经 VsyncEventData → FrameData → FrameTimeline.getVsyncId() 暴露给 app，再随 Transaction 回到 SF 的 FrameTimeline 做端到端比对。

    android::impl::EventThread::dispatchEvent() // 补 frameInterval + generateFrameTimeline→android::EventThreadConnection::postEvent()→android::DisplayEventReceiver::sendEvents()→android::gui::BitTube::sendObjects() // SOCK_SEQPACKET→android::Looper::pollInner() // epoll 唤醒 app UI 线程→android::DisplayEventDispatcher::handleEvent()→android::DisplayEventDispatcher::processPendingEvents()→android::NativeDisplayEventReceiver::dispatchVsync() // JNI CallVoidMethod→android.view.DisplayEventReceiver.dispatchVsync()→android.view.Choreographer$FrameDisplayEventReceiver.onVsync()→android.view.Choreographer$FrameHandler.handleMessage() // MSG_DO_FRAME→android.view.Choreographer$FrameDisplayEventReceiver.run()→android.view.Choreographer.doFrame()→android.view.Choreographer.doCallbacks()→android.view.ViewRootImpl.doTraversal() // CALLBACK_TRAVERSAL 内

    SF 侧出口：dispatchEvent 补全数据后写 BitTube

    EventThread::dispatchEvent()（EventThread.cpp:769）对每个消费者做两件事：先用 mCallback.getVsyncPeriod(consumer->mOwnerUid) 取该 uid 实际生效的 frame period（注意是 per-consumer，不同 uid 可以有不同帧率），写回 copy.vsync.vsyncData.frameInterval；再 generateFrameTimeline() 把 EventThread.cpp:712 的多 timeline 展开：以 preferred 那条为 multiplier == 0，向前后各展开若干条（容量 VsyncEventData::kFrameTimelinesCapacity = 7），deadlineTimestamp 必须大于本拍 timestamp 才有效，每条都通过 mTokenManager->generateTokenForPredictions()（FrameTimeline.cpp:1294）分配一个单调自增的 vsyncId，并登记到 SF 的 mPredictions 环形表里，供之后按 id 反查 deadline/expectedPresentationTime。

    写管道的是 EventThreadConnection::postEvent()（EventThread.cpp:283）：非 frame-rate-override 类事件先 mPendingEvents.emplace_back(event)，再 DisplayEventReceiver::sendEvents(&mChannel, mPendingEvents.data(), mPendingEvents.size())，即 gui::BitTube::sendObjects()（BitTube.cpp:148）。BitTube 是 socketpair(AF_UNIX, SOCK_SEQPACKET)（BitTube.cpp:49）——一条消息就是一个完整 Event，不会出现半个事件；源码里对 msg_nosignal 的部分写有断言注释提醒 “partial events were dropped” 只在异常时发生。返回 -EAGAIN（管道满）只打 ALOGW 不重试（源码注释 “TODO: Try again if pipe is full.”），EPIPE 等则把该连接从 EventThread 摘掉。

    app 侧入口：epoll 唤醒后的“排空 + 只留最后一个”

    执行线程在这里第一次切到 app：BitTube 的接收 fd 在 DisplayEventDispatcher::initialize()（native/libs/gui/DisplayEventDispatcher.cpp:53）里被 mLooper->addFd(mReceiver.getFd(), 0, Looper::EVENT_INPUT, …) 挂到 MessageQueue 自己的 native Looper 上，于是它的可读事件是在 app UI 线程执行 MessageQueue.nativePollOnce()（base/core/jni/android_os_MessageQueue.cpp:223，内部 mLooper->pollOnce()）时被 epoll 发现并派发的——也就是说 onVsync 的 C++ 部分跑在 UI 线程的 nativePollOnce 栈里，不是在 SF 线程。

    DisplayEventDispatcher::handleEvent()（同文件 113 行）先判 EVENT_ERROR|EVENT_HANGUP（管道对端消失，返回 0 移除回调）与 EVENT_INPUT，然后 processPendingEvents() 循环 recvObjects 直到读空，并且只保留最后一条 vsync（源码注释：“Later vsync events will just overwrite the info from earlier ones. That's fine, we only care about the most recent.”）。这意味着如果 app 主线程被卡了两拍，中间那拍的 vsync 会被静默丢弃，Choreographer 拿到的是最新一拍，靠 jitter 计算去感知跳帧。

    随后 mWaitingForVsync = false 并 dispatchVsync(timestamp, displayId, count, vsyncData)，JNI 侧 NativeDisplayEventReceiver::dispatchVsync 用 CallVoidMethod 回调 Java 的 DisplayEventReceiver.dispatchVsync()（DisplayEventReceiver.java:362），后者把 native 填充好的 mVsyncEventData 一起交给子类：onVsync(timestampNanos, physicalDisplayId, frame, mVsyncEventData)。兜底路径：若 mWaitingForVsync 仍为真且 now − mLastScheduleVsyncTime > WAITING_FOR_VSYNC_TIMEOUT（源码常量 300ms），会打 “Vsync time out!” 并用当前时间 + 空 vsyncData 伪造一次 dispatch；这个空数据在 doFrame 里会走到 frameIntervalNanos == 0 分支并打印 “Vsync data empty due to timeout”（Choreographer.java:1127）。

    onVsync 为什么还要绕一条 Handler 消息

    FrameDisplayEventReceiver.onVsync()（Choreographer.java:1594）刻意不在回调里直接跑帧逻辑，而是把事件转成一条 Message 投给 FrameHandler。源码注释给出了理由：防止源源不断的 vsync 事件把消息队列里的其他消息饿死；只有当队列里没有早于 frame time 的消息时，这条 vsync 消息才会被立刻处理，否则更早的普通消息先跑。

    三个容易漏的细节：

    • 若 timestampNanos > now（硬件时间基不对，落在未来），直接截断为 now 并仅在 DEBUG_JANK 下告警 “Check that graphics HAL is generating vsync timestamps using the correct timebase”，不会拒绝这一拍。
    • mHavePendingVsync 为真时只是打日志 “Already have a pending vsync event. There should only be one at a time.”，不会丢弃新事件，仍然覆盖 mTimestampNanos/mFrame/mLastVsyncEventData 并 post。
    • Message 用 msg.setAsynchronous(true) 且 sendMessageAtTime(msg, timestampNanos / NANOS_PER_MS)——投递时间等于 vsync 时刻，因此这条消息在队列里排在所有“本该在 vsync 之前完成”的消息之后。
    真正执行的是同一个类的 run()（Choreographer.java:1638）：mHavePendingVsync = false; doFrame(mTimestampNanos, mFrame, mLastVsyncEventData)。所以 onVsync → doFrame 之间隔着一次消息队列调度，主线程繁忙时会引入额外延迟，这正是 jitter 的来源之一。

    doFrame：jitter 修正、resync 与跳帧告警

    doFrame()（Choreographer.java:1074）先评估 buffer stuffing 状态，再用带 offset 的帧时间 mFrameData.update(offsetFrameTimeNanos, vsyncEventData) 填充 FrameData，并打上 Choreographer#doFrame <vsyncId> 的 trace。之后在 mLock 里做三件事：

    1. if (!mFrameScheduled) { traceMessage("Frame not scheduled"); return; }——这一拍在别处已经被消费（比如 FPSDivisor 或 frame-time 回退分支提前 return），直接丢掉。
    2. 算 jitter：jitterNanos = startNanos − frameTimeNanos（Choreographer.java:1123）。若 jitterNanos >= frameIntervalNanos，说明主线程已经错过至少一整拍：把 frameTimeNanos 重新对齐到 startNanos − (jitterNanos % frameIntervalNanos)，算出 skippedFrames = jitterNanos / frameIntervalNanos，达到 SKIPPED_FRAME_WARNING_LIMIT（属性 debug.choreographer.skipwarning，默认 30）就打印 “Skipped N frames! The application may be doing too much work on its main thread.”；然后 mFrameData.update(frameTimeNanos, mDisplayEventReceiver, jitterNanos) 重新挑 timeline（先在本地 7 条里找 deadline 不早于 原 deadline + jitter 的，找不到才 binder 调 getLatestVsyncEventData()，源码注释说明 binder 是 O(ms) 级、只在必要时用），并置 resynced = true，额外开一条 Choreographer#doFrame - resynced to %d in %.1fms 的 trace。
    3. 回退与降频判定：frameTimeNanos < mLastFrameTimeNanos 时视为时间倒退，仅打日志并 scheduleVsyncLocked() 等下一拍；mFPSDivisor > 1 时按 frameIntervalNanos * mFPSDivisor 跳过若干拍。

    都通过后调用 mFrameInfo.setVsync(intendedFrameTimeNanos, frameTimeNanos, vsyncEventData.preferredFrameTimeline().vsyncId, deadline, startNanos, frameInterval, frameTimeNanos)（Choreographer.java:1183，落到 android.graphics.FrameInfo 的 FRAME_TIMELINE_VSYNC_ID/INTENDED_VSYNC/VSYNC/FRAME_DEADLINE/… 槽位），然后 mFrameScheduled = false; mLastFrameTimeNanos = frameTimeNanos;，最后 AnimationUtils.lockAnimationClock() 并进入五段回调。

    五段回调的严格顺序与 vsyncId 的端到端传递

    顺序在 doFrame() 尾部硬编码（Choreographer.java:1199-1211）：CALLBACK_INPUT(0) → CALLBACK_ANIMATION(1) → CALLBACK_INSETS_ANIMATION(2) → CALLBACK_TRAVERSAL(3) → CALLBACK_COMMIT(4)，中间用 mFrameInfo.markInputHandlingStart()/markAnimationsStart()/markPerformTraversalsStart() 打三个时间戳（base/graphics/java/android/graphics/FrameInfo.java:123/128/133）。设计意图：input 可能触发动画，所以 input 先跑；animation 与 insets_animation 分开是因为 inset 动画要把多个 controller 的 setInsetsAndAlpha() 结果“攒”起来一次性下发给 view 树；traversal 负责 measure/layout/draw；commit 在 traversal 返回后执行帧后处理，不表示 GPU 已完成或画面已上屏。当前实现于五段回调前设置 mLastFrameTimeNanos（Choreographer.java:1188），doCallbacks() 没有 COMMIT 专用的 frame time 修正分支；CALLBACK_COMMIT 注释（Choreographer.java:354-360）仍保留“可能更新 frame time”的旧说明，不能据此认定当前执行体会在 commit 阶段补偿 traversal 延迟。

    doCallbacks()（Choreographer.java:1229）用 now = System.nanoTime() 而不是 frameTime 去 extractDueCallbacksLocked(now / NANOS_PER_MS)，源码注释解释了原因：一帧里更早的阶段可能 post 出本应属于后续阶段的回调（如 input 触发动画启动），用 now 判定才能让它们在同一帧的后续阶段执行；每次回调的 trace 名取自 CALLBACK_TRACE_TITLES = {"input", "animation", "insets_animation", "traversal", "commit"}（Choreographer.java:313）。

    vsyncId 怎么从 SF 到 app：SF 的 TokenManager 在 generateFrameTimeline 时分配 id → VsyncEventData::FrameTimeline.vsyncId 随 BitTube 到 app → JNI 用反射/缓存构造 DisplayEventReceiver.VsyncEventData.FrameTimeline 对象（createJavaVsyncEventData()，android_view_DisplayEventReceiver.cpp:164）→ Choreographer.FrameData.update() 逐个 FrameTimeline.update(vsyncId, expectedPresentationTime, deadline)（Choreographer.java:1484）→ 回调里通过 FrameData.getPreferredFrameTimeline().getVsyncId() 或 Choreographer.getVsyncId() 取出（后者在 mInDoFrameCallback 之外调用会返回未定义值并打 “unsync-vsync-id” 告警）。app 再把它交给 SF：SurfaceControl.Transaction.setFrameTimelineVsync(long)（SurfaceControl.java:5664，native 侧 nativeSetFrameTimelineVsync），本仓库可见的调用点是 InsetsAnimationThreadControlRunner（base/core/java/android/view/InsetsAnimationThreadControlRunner.java:108）；HWUI 里的调用点在 frameworks/libs/hwui，不在本仓库，源码中未体现。SF 收到后按 id 从 mPredictions 表里取出预测值，与实际 present fence 比对，据此判定 jank 类型（SurfaceFlinger 侧 FrameTimeline）。

    !坑点与边界
    onVsync 到达 ≠ 立刻 doFrame。onVsync 只是 post 一条消息；且消息按 timestampNanos 排序，只有当队列里没有更早的消息时才会立即执行。主线程繁忙时这段排队时间会直接变成 jitter，别把 onVsync 的时间戳当成帧开始时间。
    doFrame 的 frameTimeNanos 不等于硬件 vsync：jitter >= 一个 frameInterval 时它被重写成 startNanos 对齐到 period 的值（resync），buffer stuffing 恢复期还会再减一个 frameInterval。要硬件时间是 FrameInfo 的 INTENDED_VSYNC，或 SF 侧 atrace 的 VSYNC 轨道。
    processPendingEvents 只保留最后一个 vsync：主线程连续卡两拍时中间那拍被静默丢弃，不会补发；因此“掉帧”在 app 侧表现为一次大 jitter，而不是多条 doFrame。
    mHavePendingVsync 为 true 只打日志（"There should only be one at a time."），不会丢事件，所以 logcat 里看到它并不代表丢帧；真正的丢帧要结合 resync slice 与 skipped frames 判断。

    先向 WMS 做一次 relayout 拿到 frame、insets 与 SurfaceControl，再自顶向下 measure 与 layout

    入口：performTraversals 在什么条件下真正干活

    traversal 回调最终落在 ViewRootImpl.doTraversal(long frameTimeNanos)（ViewRootImpl.java:3347）：先清 mTraversalScheduled、removeTraversalBarrier()，再调 performTraversals(frameTimeNanos)（ViewRootImpl.java:3924）。入参是 VSYNC 时间戳，全程在 UI 线程同步执行。

    先量尺寸：measureHierarchy、getRootMeasureSpec 与 mViewMeasureDeferred

    measureHierarchy()（ViewRootImpl.java:3625）在这一帧里可能被调用两次：第一次在 relayout 之前（ViewRootImpl.java:4099），第二次在 mApplyInsetsRequested 触发重新 dispatch insets 之后（ViewRootImpl.java:4139）。它的逻辑分两支：

    • 当 lp.width == WRAP_CONTENT 时做对话框宽度试探：先按 config_prefDialogWidth 量一次，若结果带 MEASURED_STATE_TOO_SMALL，就用 (baseSize + desiredWindowWidth) / 2 再量一次。这是本帧内唯一会连续 performMeasure 两次的地方。
    • 否则直接 getRootMeasureSpec(desiredWindowWidth, lp.width, lp.privateFlags)（ViewRootImpl.java:5704）生成 root 的 spec：MATCH_PARENT 对应 EXACTLY(windowSize)，WRAP_CONTENT 对应 AT_MOST(windowSize)，固定值对应 EXACTLY(rootDimension)。

    预测量优化：当 forRootSizeOnly（即 shouldOptimizeMeasure）为真且两个 spec 都是 EXACTLY 时，setMeasuredRootSizeFromSpec()（ViewRootImpl.java:3713）只把 mMeasuredWidth/mMeasuredHeight 记下来并置 mViewMeasureDeferred = true，不真正 measure。真正测量被推迟到 relayout 拿到 frame 之后（ViewRootImpl.java:4597-4603，用 frame.width()/frame.height() 构造两个 EXACTLY spec 再调 performMeasure）。这样就避免了先用猜测尺寸量一遍、拿到真实 frame 再量一遍的双倍开销。

    注意因此在本版本中 measure 不一定发生在 relayout 之前，顺序取决于 shouldOptimizeMeasure 与 spec 是否双 EXACTLY。这一点与很多旧版本的线性叙述不同。

    耗时与掉帧风险

    • relayout 是同步 binder：一旦 canRelayoutAsync 判定失败（窗口位置或尺寸真的变了，例如旋转、分屏拖动、弹窗尺寸变化），UI 线程会阻塞在 mWindowSession.relayout2() 上，等待 WMS 在 mGlobalLock 下处理完。窗口动画、转场、其它窗口的 add/remove 都会和它抢同一把锁。
    • measure/layout 是 UI 线程上的同步递归：深度嵌套（RecyclerView 内嵌 ConstraintLayout 再加多层 LinearLayout weight）会让耗时线性甚至超线性增长，因为每层都可能触发两遍 onMeasure（weight 分配与 wrap_content 测量）。
    • 风险模型：这一切都发生在 Choreographer#doFrame 的 traversal 段内，后面还要留出 draw（生成 DisplayList）、sync（BLAST 同步事务）与 RenderThread 的 GPU 提交时间。总时长超过到 deadline 的预算，下一拍 VSYNC 就取不到新 buffer，Choreographer.doFrame() 会打印 Skipped N frames（Choreographer.java:1133）并记为 jank。
    • 观测：measure 与 layout 两个 trace slice（ViewRootImpl.java:5476、5552）；客户端 relayout 的 trace 名形如 <mTag>-relayoutWindow#first=%b/resize=%b/vis=%b/params=%b/force=%b/seqId=%d（ViewRootImpl.java:4204-4208）；WMS 侧 relayoutWindow: <pkg>（Session.java:290-299）；以及 relayoutWindow 内部投的 relayoutSync instant，它要么带 old 到 new 的 frame 尺寸位置，要么带同步原因字符串。

    UI 线程把 View 树录制成 RenderNode DisplayList，再交给 RenderThread

    Choreographer 的 traversal 回调进入 ViewRootImpl.performTraversals() 后，performDraw() 在 UI 线程发起这一拍绘制。硬件加速路径下 ViewRootImpl.draw() 不直接画像素：它先清空 mDirty、处理 invalidateRoot 与 HDR/同步组等事务，然后调用 ThreadedRenderer.draw(mView, mAttachInfo, this)。后者的 updateRootDisplayList() 是该帧真正的“录制”阶段：updateViewTreeDisplayList() 触发 View.updateDisplayListIfDirty()，逐层 RenderNode.beginRecording() → View.draw()/ViewGroup.dispatchDraw() → 子 View 通过 drawRenderNode() 把子 DisplayList 挂进父 DisplayList → endRecording()，最终把根 DisplayList 写进 mRootNode。录制完成后 syncAndDrawFrame(FrameInfo) 经 JNI 进入 RenderProxy::syncAndDrawFrame()，即 DrawFrameTask::drawFrame()：把任务 post 到 RenderThread 队列并 wait 一个 Condition，直到 RT 上的 syncFrameState()/prepareTree() 把 RenderNode 树同步完才 signal 唤醒。因此 UI 线程只是“提交 + 等同步”，真正的 GPU 绘制在 RenderThread 的 CanvasContext::draw() 里继续。

    录制与 GPU 绘制分离：FrameInfo、damage、hardware layer 与掉帧风险

    本阶段最需要建立的心智模型是两段式：UI 线程做 CPU 侧的 DisplayList 录制（把 Canvas 调用变成 native DisplayList 的绘制指令 + 属性），并把 RenderNode 树的脏状态同步给 RT；RenderThread 才做 DisplayList 展开/Skia 录制回放、上传纹理、提交 GPU 命令、dequeue/queue BufferQueue buffer，最后经 SurfaceFlinger/HWC 上屏。Choreographer.doFrame 之后的 UI 线程工作必须在本帧 deadline（FrameInfo 里的 FrameDeadline，FrameInfoIndex::FrameDeadline，base/libs/hwui/FrameInfo.h:46）前完成同步，否则 RT 会拿不到这一拍的更新，表现为 jank；而 RT 侧的 GPU 工作则要赶在下一个 vsync 的 SwapBuffers 前完成。

    hardware layer：当 View 的 layerType 为 LAYER_TYPE_HARDWARE 时，View 对应的 RenderNode 自带一块离屏层（LayerType::RenderLayer）：prepareTree 遍历到它时，RenderNode::pushLayerUpdate()（base/libs/hwui/RenderNode.cpp:186-209）经 CanvasContext::createOrUpdateLayer 建/更新层，再 info.layerUpdateQueue->enqueueLayerWithDamage(this, dirty) 放进 CanvasContext 的 mLayerUpdateQueue（CanvasContext.cpp:550）；真正把层内容画进离屏层发生在 CanvasContext::draw() 里，mRenderPipeline->draw(..., &mLayerUpdateQueue, ...)（CanvasContext.cpp:743）先 renderLayers 再画主帧。注意不要和 DeferredLayerUpdater 混淆：后者服务的是 TextureView/SurfaceTexture 的外部纹理，DrawFrameTask 在 syncFrameState() 里逐个 apply() 的就是它（DrawFrameTask.cpp:182-189）。层的意义是“内容可复用，变换在合成时做”，因此动画期间不必重录 DisplayList；但层一旦失效就要整层重录 + 重新上传纹理，代价比直接画更大。

    GL 还是 Vulkan：RenderThread 用哪条 pipeline 由 Properties::peekRenderPipelineType()（base/libs/hwui/Properties.cpp:216-227）决定：默认值取 ro.hwui.use_vulkan（为真则 "skiavk"，否则 "skiagl"），可被 debug.hwui.renderer（PROPERTY_RENDERER）覆盖，结果为 SkiaVulkan 或 SkiaGL，进程内一旦确定不可再改（overrideRenderPipelineType 会 fatal）。本阶段 UI 线程录制与两者无关，差异全部在 RT 侧的 draw/swap（见下一阶段）。

    damage/脏区：mRecreateDisplayList、PFLAG_DRAWING_CACHE_VALID 决定“录不录”，RT 侧的 mDamageAccumulator（CanvasContext.cpp:548/686）决定“画多大一块”。二者都不等于 ViewRootImpl 的 mDirty（硬件路径已被 setEmpty()）。如果 mDamageAccumulator.finish(&dirty) 得到空 dirty 且 Properties::skipEmptyFrames 成立，RT 可能直接跳过绘制（CanvasContext.cpp:694-699 的 skippedFrameReason 判定），这属于正常省电路径而非丢帧。

    内容边界：mContentDrawBounds 的来源链是 HardwareRenderer.setContentDrawBounds(int,int,int,int)（HardwareRenderer.java:1039）→ JNI android_view_ThreadedRenderer_setContentDrawBounds（android_graphics_HardwareRenderer.cpp:618-621）→ RenderProxy::setContentDrawBounds（RenderProxy.cpp:444-445）→ DrawFrameTask::setContentDrawBounds → syncFrameState() 里 mContext->setContentDrawBounds(mContentDrawBounds)（DrawFrameTask.cpp:190）。在 AOSP 中 DecorView.onContentDrawn() 恒 return false;（base/core/java/com/android/internal/policy/DecorView.java:1847-1849），因此默认窗口路径不会改写它；除测试代码外，base/ 内没有别的 Java 调用者，这一点在源码中就是这样。

    典型耗时与掉帧风险：录制成本基本与“被标记要重录的 View 数 × 各自 Canvas 指令数”成正比；深层 View 调用 invalidate() 时，硬件快路径通常只给祖先置 PFLAG_DIRTY、清 PFLAG_DRAWING_CACHE_VALID，并不会把祖先链全部置为 PFLAG_INVALIDATED；软件 layer 祖先才会被额外置为 PFLAG_INVALIDATED（ViewGroup.java:6201-6231）。父节点已有 DisplayList 且 !mRecreateDisplayList 时，只经 dispatchGetDisplayList() 更新后代，不重录父节点自身（View.java:24318-24324）。常见风险：自定义 View 在 onDraw 里 new 对象/建 Paint、在 onDraw 里读磁盘或做字符串拼接、内容动画每帧 invalidate() 带来的相关 View 重录（不能一概视为祖先链整层重录）、requestLayout() 与 invalidate() 同时调用造成同一帧测量+录制双成本、以及 layer 滥用导致显存与上传带宽双爆。源码中未体现任何“绘制耗时阈值”的硬编码判定，JankTracker 等统计逻辑不在本阶段文件内。

    dequeueBuffer / eglSwapBuffers / queueBuffer 的真实顺序

    GL 路径下 hwui 侧只有一步：SkiaOpenGLPipeline::swapBuffers()（SkiaOpenGLPipeline.cpp:194）先 currentFrameInfo->markSwapBuffers()（:201，jank 指标以此刻为准），再判断 *requireSwap = drawResult.success || mEglManager.damageRequiresSwap()，为真时调 mEglManager.swapBuffers(frame, screenDirty)（:209）。

    EglManager::swapBuffers()（EglManager.cpp:621）做两件事：frame.map(screenDirty, rects) 把脏区转成 EGL 坐标，然后 eglSwapBuffersWithDamageKHR(...)。EGL 驱动经 native window hook 管理 buffer：取得当前 back buffer 后提交针对它的绘制，再在 swap 中 queue 当前帧并附带 GPU 完成 fence；queue 不要求 GPU 此时已执行完。dequeue 可能早于本帧绘制；若驱动在 swap 中取得后续 back buffer，那次 dequeue 不能被解释为当前帧尚未取得 buffer。本仓没有 vendor EGL 实现，不能把所有驱动的 dequeue 固定到同一个调用点。hwui 的 GL pipeline 不直接调用 queueBuffer；native window 回调入口是 Surface::hook_queueBuffer()（native/libs/gui/Surface.cpp:614）。

    Vulkan 路径不同（SkiaVulkanPipeline，由 ro.hwui.use_vulkan / debug.hwui.renderer 选择）：hwui 自己管理 native window。VulkanManager::dequeueNextBuffer（VulkanManager.cpp:583）→ VulkanSurface::dequeueNativeBuffer 里显式 mNativeWindow->dequeueBuffer(...)（VulkanSurface.cpp:409），并把 dequeue fence 导入为 VkSemaphore；提交后 VulkanManager::swapBuffers（:766）→ VulkanSurface::presentCurrentBuffer（VulkanSurface.cpp:496）显式 mNativeWindow->queueBuffer(...)（:520），GPU 完成 fence 作为 acquire fence。两条路径的 window 外面都包着 ReliableSurface：它通过 ANativeWindow_setDequeueBufferInterceptor（ReliableSurface.cpp:57）拦截 dequeue，reserveNext()（:74）保留了预取实现，但本树 DISABLE_BUFFER_PREFETCH = true（ReliableSurface.cpp:31），调用直接返回 OK，不会预 dequeue。实际 dequeue 失败时仍可由 interceptor 使用独立的 fallback buffer 兜底；不要把 fallback 与已禁用的预取混为一谈。

    两个 fence 语义要分清：acquire fence 由生产者提供，表示“GPU 什么时候写完这个 buffer，消费者/合成器可以读”；present fence 由 HWC 在 present 提交时返回，并由 SF 回传，用其 signal 时间描述这一帧的呈现时刻。前者随 queueBuffer 传给 BufferQueue；app 可在 TransactionCompletedListener 的 ON_COMPLETE 回调里拿到后者，但回调和 fence 返回均不保证 fence 已 signal，不能把回调到达时间当作实际上屏时间。

    Surface::queueBuffer → queueBufferImpl（:1330）→ BufferQueueProducer::queueBuffer（BufferQueueProducer.cpp:976）；返回后 Surface::onBufferQueuedLocked（:1428）更新 mNextFrameNumber、transform hint 与 mConsumerRunningBehind。

    进入 BufferQueueProducer::queueBuffer（BufferQueueProducer.cpp:976）后，先 input.deflate(...) 解出 acquireFence、crop、transform、dataspace、scalingMode 等（acquireFence 为 null 直接 BAD_VALUE）。持 mCore->mMutex 后校验 mSlots[slot].mBufferState.isDequeued()，然后：

    BLAST：queueBuffer 之后不再等 latch，而是立刻提交 Transaction

    这是 android17 与旧 BufferQueue 模型最大的差别。旧模型里 queueBuffer 只是把 buffer 放进 SF 侧 BufferQueue 的队列，等 SF 下一次合成时 acquireBuffer 才 latch。BLAST 把这段拆开：

    1. BufferQueueProducer::queueBuffer 回调 BLASTBufferQueue::onFrameAvailable()（native/libs/gui/BLASTBufferQueue.cpp:779）。它只把 mNumFrameAvailable++（:829）记进“影子队列”，然后调 acquireNextBufferLocked(std::nullopt)（:864）。
    2. acquireNextBufferLocked()（:567）用 mBufferItemConsumer->acquireBuffer(&bufferItem, 0, false)（:600）自己当消费者把 buffer 拿回来，mNumAcquired++ 并记 mLastAcquiredFrameNumber。
    3. 构造 SurfaceComposerClient::Transaction，t->setBuffer(mSurfaceControl, buffer, fence, bufferItem.mFrameNumber, mProducerId, releaseBufferCallback, dequeueTime)（:667）连同 dataspace/HDR/damage/crop/transform 一起写入，并 addTransactionCompletedCallback(makeTransactionCallbackThunk(), nullptr)（:672）。
    4. mergePendingTransactions(t, bufferItem.mFrameNumber)（:723）合入 mergeWithNextTransaction 挂起的交易；然后 t->setApplyToken(mApplyToken).apply(false, true)（:726）——one-way 的 ISurfaceComposer::setTransactionState，一步跨进程送到 SF。

    apply 成功会置 mAppliedLastTransaction = true、mLastAppliedFrameNumber、mSetBufferBarrier = true（:738-740）；失败则 LOG_ALWAYS_FATAL。也就是说：BLAST 下 queueBuffer 之后 buffer 几乎立刻（同一调用栈内）就进了 SF 的 Transaction 队列，合成时机由 SF 的 apply token 与 latch 逻辑决定，而不是由 BufferQueue 的占用决定。

    同步提交与单 buffer 模式：mergeWithNextTransaction / transaction ready callback

    当 UI 线程需要“这一帧的改动必须和下一个 buffer 一起生效”时（例如 SurfaceControl.Transaction 的同步提交），走的是 mergeWithNextTransaction()（BLASTBufferQueue.cpp:1100）：若 mLastAcquiredFrameNumber >= frameNumber 说明目标帧已被 acquire，直接 t->setApplyToken(mApplyToken).apply()；否则把交易塞进 mPendingTransactions 并 t->clear()，等 acquireNextBufferLocked 里 mergePendingTransactions 合并。

    另一条路径是 syncNextTransaction()（:887）配合 mTransactionReadyCallback / mSyncTransaction / mAcquireSingleBuffer（BLASTBufferQueue.h:324 默认 true）：此时 onFrameAvailable 会把 buffer 装进复用的 mSyncTransaction 而不立刻 apply，等客户端调 mTransactionReadyCallback 时才把整条交易连同 buffer 一起提交，保证“这组 SurfaceControl 属性 + 这一个 buffer”原子生效。因为要复用同一条 mSyncTransaction，代码在 :796-802 会把上一次塞进去的 buffer 先 releaseBuffer 掉以尽早腾出 slot。

    理解要点：BLAST 的“同步”不是等 buffer，而是让 buffer 与 Transaction 同生共死——buffer 不再单独进 SF 的队列，而是 Transaction 的一个字段。

    三缓冲 / slot 状态机与 dequeue 阻塞条件

    slot 状态定义在 native/libs/gui/include/gui/BufferSlot.h:35 的 struct BufferState，用 mDequeueCount/mQueueCount/mAcquireCount/mShared 四个计数表达五种状态：FREE / DEQUEUED / QUEUED / ACQUIRED / SHARED（同文件 :50-58 的状态表）。isFree() 的实现是 !isAcquired() && !isDequeued() && !isQueued()。

    dequeue 是否阻塞由 BufferQueueProducer::waitForFreeSlotThenRelock()（BufferQueueProducer.cpp:347）决定，条件不止“有没有 free slot”：

    • 在已经 queue 过 buffer（mCore->mBufferHasBeenQueued）之后，已 dequeue 的数量 dequeuedCount >= mCore->mMaxDequeuedBufferCount 直接 INVALID_OPERATION（默认值 1，见 BufferQueueCore.cpp:121；检查在 BufferQueueProducer.cpp:372-373）；
    • mCore->mQueue.size() > maxBufferCount（tooManyBuffers）也会等，防止生产者跑太快把内存吃光；
    • 非阻塞模式（mDequeueBufferCannotBlock 或 mAsyncMode）且 acquired 未超限时返回 WOULD_BLOCK，否则调用虚函数 waitForBufferRelease(lock, mDequeueTimeout)（:438）：基类实现是 mDequeueCondition.wait/wait_for（:448-460）；BLAST 的 BBQBufferQueueProducer 覆写它，解锁后在 BufferReleaseReader::readBlocking 上等 SF 经 BufferReleaseChannel 发来的 release，读到后直接 bbq->releaseBufferCallback(...)（BLASTBufferQueue.cpp:1302-1331）。

    BLAST 侧还有自己的上限：mMaxAcquiredBuffers 默认 1（BLASTBufferQueue.h:206），acquireNextBufferLocked 在 mNumAcquired >= (mMaxAcquiredBuffers + 2) 时直接返回 NO_BUFFER_AVAILABLE（:578）；onFrameAvailable 在同步模式下会 mCallbackCV.wait(_lock) 直到有 buffer 可用（:847-850）。所谓“三缓冲”指的是 slot 总数与 mMaxAcquiredBufferCount + mMaxDequeuedBufferCount 的组合，hwui 侧默认配置不由本文件写死；三缓冲并不意味着 dequeue 永不阻塞。

    GL 路径在 hwui pipeline 里搜不到直接的 queueBuffer 调用不是代码缺失：EGL 经 native window hook 回调 Surface::hook_queueBuffer，再进入 Surface::queueBufferImpl 与 BufferQueueProducer::queueBuffer。dequeue 可能早于本帧绘制，不应把本次 swap 中的 dequeue 一律归给当前帧。Vulkan 路径则由 VulkanSurface 显式调用 dequeueBuffer（VulkanSurface.cpp:409）与 queueBuffer（:520）。

    VSYNC 到达后，MessageQueue::vsyncCallback 在 SF 的调度线程上生成 VsyncId，经 Handler::dispatchFrame 把工作投递到 SurfaceFlinger 主线程（scheduler 线程）。Scheduler 以 commit/composite 两段式驱动 ICompositor：SurfaceFlinger::commit 先调用 updateLayerSnapshots，把 BLAST Transaction 经 TransactionHandler::flushTransactions 应用到 LayerLifecycleManager，重建 frontend::LayerSnapshot，再对每个有 ready frame 的 layer 调用 latchBufferImpl（默认启用 AutoSingleLayer：符合条件的单层简单 buffer 更新可 latch 未 signal 的 acquire fence，其他未就绪事务留队；默认 BLAST layer 的 backpressure 还会阻止同拍后续自动时间戳 buffer 覆盖前一个），必要时 commitTransactions → commitTransactionsLocked → doCommitTransactions 把 mDrawingState 换成 mCurrentState。随后 SurfaceFlinger::composite 组装 CompositionRefreshArgs 并调用 CompositionEngine::present：每个 Output 先 prepare（只做 rebuildLayerStacks/uncacheBuffers），再在 Output::present 的 prepareFrame/prepareFrameAsync 里经 Display::chooseCompositionStrategy 让 HWC validate（或 presentOrValidate 跳过 validate）决定 overlay 还是 client composition，finishFrame 用 RenderEngine 完成 client composition，最后由 Display::presentFrame 调 HWComposer::presentAndGetReleaseFences 提交。主流程由 SF 主线程驱动，部分 HWC 工作可异步或按 display offload；GPU 执行与 fence signal 仍是异步的。超出 sfWorkDuration 可能错过目标上屏时刻，不能把主线程调用返回当作面板已开始显示。

    事务应用：从 BLAST Transaction 到只读 LayerSnapshot

    事务的跨进程入口是 app 侧 SurfaceComposerClient::Transaction::apply()。BLAST 用的是 apply(false, true)，即 oneway binder（BLASTBufferQueue.cpp:726，SurfaceComposerClient.cpp:1146/1190），app 不等 SF 返回。服务端路径：SurfaceFlinger::setTransactionState（SurfaceFlinger.cpp:5579）→ mTransactionHandler.queueTransaction(...)（:5720）→ setTransactionFlags(eTransactionFlushNeeded, ...)（:5729）请求下一次 SF 帧。下一拍 commit 中 clearTransactionFlags(eTransactionFlushNeeded)（:3135）决定是否 flush。真正消费发生在 updateLayerSnapshots（SurfaceFlinger.cpp:2771）：先 mTransactionHandler.collectTransactions()，把 created layers、新事务一次性搬进 frontend::Update，然后 mLayerLifecycleManager.addLayers()，再 mTransactionHandler.flushTransactions()（:2807）取出已就绪的事务，mLayerLifecycleManager.applyTransactions() 把它们写进 RequestedLayerState，再 mLayerHierarchyBuilder.update() 更新层级。

    随后 LayerSnapshotBuilder::update(args) 依据 hierarchy 与 lifecycle manager 生成/复用 frontend::LayerSnapshot（字段如 isVisible、contentDirty、changes、transformedBoundsWithoutTransparentRegion、outputFilter）。快照是只读的中间表示：CompositionEngine、LayerFE 读的是快照，不再直接读 Layer 的 mDrawingState。这就是 android17 的 FrontEnd 架构。

    latch：事务就绪过滤、默认未信号 latch 与 backpressure

    fence 就绪首先由事务队列把关：flushTransactions 只放出通过 ready filter 的事务（addTransactionReadyFilters，SurfaceFlinger.cpp:5478）。transactionReadyBufferCheck（:5359）对带 buffer 的 state 检查：buffer barrier 未满足返回 NotReadyBarrier；开启 backpressure、该 layer 本帧已有待提交 buffer 且事务使用自动时间戳（isAutoTimestamp）时返回 NotReady；acquire fence 仍 Unsignaled 时，若 shouldLatchUnsignaled（:5543）允许且是简单 buffer 更新则为 NotReadyUnsignaled（可提前 latch 未信号 buffer），否则 NotReady，事务留在队列里等下一拍（:5428-5455）。另有 transactionReadyTimelineCheck（:5315）按 desiredPresentTime / frame timeline 拦住“太早”的事务。

    默认未信号 latch 有严格条件：debug.sf.auto_latch_unsignaled 默认 true，选择 AutoSingleLayer（SurfaceFlinger.cpp:598-603）。事务必须只更新一个 layer、是本次 flush 的首个事务、处于非 early 的 VSYNC 配置，并通过 isSimpleBufferUpdate；TransactionHandler::applyUnsignaledBufferTransaction 还要求本次没有其他已就绪事务才取出候选（FrontEnd/TransactionHandler.cpp:118-138）。因此未 signal 不等于必定不能 latch，但也不是所有未信号 buffer 都能提前使用。

    多个 buffer 不等于默认只留最新：BLAST 为 SurfaceControl 设置 eEnableBackpressure（BLASTBufferQueue.cpp:294-297）。同一 layer 的首个 buffer 事务已就绪后，后续自动时间戳事务会被 transactionReadyBufferCheck 拦为 NotReady；TransactionHandler.cpp:202-218 停止消费该 apply-token 队列并保留事务。只有绕过该条件、使多个 buffer 状态确实在 latch 前依次应用等情形，才可能覆盖中间 buffer 并记 dropped，不能把 latest/drop 当作默认 BLAST 窗口规则。

    latch 在 updateLayerSnapshots 的后半段逐 layer 执行：layer->hasReadyFrame() 为真（或需要释放上一帧 buffer）才有资格，随后调用 Layer::latchBufferImpl（Layer.cpp:1506）。它先 latchSidebandStream，然后检查 mDrawingState.buffer && !fenceHasSignaled()。必须结合 Layer::fenceHasSignaled（Layer.cpp:1203-1215）阅读：未信号 latch 配置非 Disabled 时该函数直接返回 true，资格由前面的事务过滤决定；只有配置 Disabled 时才检查 acquire fence 状态，未 signal 则 mFlinger->onLayerUpdate() 并 return false，本拍该 layer 不 latch。不能把此处视为默认配置下一律阻挡 pending acquire fence 的检查。

    通过 fence 检查后，latchBufferStatsAndHandles 记录 acquire signal time、latch time，并把 SurfaceFrame 标记为 PresentState::Presented（Layer::addSurfaceFramePresentedForBuffer，:461，内部 mFrameTimeline->addSurfaceFrame），再 gatherBufferInfo() 把新 buffer 的 crop/transform/dataspace 等采进 mBufferInfo；只有 latch 成功，LayerSnapshot::contentDirty 才为真，才会 invalidateLayerStack 把脏区丢给 Output 的 dirtyRegion。

    内存/IPC 上要分清：BLAST 下 buffer 不是 SF 主动从 BufferQueue 里 acquire 的——BufferData（native/libs/gui/include/gui/LayerState.h:115）随 Transaction 一起 parcel 过来，携带 acquireFence、releaseBufferListener、releaseBufferEndpoint、frameNumber、producerId；SF 侧本树没有对 IGraphicBufferConsumer::acquireBuffer 的调用（grep acquireBuffer native/services/surfaceflinger 无命中），Layer 也不再持有 BufferQueueConsumer。GraphicBuffer 的 handle 通过 binder 的 fd dup 共享同一块 gralloc 内存，不做拷贝。

    合成决策与执行：HWC overlay 还是 GPU client composition

    SurfaceFlinger::composite（:3330）先填 CompositionRefreshArgs：outputs、layers、frameInterval、scheduledFrameTime、bufferIdsToUncache、updatingGeometryThisFrame，并算出 refreshStartTime；然后 mCompositionEngine->present(refreshArgs)（CompositionEngine.cpp:131）。present 的顺序是：preComposition → 每个 output->prepare(args, latchedLayers) → offloadOutputs → 每个 output 的 present(args) 拿到 future 并发提交 → Waiting on HWC 统一 wait → postComposition。

    同一帧内的 SF 相位：APP 与 SF 如何接力，以及耗时预算

    app 与 SF 收到的是同一路硬件 VSYNC，但相位不同：VsyncConfiguration::PhaseOffsets::getDefaultOffsets（Scheduler/VsyncConfiguration.cpp:161）把 mVsyncPhaseOffsetNs（appOffset）与 mSfVSyncPhaseOffsetNs（sfOffset）配成一对。是否“同一周期内接力”取决于配置：只有 appWorkDuration + sfWorkDuration ≤ 刷新周期 时，app 在 V_app 绘制提交、SF 在同一周期更晚的 V_sf 合成才能成立。按 AOSP 的 PhaseOffsets 默认值（vsync_event_phase_offset_ns 与 vsync_sf_event_phase_offset_ns 都是 1ms，VsyncConfiguration.cpp:89-90），sfWorkDuration = period - sfOffset，appOffsetToDuration 结果小于一个周期时还会再加一个周期（:150-158）。因此 60Hz 下 app 从唤醒到 present 约 2 个周期；high fps 下 late app/sf offset 默认 2ms/1ms（:95-96），约 3 个周期。若设置了 debug.sf.use_phase_offsets_as_durations，则走 WorkDuration（SurfaceFlingerDefaultFactory.cpp:46-50），由 app/sf duration 直接决定。

    如果 Transaction 到达 SF 时，本帧的 SF 相位已经跑完 present，SF 就只能等下一帧的 SF 相位再消费，于是多等一拍。appOffsetToDuration 表达的就是这个预算边界：app 的 deadline 是它所对准的那次 SF 唤醒；赶不上时顺延到下一次 SF 唤醒。

    三类 fence 要分别理解：acquire fence 表示生产者写入何时完成，决定消费者何时能安全读取；默认 AutoSingleLayer 在满足条件时允许先 latch，仍需由下游遵守该 fence。present fence 的 signal 时间描述呈现时刻，不等于 present 调用或事务回调的返回时间。逐层 release fence 则描述旧 buffer 何时可安全重写：回调可先携带 pending fence 归还，slot 也可先释放并再次 dequeue，但实际写入必须等待该依赖完成。SF 的 CPU 时间不等于 GPU 完成或上屏时间。

    预算上，SF 从 frameBeginTime 起算，必须在 sfWorkDuration 内完成 commit+latch+composite；HWComposer::presentAndGetReleaseFences 里的 std::this_thread::sleep_until(*earliestPresentTime)（HWComposer.cpp:676-679）是显式的“等到最早可上屏时刻”。超时的后果不是丢这一帧，而是 expectedPresentTime 与实际 present 错位，FrameTimeline 判定为 jank（app 侧表现为掉帧、SurfaceFlinger 侧表现为 sf jank）。

    线程、IPC 与内存：这一拍的数据是怎么进来的

    触发者是 VSYNC：VSyncDispatch 在调度线程上触发，SF 的工作最终在 SurfaceFlinger 主线程（scheduler thread 的 looper）串行执行；MessageQueue 只负责“什么时候跑”，不负责“跑什么”。app 侧 BLAST 的事务走 SurfaceComposerClient::Transaction 的 oneway binder（apply(false, true)）进入 SF 的 TransactionHandler 队列，Transaction 里携带 BufferData（含 GraphicBuffer handle 与 acquire fence fd），fd 通过 binder 的 dup 语义跨进程共享，不做像素拷贝。

    合成阶段如果再拆：CompositionEngine::present 的 output->prepare 与 output->present（含 finishFrame）在 SF 主线程执行，client composition 的 GPU 命令由 SF 主线程提交给 RenderEngine（内部是 EGL/GL 或 Vulkan），但 GPU 执行是异步的，SF 只拿 acquire fence；offloadOutputs 允许把多 display 的 present 调用挪到别的线程，源码注释明确“HWC 调用会阻塞且可能很慢”。所以“SF 主线程耗时”与“这一帧的上屏时间”之间隔着 GPU 与 HWC 两段异步尾巴。

    观测上最实用的是三处：commit <vsyncId> / composite <vsyncId>（SurfaceFlinger.cpp:3012/3342，名字来自 __func__）、Transaction Handling、Composition/Waiting on HWC 的 slice 组合，配合 dumpsys SurfaceFlinger --latency 的 desired/actual present 三元组；如果要看事务本身，用 transaction tracing（mTransactionTracing->addCommittedTransactions，SurfaceFlinger.cpp 内 updateLayerSnapshots 分支）或 Perfetto 的 transaction slice。源码中未体现的部分：HWC 内部调度与面板时序，只能靠 present fence 与 vendor trace。

    本仓库只到 HAL 客户端侧：HWComposer/HWC2（native/services/surfaceflinger/DisplayHardware/）通过 AIDL 接口 aidl::android::hardware::graphics::composer3::IComposer 调 vendor 实现（AidlComposer::presentDisplay，AidlComposerHal.cpp:748，内部 writer->get().presentDisplay(displayId)）。HAL 服务内部如何编程 DRM/KMS（atomic commit、plane 分配、DSI 时序、面板扫描）不在本仓库；内核 drivers/gpu/drm 也不在。任何“DRM atomic 何时生效”的结论都需要另外的源码或 trace，本文只到 present fence 与 presentation timestamp 为止。

    能确定的是契约：presentDisplay 返回一个 present fence（HWC2 语义：这一帧开始扫描输出时 signal；“retire fence”是 HWC1 的旧称，含义不同），随后扫描输出按面板时序进行，什么时候真正点亮像素由 HWC/显示子系统决定。SF 侧用 HWComposer::getPresentFence（HWComposer.cpp:637）取这个 fence，用 getPresentTimestamp（:642，读 lastPresentTimestamp）取 HWC 上报的最近一次呈现时间戳。

    当 HWC 不提供 present fence 时，Layer 会用 getPresentTimestamp 反推：actualPresentTime = now - ((now - presentTimestamp) % vsyncPeriod)（Layer.cpp:1479-1498 一带），并把结果写进 TimeStats/FrameTracer。这说明“实际呈现时间”在源码里是推算而非直接量测。

    present fence：present 是阻塞调用，fence 才是异步信号

    HWComposer::presentAndGetReleaseFences 里有两件事值得注意：一是若 displayData.validateWasSkipped 为真，它不调 present 而是 executeCommands 把之前攒下的 HWC 命令 flush 掉；二是 present 之前可以 std::this_thread::sleep_until(*earliestPresentTime)（:676-679），把帧硬等到“最早可上屏时刻”，用于避免过早提交导致的排队。若前面 presentOrValidate 已直接 present 成功，present/release fence 在 getDeviceCompositionChanges 阶段就已取回（HWComposer.cpp:589-596）。之后 hwcDisplay->present(&displayData.lastPresentFence)（HWC2::Display::present，HWC2.cpp:413）一次拿回 present fence 与全部 layer 的 release fence（getReleaseFences，HWC2.cpp:382）。

    fence 语义要分清：present fence 在这一帧开始扫描输出时 signal（此时上一帧随之被替换下屏）；release fence 是逐层的，其 signal 表示旧 buffer 可被 producer 安全重写。回调传回 release fence、slot 回到 free 列表和 fence signal 是不同事件；BufferQueueConsumer::releaseBuffer 保存 fence 并释放 slot（BufferQueueConsumer.cpp:561-573），下一次 dequeue 将该 fence 交给 producer（BufferQueueProducer.cpp:648-654），写入前仍须等待或导入该依赖。present fence 主要用于呈现统计，在部分移除层的释放路径中也会作为 release 依赖。FrameTarget::setPresentFence 包装并保存 present fence，presentFenceForPreviousFrame 供下一拍功耗时序统计使用；这些操作都不保证 fence 此刻已 signal。

    SurfaceFlinger::onCompositionPresented 在合成提交路径中被调用（SurfaceFlinger.cpp:3522），不是 present fence signal 的回调。TransactionCallbackInvoker::sendCallbacks 把 fence 附到事务结果中，app 的 ON_COMPLETE 回调也不先等待该 fence。因此 present 返回、事务完成回调到达和呈现信号必须分别观测。

    可靠性上源码自己留了退路：mHasReliablePresentFences（SurfaceFlinger.cpp:3830 一带）为 false 时 presentLatency 直接置零，不做推测；注释也指出有些设备的 HWC 不阻塞上一帧的 present fence（:3508-3512）。因此把 present fence 信号时间当成“scanout 时刻”是不严谨的。

    buffer 回收：TransactionCallbackInvoker、binder 与 BufferReleaseChannel

    正常替换路径回传旧 buffer 的释放依赖，不是在实际上屏后才发一个无条件可写通知：后续 buffer 替换 N 后，SF 可先把 N 的 pending release fence 交还 app；slot 经 BBQ 暂扣策略后可以释放，但 producer 必须等 fence signal 才能安全重写。具体链路：

    FrameTimeline：present fence 如何变成端到端可见的时间线

    SurfaceFlinger::onCompositionPresented（SurfaceFlinger.cpp:3775）是所有回传的汇聚点：取各 display 的 present fence，pacesetter 的交给 mTransactionCallbackInvoker.addPresentFence（随 transaction callback 回给 app），同时 targeter->setPresentFence 保存；若该 display 用了 client composition，再取 RenderSurface::getClientTargetAcquireFence 作为 GPU 完成 fence。最后 mFrameTimeline->setSfPresent(presentTime, presentFence, gpuFence)。

    FrameTimeline::setSfPresent（Scheduler/FrameTimeline.cpp:1420）把当前帧 fence 塞进 mPendingPresentFences 后立即调用 flushPendingPresentFences（:2095）。它先查找已非 pending 的 fence；没有则返回，找到后对已完成的帧调用 DisplayFrame::onPresent(signalTime, ...) 并 trace(...)，继续遇到 SIGNAL_TIME_PENDING 时停止。present fence 预期按序完成，若观察到后面的 fence 已完成而前面仍 pending，会把前面的项按错误处理（:2084-2141）。因此jank 分类不是固定 N+1：本帧 fence 在本次 flush 已完成即可当次分类；仍 pending 时可延后多帧，取决于后续 flush 观察到的状态。不能把分类执行时机当作实际呈现时刻，后者取自 fence 时间戳。

    逐层那一侧：latch 时 Layer::addSurfaceFramePresentedForBuffer（:461）已把 SurfaceFrame 以 PresentState::Presented 交给 FrameTimeline；被丢弃的 buffer 走 addSurfaceFrameDroppedForBuffer。分类完成后 FrameTimeline.cpp:1077 构造 gui::JankData，:1102 调 JankTracker::onJankData，后者把数据投到低优先级后台线程，按监听与批处理策略回传给 SurfaceControl.JankData 监听者（OnJankDataListener）。这与 Window FrameMetrics 是不同数据链：后者由 HWUI 的 FrameInfo 经 FrameMetricsReporter、HardwareRendererObserver 上报，FrameMetricsObserver.java:48-49 还明确设置 waitForPresentTime=false。不能把 TOTAL_DURATION/DEADLINE 等归为 SF JankTracker 的回传字段；AndroidX JankStats 的具体适配实现不在本树，不应在此断言其数据源。

    端到端延迟模型：为什么典型是 2~3 个 VSYNC

    把两阶段拼起来：requestLayout 置脏 → 下一拍 appOffset 时 Choreographer 的 doFrame（CALLBACK_TRAVERSAL）→ RenderThread 绘制 → queueBuffer 以 BLAST Transaction 提交 → SF 在它对准的那次 sfOffset 唤醒时消费（赶不上则顺延一次） → commit（latch+快照）→ composite（HWC validate/present 或 GPU client composition）→ present fence → 面板扫描。若 app 在 SF 相位之后才交帧，就多等一拍；若 SF 合成超过 sfWorkDuration，上屏再顺延一拍。所以 2 个 VSYNC 是顺利路径，3 个是常见抖动路径。

    刷新率直接缩放整条预算：60Hz=16.67ms、90Hz=11.11ms、120Hz=8.33ms 一个周期；PhaseOffsets（VsyncConfiguration.cpp:161）把 app 与 SF 的唤醒点错开，appWorkDuration = vsyncDuration + (sfOffset - appOffset)，结果小于一个周期时再加一个周期（:150-158）。只有 appWorkDuration + sfWorkDuration ≤ 周期 时 app 与 SF 才能在同一周期内接力；这取决于配置。按 AOSP 默认 offset（app/sf 都是 1ms，high fps 下 late 为 2ms/1ms，:89-96），app 唤醒到 present 在 60Hz 下约 2 个周期、高刷下约 3 个周期；VsyncModulator 会在 onTransactionCommit（VsyncModulator.cpp:107）等时机切换 early/late/earlyGpu 三套偏移，以适配“有事务提交/有 GPU 合成”的不同场景。

    LTPO 与 PSR 只能作概念说明并标注边界：本仓库可见的是 RefreshRateSelector、LayerHistory 之类的软件选择与 vote 逻辑，面板可变刷新率的硬件行为、以及 PSR（Panel Self Refresh）在面板/DDIC 侧的自刷新与退出延迟，源码中未体现（在 vendor HAL/内核/面板固件中）。因此不能用 SF 侧 present 时间戳精确推断 LTPO 切频时刻或 PSR 退出开销。

    !坑点与边界
    present fence 的 signalTime 是呈现同步的观测值，不等于所有像素扫描或发光完成的精确时刻。HWC 可能不阻塞上一帧 present fence（SurfaceFlinger.cpp:3508 注释），mHasReliablePresentFences 为 false 时 presentLatency 直接置零；没有 vendor HAL 与面板证据，不能从这里断言物理显示延迟的误差方向和幅度。
    释放回调到达、slot free 与安全写入是不同事件：BBQ 可能按 maxAcquiredBufferCount 暂扣 release；交给 BufferQueueConsumer 后可先把 slot 放回 free 列表，不等 release fence signal。dequeue 会返回该 fence，producer 仍须等待或导入依赖后再写；无可用 slot 时的 socket 阻塞读等待的是释放消息，不等于等待 fence signal。
    不要以为 SF 在 releasePendingBuffer 里直接回调 app：它只把 callbackHandles 交给 TransactionCallbackInvoker（Layer.cpp:814-836），release 随 surfaceStats（binder）或 BufferReleaseChannel（socket）一起发出；callReleaseBufferCallback 只用于 latch 前被覆盖的 buffer、EARLY_RELEASE 与 ~Layer。看 trace 时若只有 writeReleaseFence 没有 onReleaseBuffer，不代表 buffer 没回收。
    jank 分类不固定滞后一拍：setSfPresent 加入当前帧后立即 flush 已完成的 present fence，本次即可完成，也可能因 pending 延后多帧。按 fence signal 时间戳和 vsyncId 对齐，不能把分类执行或回调到达时间当作实际呈现时刻，也不能按 N+1 固定偏移。
    LTPO/PSR/DRM atomic 的行为不在本仓库（vendor HAL、内核、面板固件），用 SF 侧时间戳推断切频/自刷新开销属于越界结论。
    release fence 到达 app 不保证 slot 立即 free：BBQ 对 EGL 客户端可能在 mPendingRelease 暂扣（BLASTBufferQueue.cpp:507-531）。反过来，slot free 或 dequeue 成功也不保证能立即写入：BufferQueueConsumer 保存 release fence 后即可释放 slot，producer 必须遵守 dequeue 返回的 fence，直到其 signal 才可覆盖旧内容。

    A为什么不是“越快越好”，而是“对齐节拍”

    显示控制器按固定周期扫描 framebuffer。若在扫描中途替换内容会撕裂；若生产完成得太晚，SF 只能重复上一帧。VSYNC 把连续时间离散化，所有生产者/消费者都对齐到同一组节拍上。

    B三缓冲买到的是“生产窗口”，不是“零延迟”

    本页选择三个 slot 作为直观示例；真实容量由 maxAcquiredBufferCount、maxDequeuedBufferCount、异步模式与配置共同决定。更多可用 buffer 能增加流水线重叠，也可能增加排队延迟，并不固定多一拍。

    C相位的意义：相位差 = appWorkDuration，由配置决定

    APP 与 SF 的唤醒点都从同一个预期上屏时刻倒推，二者相差 appWorkDuration。appWorkDuration + sfWorkDuration ≤ 一个周期时（如本页的 8.3ms + 8.3ms），APP 画完、SF 同周期合成、下一拍上屏；本帧赶不上 SF 唤醒才顺延一个周期。

    04 / JANK & DEADLINES

    掉帧：不是“慢”，而是“晚于截止线”

    本例的 appWorkDuration 为约 8 ms，不是 60Hz 设备的统一预算。错过事务接纳时机可能延后显示，但“晚显示”与“从未显示而被丢弃”不同；GPU fence 晚于 SF 唤醒也不必然错过呈现。真实 jank 还需 FrameTimeline 的预测、阈值与状态共同判断。

    FRAME TIMELINE + TRACE
    区分接纳、呈现、丢弃与依赖等待

    UI 线程：traversal 超预算

    • 层级过深 / 重复 measure：performMeasure 与 performLayout 耗时上升。
    • 绘制指令过多：draw 录制 DisplayList 变慢，RenderNode 树过大。
    • 主线程被 Input、Binder、业务逻辑占用，doFrame 被推迟。
    • 典型证据：Choreographer#doFrame 或 traversal 回调变长，随后出现 skipped frame 告警。

    RenderThread / GPU：绘制与提交超预算

    • GPU 负载过高（过度绘制、大图、复杂 Shader），CanvasContext::draw 拉长。
    • dequeueBuffer 等不到 free slot：队列被 SF 占满，生产者阻塞。
    • queueBuffer 晚于本帧 SF 相位：BLAST Transaction 只能等下一帧 SF 相位。
    • 典型证据：DrawFrame / GPU completion / BufferQueueProducer#queueBuffer 越过 SF VSYNC 相位与 DISPLAY V2。

    SurfaceFlinger：合成超预算

    • client composition 过多（GPU 合成），RenderEngine 耗时增加。
    • 事务因 acquire fence 未就绪留队，或先 latch 后在后续合成 / 呈现路径等待依赖。
    • 主线程被其它事务/回调占用，错过本次 refresh。
    • 典型证据：SF 的 commit / latch / composite / present 跨越 VSYNC。

    Buffer 与背压

    • 三缓冲被占满，app 的 dequeueBuffer 阻塞，UI 线程反过来被拖慢。
    • SF 长时间不 release，生产者没有空闲 slot。
    • 典型证据：结合实际队列容量、持有数量与 fence 状态检查 queueBuffer/dequeueBuffer 等待。

    把掉帧放进时间轴：打开“掉帧演示”，UI 线程的 measure/layout 与绘制时间被拉长，queueBuffer 越过本帧 SF VSYNC 相位与 DISPLAY V2，原本应在 V2 显示的帧要等下一帧 SF 相位合成、到 V3 才上屏，V2 只能重复上一帧。
